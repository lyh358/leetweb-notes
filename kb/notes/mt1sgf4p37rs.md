## 03 FreeRTOS 中两个任务，一个 10ms 执行一次，一个 20ms 执行一次，怎么去实现这种场景？

> 面试回答要点：区分`vTaskDelay()`相对延时、`vTaskDelayUntil()`绝对周期延时，推荐固定周期用`vTaskDelayUntil`。

1. 方式 1：vTaskDelay 相对延时（不推荐做严格周期）

   ```
   vTaskDelay()
   ```

   是相对延时，从任务让出 CPU 那一刻开始计时。任务如果被其他高优先级任务抢占，实际执行周期会漂移。

- 任务 A：循环执行业务，调用`vTaskDelay(pdMS_TO_TICKS(10))`，期望 10ms 一次。
- 任务 B：循环执行业务，调用`vTaskDelay(pdMS_TO_TICKS(20))`，期望 20ms 一次。

> 缺点：存在时间漂移，不适合对周期精度有要求的业务。

2. 方式 2：vTaskDelayUntil 绝对周期延时（推荐）

```
vTaskDelayUntil()
```

以任务上一次唤醒时刻作为基准，保证严格固定周期，不受任务执行时长影响。

- 10ms 任务：以 10ms 为周期调用`vTaskDelayUntil`。
- 20ms 任务：以 20ms 为周期调用`vTaskDelayUntil`。

伪代码示例：

```
//10ms周期任务
void Task10ms(void *arg)
{
    TickType_t xLastWakeTime = xTaskGetTickCount();
    for(;;){
        //业务逻辑
        vTaskDelayUntil(&xLastWakeTime, pdMS_TO_TICKS(10));
    }
}

//20ms周期任务
void Task20ms(void *arg)
{
    TickType_t xLastWakeTime = xTaskGetTickCount();
    for(;;){
        //业务逻辑
        vTaskDelayUntil(&xLastWakeTime, pdMS_TO_TICKS(20));
    }
}
```

> 补充注意：系统 SysTick 时钟节拍要足够细，若`configTICK_RATE_HZ`设置过粗，无法实现 10ms 精度；任务优先级要合理，避免高优先级任务长期占 CPU，导致周期任务被饿死。

## 04 假设一个场景，不改变 IIC 的原有传输协议，如果需要绑定 2^7 以上个设备，该怎么办呢，给出你的思考

I2C 标准 7 位地址，最多只能支持`2^7=128`个从设备，部分地址为保留地址，实际可用小于 120 个。**不能修改协议**，有下面几种方案：

1. I2C 多路切换器（I2C MUX，如 TCA9548）【工业最常用】

   芯片带有多路选通开关，主机只挂 MUX，MUX 分出多路 I2C 总线；每一路 I2C 上可以挂一组 I2C 从机。主机通过控制 MUX 的通道选择，选通某一路总线，间接扩展设备数量。

> 优点：不需要修改原有从设备，完全兼容原有 I2C 协议；缺点：增加外围器件成本。

2. 设备本身带可配置硬件地址引脚

如果外设支持硬件 A0/A1/A2 引脚修改自身 7 位 I2C 地址，同一型号多片设备，通过硬件引脚配置不同地址，挂载同一 I2C 总线。

> 局限：设备地址引脚位数有限，扩展数量有限，不能突破单总线地址上限。

3. 增加多条独立 I2C 硬件总线

MCU 多出几组 I2C 外设，每组 I2C 总线挂载一批从设备。

> 局限：受 MCU 硬件 I2C 外设数量限制。

❌ 不能做的：不修改 I2C 协议前提下，**单条 I2C 总线无法突破 7 位地址 128 个的上限**。

> 总结：项目首选 I2C MUX 多路切换芯片，不改动原有 I2C 协议与从设备，扩展能力强。

## 05 RTOS 相对于裸机开发的优势是什么？

1. **任务管理，业务解耦**

   裸机一般大循环 + 中断，所有业务跑在 while (1)；RTOS 可以把不同业务拆成独立任务，每个任务拥有独立栈，逻辑隔离，代码可读性、可维护性更好。

2. **抢占式调度，实时性更好**

   裸机大循环中，一段代码执行不完，其他业务无法运行；RTOS 抢占调度，高优先级任务可以立刻抢占 CPU，紧急业务可以快速响应，满足实时控制需求。

3. **丰富内核组件**

   提供信号量、互斥锁、消息队列、事件组、任务通知，方便处理中断与任务同步、多任务数据交互、资源互斥访问；裸机需要自己手写同步逻辑，容易出错。

4. **软件复用，降低开发复杂度**

   复杂业务不用手写状态机，按任务拆分开发；提供延时、定时器，周期业务开发简单。

5. **资源管理**

   支持任务栈监控，CPU 利用率统计，方便调试系统性能。

> 补充劣势（面试可以顺带提）：RTOS 会占用 ROM/RAM 资源，对极小资源 MCU 不友好；多任务引入竞争，需要注意死锁、优先级反转问题。

## 07 C++ 的智能指针在嵌入式中解决了什么问题和用法？

### 解决什么问题

1. **解决裸指针内存泄漏**：手动`new/malloc`后忘记`delete/free`，长期运行内存泄露，嵌入式设备长期运行会内存耗尽死机。
2. **解决野指针、悬垂指针**：一块堆内存多处引用，一处释放，其他指针变成野指针。
3. **自动管理堆内存生命周期，RAII 机制，出作用域自动释放内存，不用手动写释放代码**。

> ⚠️嵌入式注意：智能指针依然使用堆内存，堆内存分配有碎片风险；中断上下文**禁止使用动态内存**。

### 三种智能指针用法

1. `std::unique_ptr`：独占所有权。同一个对象只能被一个 unique_ptr 持有，离开作用域自动释放；不允许拷贝，只可以移动。适合嵌入式大多数场景，开销最小。

```
std::unique_ptr<int> p(new int(10));
```

1. `std::shared_ptr`：共享所有权，引用计数机制。多个 shared_ptr 指向同一块内存，引用计数归 0 自动释放。**有计数原子操作开销，嵌入式谨慎使用**，频繁创建销毁会增加性能损耗。

```
std::shared_ptr<int> sp = std::make_shared<int>(20);
```

1. `std::weak_ptr`：配合 shared_ptr 使用，解决循环引用问题，不增加引用计数。

> 嵌入式最佳实践：优先用`unique_ptr`，尽量少用`shared_ptr`；能栈上分配就不用堆；不要在中断里使用智能指针。

## 08 两个 MCU 之间通过 SPI 通讯，如果从机它有数据要向主机发，要怎么设计？

SPI 协议本身是**主机驱动时钟**，只有主机发起 SCLK 时钟，才会交换 MOSI/MISO 数据；从机不能主动产生时钟，从机无法主动发送数据。有下面几种方案：

1. 外部中断引脚（最常用）

   额外增加一根 GPIO 信号线：

   从机 INT 引脚接到主机外部中断引脚。

- 从机有数据要上报：拉高 / 拉低 INT 信号，触发主机外部中断。
- 主机收到中断后，主动发起 SPI 通信，读取从机的数据。

> 优势：标准方案，硬件改动小；主机可以批量读取。

1. 主机轮询查询

   主机周期性调用 SPI，轮询读取从机状态寄存器，判断是否有新数据。

> 缺点：实时性差，浪费主机 CPU，不推荐。

2. SPI 双工模式 + 状态标志

每次主机读写时，从机在返回字节中携带 “有新数据” 标志位；主机解析标志位，如果标志置位，再发起一次 SPI 读取上报数据。

> 缺点：只有主机发起通信时，从机才能通知，事件会有延迟。

> 面试标准答案：实际项目优先**增加从机中断通知线**，从机有数据触发主机外部中断，主机收到中断后启动 SPI 读取数据。

## 09 有了解到 IIC 死锁的内容吗？总线恢复操作是由主机还是从机操作的？

### I2C 死锁原因

1. 通信过程异常，比如主机在传输中途复位，SCL 时钟已经释放，但是 SDA 数据线被从机持续拉低，从机等待主机继续发送时钟，总线卡死。
2. 中断打断 I2C 通信，时序错乱，SDA 被从机拉低，没有收到 STOP 停止信号。

### 总线恢复操作：**由主机执行**

I2C 从机本身没有总线恢复能力，从机只能被动响应时钟。主机进行总线恢复的常用手段：

1. 软件模拟 I2C 总线恢复（最常用）

   主机把 I2C 引脚切换为普通 GPIO 输出，手动模拟产生 9 个 SCL 时钟脉冲；如果 SDA 被从机拉低，在 9 个时钟过程中，从机会释放 SDA；之后主机发送 STOP 信号，释放总线。

> 硬件 I2C 外设，很多 MCU 库也提供类似的总线复位逻辑。

硬件复位 I2C 外设

2. 位 MCU 的 I2C 硬件外设模块，重新初始化。

> 面试总结：I2C 死锁大多是 SDA 被从机持续拉低；**总线恢复一定是主机来操作**，从机无法主动释放总线，主机输出若干个 SCL 时钟，使从机释放 SDA，再发送停止信号恢复总线。
