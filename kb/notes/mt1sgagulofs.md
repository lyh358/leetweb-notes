# =={pink}01 线程池实现==

=={yellow}线程池的核心是**复用线程**避免**频繁创建 / 销毁开销**==，以 C++ 为例的核心实现如下：

## =={pink}1. 核心组件==

- 任务队列：存储 `std::function<void()>` 类型任务，用互斥锁 + 条件变量保证线程安全；
- 工作线程数组：预先创建的线程，循环从队列取任务执行；
- 控制变量：停止标志（`atomic<bool>`）、核心线程数、最大线程数等。

## 2. 核心代码（简化版）

```cpp
#include <vector>
#include <queue>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <functional>
#include <atomic>

class ThreadPool {
public:
    ThreadPool(size_t core_size) : core_size_(core_size), stop_(false) {
        // 初始化核心线程
        for (size_t i = 0; i < core_size_; ++i) {
            workers_.emplace_back([this]() {
                while (true) {
                    std::function<void()> task;
                    {
                        std::unique_lock<std::mutex> lock(mtx_);
                        // 等待：有任务 或 线程池停止
                        cv_.wait(lock, [this]() { return stop_ || !tasks_.empty(); });
                        if (stop_ && tasks_.empty()) return; // 退出线程
                        task = std::move(tasks_.front());
                        tasks_.pop();
                    }
                    task(); // 解锁后执行任务，减少锁持有时间
                }
            });
        }
    }

    // 提交任务
    template<typename F>
    void submit(F&& f) {
        std::lock_guard<std::mutex> lock(mtx_);
        if (stop_) throw std::runtime_error("线程池已停止");
        tasks_.emplace(std::forward<F>(f));
        cv_.notify_one(); // 唤醒一个等待线程（避免惊群）
    }

    ~ThreadPool() {
        { std::lock_guard<std::mutex> lock(mtx_); stop_ = true; }
        cv_.notify_all(); // 唤醒所有线程
        for (auto& t : workers_) if (t.joinable()) t.join();
    }

private:
    size_t core_size_;
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex mtx_;
    std::condition_variable cv_;
    std::atomic<bool> stop_;
};
```

## 3. 关键细节

- 用 `notify_one()` 而非 `notify_all()` 避免惊群效应；
- 任务执行前解锁，减少锁的持有时间；
- 原子变量 `stop_` 保证线程安全的停止控制。

# 02 内存池实现

内存池核心是预先分配一大块连续内存，按需切割分配，减少内存碎片和系统调用开销，核心实现步骤：

1. **初始化**：向系统申请一块大内存（如 `mmap` / `new[]`），按固定大小（如 64B、128B）划分为多个内存块，用链表管理空闲块；
2. **分配**：从对应大小的空闲链表表头取块，若无则扩展内存池或分配新大块；
3. **释放**：将块归还给空闲链表（不立即归还给系统），可合并相邻空闲块减少碎片；
4. **销毁**：将所有预分配的内存归还给系统。

**核心特点**

- 适合频繁分配 / 释放小内存的场景（如网络编程、对象池）；
- 可分为 "固定大小内存池"（简单高效）和 "可变大小内存池"（灵活但复杂）。

# 03 协程底层实现

协程是用户态轻量级线程，由程序自身调度，核心实现依赖 "上下文切换" 和 "栈管理"：

## 1. 上下文切换

- 基于 `ucontext` / `setjmp/longjmp`（用户态）：保存 / 恢复 PC 指针、寄存器、栈指针，无内核态切换开销（比线程快 100~1000 倍）；
- 调度方式：协作式调度（需主动 `yield` 让出 CPU），而非线程的抢占式调度。

## 2. 栈管理

- 每个协程有独立栈（8KB~64KB），分为 "固定栈"（易溢出）和 "分段栈 / 增长栈"（自动扩容）；

## 3. 调度器

- 维护就绪 / 等待队列，协程 `yield` 时保存上下文，从就绪队列取下个协程恢复执行；
- IO 阻塞时，协程挂起并调度其他协程，IO 完成后唤醒。

**核心优势**

- 一个进程可创建数万协程（线程仅数千），适合高并发 IO 场景（如网关、爬虫）。

# 04 进程上下文切换底层实现

进程上下文切换是内核将 CPU 从一个进程切换到另一个的过程，核心步骤：

1. **触发时机**：时钟中断（时间片到）、进程阻塞（IO/sleep）、系统调用等；
2. 切换流程：
  - 硬件触发中断，CPU 切到内核态，保存当前进程的用户态上下文（寄存器、PC、栈）到内核栈；
  - 内核调用 `schedule()`：保存当前进程的内核态上下文到 PCB（`task_struct`），更新进程状态（RUNNING→READY）；
  - 从就绪队列选下一个进程（如 CFS 选 vruntime 最小的），恢复其内核态上下文；
  - 更新 MMU 的页表基址寄存器（CR3），切换地址空间，恢复用户态上下文并执行。
3. **开销来源**：寄存器 / 栈保存、页表切换导致 TLB 失效、内核 / 用户态切换。

# 05 CFS 调度算法底层

CFS（完全公平调度器）是 Linux 默认进程调度算法，核心是 "让每个进程获得均等 CPU 时间"：

1. **核心指标**：虚拟运行时间（`vruntime`） = 实际运行时间 × 1 / 权重（权重与优先级正相关）；
2. **数据结构**：红黑树（按 `vruntime` 排序），始终选 `vruntime` 最小的进程执行；
3. 关键逻辑：
  - 进程运行时累加 `vruntime`，时间片到则触发调度；
  - 高优先级进程权重高，`vruntime` 增长慢，能更频繁被调度；
  - 睡眠进程唤醒时调整 `vruntime`，避免低优先级进程饥饿。

# 06 IPC 通信方式

IPC（进程间通信）的核心方式及特点：

| 方式 | 核心特点 | 适用场景 |
| --- | --- | --- |
| 管道 / PIPE | 半双工、仅父子进程、内核缓冲区 | 简单父子进程通信 |
| 命名管道 / FIFO | 全双工、任意进程（文件路径标识） | 无亲缘关系进程简单通信 |
| 共享内存 | 最快（无内核拷贝）、需同步 | 大数据传输（如数据库） |
| 消息队列 | 按类型 / 优先级收发、异步 | 消息分类场景 |
| 信号量 | 用于同步（互斥 / 计数） | 保护共享资源 |
| 信号 | 异步通知、仅传信号值 | 简单事件通知（退出 / 异常） |
| Socket | 跨主机 / 跨进程、全双工 | 网络通信、本机复杂通信 |

# 07 互斥锁和自旋锁区别

两者均实现互斥，但等待方式和场景不同：

| 维度 | 互斥锁（Mutex） | 自旋锁（Spinlock） |
| --- | --- | --- |
| 等待方式 | 阻塞（放弃 CPU，进入睡眠） | 自旋（循环检测，不放弃 CPU） |
| 开销 | 上下文切换开销大 | 无切换开销，但空转占用 CPU |
| 适用场景 | 临界区耗时长（如 IO、大计算） | 临界区耗时极短（如几行代码） |
| 使用限制 | 可用用户态 / 内核态 | 主要内核态（用户态慎用） |
| 死锁风险 | 持有锁睡眠可能死锁 | 持有锁抢占可能死锁 |

# 08 条件变量底层实现

条件变量用于线程同步（等待某个条件满足），需与互斥锁配合，核心实现：

1. **数据结构**：维护等待队列（存储等待的线程）；
2. 核心操作：
  - `wait()`：原子释放互斥锁 → 线程加入等待队列并睡眠 → 被唤醒后重新获取互斥锁；
  - `signal()`：唤醒等待队列中的一个线程；
  - `broadcast()`：唤醒所有等待线程；
3. 关键细节：
  - 必须循环判断条件（`while(条件不满足)`），避免 "虚假唤醒"（内核因信号 / 超时唤醒）。

# 09 原子变量底层实现

原子变量保证操作不可中断，核心依赖 CPU 硬件指令：

1. **硬件层**：x86 的 `lock` 前缀（锁定总线）、`cmpxchg`（CAS 指令），保证指令执行期间其他 CPU 无法访问该内存；
2. 软件层：
  - 简单类型（int / 指针）：直接封装硬件原子指令（无锁）；
  - 复杂类型：底层退化为自旋锁（有锁）；
3. **核心应用**：CAS 操作实现无锁队列、计数器，避免锁的开销。

# 10 Slab 内存管理

Slab 是 Linux 内核管理小内存的机制，核心是 "缓存复用"：

1. **核心思想**：将相同大小的内核对象（如 `task_struct`、`file_struct`）归类为 Slab 缓存，分配时从缓存取已初始化的对象，释放时保留在缓存中；
2. 结构：
  - `kmem_cache`：每个缓存对应一种对象大小，包含多个 Slab（由物理页组成）；
  - 每个 Slab 维护已分配 / 空闲对象链表；
3. **优势**：减少内存碎片，复用对象避免重复初始化，提升内核内存分配效率。

# 11 Buddy 伙伴系统

Buddy 是 Linux 内核管理物理页框的机制，解决外部碎片问题：

1. **核心思想**：将内存划分为 (2^n) 个页框的块（1 页、2 页、4 页...），分配时拆分为最小匹配块，释放时合并空闲伙伴块；
2. 流程：
  - 分配 4 页：先查 4 页空闲块，无则拆 8 页为两个 4 页，分配一个；
  - 释放 4 页：检查伙伴块是否空闲，空闲则合并为 8 页；
3. **局限**：仅适用于整页分配，小内存需配合 Slab。

# 12 系统调用 callback

系统调用回调是内核完成异步操作后调用用户态注册的函数，核心实现：

1. **注册**：用户态通过 `io_submit` / `signal` 向内核注册回调函数地址和参数；
2. 触发：
  - 传统方式：内核完成操作后发送 `SIGIO` 信号，进程的信号处理函数执行回调；
  - 高效方式（`io_uring`）：用户态与内核共享环形缓冲区，内核写入完成事件，用户态轮询执行回调（无系统调用开销）；
3. **关键**：回调运行在用户态，内核需验证地址合法性。

# 13 DMA 分配内存 API

DMA 内存需物理连续、缓存一致，Linux 内核核心 API：

1. dma_alloc_coherent(dev, size, dma_handle, gfp_flags)
  - 分配物理连续的 DMA 内存，返回内核虚拟地址（CPU 访问）和 `dma_handle`（外设 DMA 地址）；
  - 保证缓存一致性（CPU 和外设数据一致）；
2. `dma_free_coherent(dev, size, cpu_addr, dma_handle)`：释放 DMA 内存；
3. `dma_map_single()`：将普通内存映射为 DMA 地址（需 IOMMU 支持非连续物理内存）。

# 14 零拷贝

零拷贝是减少数据拷贝次数的 IO 优化，核心实现：

1. **传统 IO**：磁盘→内核页缓存→用户缓冲区→内核 socket 缓冲区→网卡（4 次拷贝，2 次 CPU 拷贝）；
2. 零拷贝方式
：
  - `mmap+write`：磁盘→内核页缓存（映射到用户态）→socket 缓冲区→网卡（3 次拷贝，1 次 CPU 拷贝）；
  - `sendfile`：磁盘→内核页缓存→socket 缓冲区→网卡（3 次拷贝，0 次 CPU 拷贝）；
  - `sendfile+DMA scatter‑gather`：磁盘→内核页缓存，网卡直接 DMA 读取（2 次拷贝，0 次 CPU 拷贝）；

# 15 写时复制

## 1. 写时复制（COW）

- **核心**：`fork` 创建子进程时，不拷贝物理内存，仅共享并标记为 "只读"；
- **触发拷贝**：当父 / 子进程写内存时，内核触发页错误，拷贝该页为私有副本；
- **优势**：减少 `fork` 的内存开销，提升进程创建速度。

# 16 创建线程 fork

## 1. fork（创建进程）vs pthread_create（创建线程）

| 维度 | fork（进程） | pthread_create（线程） |
| --- | --- | --- |
| 地址空间 | 独立（COW） | 共享 |
| 资源 | 大部分复制 | 大部分共享 |
| PID | 新 PID | 同进程 PID（TID 不同） |
| 开销 | 大 | 小 |
| 调度 | 内核独立调度 | 进程内调度 |

## 2. fork 的坑

多线程进程中 fork 仅复制当前线程，可能导致子进程继承锁但无其他线程解锁，解决方案：fork 后立即 exec 替换地址空间。
