# A2简历版

# A2：RTOS架构与并发设计

## 1. 对应简历条目

> **RTOS架构与并发：**将网络通信、传感器采集、GPS解析及本地显示拆分为独立任务并绑定双核；通过消息队列（Queue）解耦采集与上传、事件组（EventGroup）管理网络状态、互斥锁（Mutex）保护共享资源，降低高负载场景下的网络阻塞与资源竞争。

这一部分的叙事主线是：

> **大循环存在耦合和阻塞风险 → 按职责拆分六个任务 → 绑定双核 → 用Queue、EventGroup和Mutex处理任务交互 → 降低网络阻塞和资源竞争。**

------

## 2. 为什么不能把所有功能写在一个`loop()`中

智慧蜂箱主控需要同时完成：

- DHT22温湿度采集；
- HX711多次采样和重量计算；
- GPS UART字节接收与NMEA解析；
- Wi-Fi连接和断线重连；
- MQTT连接、心跳和数据上传；
- HTTP请求处理；
- OLED刷新；
- OTA升级处理。

这些功能的执行特点不同：

| 功能        | 执行特点           | 主要风险                        |
| ----------- | ------------------ | ------------------------------- |
| DHT22/HX711 | 周期性采集         | 采样周期被其他模块拖延          |
| GPS         | 连续UART字节流     | 长时间不读取会导致缓冲区溢出    |
| Wi-Fi/MQTT  | 耗时不确定         | 重连和网络发送可能阻塞          |
| HTTP        | 请求到达时间不确定 | 客户端访问可能拖慢主循环        |
| OLED        | 低实时性           | 不应影响核心采集和通信          |
| OTA         | 偶发但耗时较长     | 升级过程可能占用网络和Flash资源 |

如果全部串行放在一个循环里：

```
void loop() {
    readDht();
    readWeight();
    parseGps();
    reconnectWifi();
    mqttPublish();
    handleHttp();
    updateOled();
}
```

一次循环的执行时间等于所有功能耗时之和。任何一个模块变慢，都会影响后面的所有模块。

### 可能出现的问题

#### 网络重连拖慢采集

Wi-Fi连接或MQTT重连耗时可能达到秒级。如果采集和网络写在同一个执行流中，重连期间无法按预期周期采集传感器。

#### GPS接收缓冲区溢出

NEO-6M会持续通过UART输出NMEA数据。如果主循环正在等待网络或执行其他耗时操作，程序不能及时读取UART，接收缓冲区可能溢出，造成语句不完整和定位解析失败。

#### MQTT心跳维护不及时

MQTT客户端需要周期调用`loop()`处理心跳和收发缓存。主循环被其他业务长时间占用时，Broker可能认为设备离线。

#### 采样周期产生较大抖动

即使代码中设置每5秒采集一次，实际周期也会叠加网络、显示、GPS和其他操作的耗时，造成采样间隔不稳定。

#### 看门狗复位风险

ESP32上的`delay()`通常会让当前任务休眠并交出CPU，不等于整个CPU忙等。但如果代码中存在不主动让出CPU的长循环、死循环或长时间临界区，仍可能触发Task Watchdog。

因此，问题的本质不是“不能使用`loop()`”，而是：

> **不适合把执行周期、实时性和阻塞特征完全不同的业务全部耦合在一个串行执行流中。**

------

## 3. 总体设计思路

我按照任务职责和执行特征，将主控程序拆成六个业务任务：

- 网络和通信任务放在Core 0；
- 采集和本地业务任务放在Core 1；
- 跨任务业务数据使用Queue传递；
- 网络连接状态使用EventGroup表达；
- 当前最新状态使用SharedState保存；
- 共享客户端、缓存和总线使用Mutex保护；
- 断网消息写入RAM环形缓存。

整体数据路径为：

```
传感器采集
    ↓
构造遥测消息
    ↓
Telemetry Queue
    ↓
上传任务
    ├─ MQTT可用：发布至云端
    └─ MQTT不可用：写入环形缓存
                         ↓
                   网络恢复后补发
```

## 4. 双核任务划分

## 4.1 Core 0：网络与通信侧

### `taskNetManager`

- **优先级：4**
- 主要职责：
  - 检查Wi-Fi连接；
  - 定期尝试Wi-Fi重连；
  - 检查MQTT连接；
  - 定期尝试MQTT重连；
  - 调用MQTT客户端`loop()`维护心跳；
  - 处理ArduinoOTA；
  - 检查URL OTA请求；
  - 更新EventGroup中的网络状态位。

网络管理任务优先级最高，因为Wi-Fi和MQTT连接是数据上云的基础，MQTT心跳也需要及时维护。

### `taskUploader`

- **优先级：3**
- 主要职责：
  - 从Telemetry Queue中读取新遥测；
  - 通过MQTT发布数据；
  - 发布失败时将数据写入RAM环形缓存；
  - 网络恢复后补发缓存数据；
  - 周期发布设备运行状态。

上传和网络管理拆成两个任务，是为了避免大量数据发送或历史数据补发影响连接维护和MQTT心跳。

### `taskHttpServer`

- **优先级：2**
- 主要职责：
  - 处理本地状态页面；
  - 提供JSON状态接口；
  - 处理Web OTA；
  - 处理设备维护请求。

HTTP服务不是最核心的实时业务，因此优先级低于网络管理和遥测上传。

------

## 4.2 Core 1：采集与本地业务侧

### `taskSensorAcquire`

- **优先级：3**
- **默认采样周期：5秒，可远程修改**
- 主要职责：
  - 读取DHT22温湿度；
  - 读取HX711称重结果；
  - 检查传感器数据有效性；
  - 读取共享状态中的最新GPS信息；
  - 生成告警位；
  - 构造完整`TelemetryMessage`；
  - 更新SharedState；
  - 向Telemetry Queue发送消息。

传感器任务只负责采集和生成数据，不直接调用MQTT发送。

### `taskGpsReader`

- **优先级：3**
- **轮询间隔：约10毫秒**
- 主要职责：
  - 持续读取硬件UART接收缓冲；
  - 将NMEA字节交给TinyGPSPlus；
  - 判断定位是否有效；
  - 更新经纬度和卫星数量；
  - 将最新定位写入SharedState。

GPS任务和传感器任务优先级相同，但GPS任务每次处理后会主动延时，两个任务可以通过FreeRTOS调度交替运行。

### `taskOledDisplay`

- **优先级：1**
- **默认刷新周期：1秒**
- 主要职责：
  - 读取SharedState快照；
  - 显示温湿度、重量；
  - 显示Wi-Fi、MQTT和GPS状态；
  - 显示离线缓存数量。

OLED只是辅助显示，允许出现一定延迟，因此优先级最低。

------

## 5. 优先级和抢占关系

FreeRTOS中，数值越大，任务优先级越高。

### Core 0

```
taskNetManager：4
       ↓
taskUploader：3
       ↓
taskHttpServer：2
```

当网络管理任务需要运行时，可以抢占上传任务和HTTP任务。网络管理任务阻塞或延时后，上传和HTTP任务继续运行。

### Core 1

```
taskSensorAcquire：3
taskGpsReader：3
       ↓
taskOledDisplay：1
```

传感器和GPS任务优先级相同，在启用时间片调度时可以轮转运行。由于它们都会主动阻塞或延时，OLED可以在高优先级任务不就绪时获得CPU。

核绑定和优先级只能降低相互干扰，不能提供绝对实时保证。中断、系统Wi-Fi任务、临界区和锁等待仍可能带来调度延迟。

# 6. Queue：解耦采集和上传

## 6.1 为什么使用Queue

传感器采集属于周期性任务，而MQTT上传耗时受网络状态影响。如果采集任务直接调用`publish()`：

```
采集 → 等待网络发送 → 下一次采集
```

网络变慢时，采集任务也会被拖慢。

改为Queue后：

```
采集任务 → Queue → 上传任务 → MQTT
```

采集任务只需要将消息放入队列，不必等待网络发送完成。

## 6.2 Queue中传递什么

队列中传递完整的`TelemetryMessage`，主要包括：

- 消息序号；
- 设备运行时间；
- 温度；
- 湿度；
- 重量；
- GPS经纬度；
- GPS有效标志；
- 卫星数量；
- Wi-Fi RSSI；
- 告警位；
- 是否来自离线补发。

消息按值复制进入Queue，上传任务获得的是某个采样时刻的一致快照，不会出现上传过程中温度已经更新、GPS还是旧值等“读到一半新一半旧”的问题。

## 6.3 队列满了怎么办

当前Queue容量为16条。

采集任务发送消息时只等待有限时间。如果Queue已满，不会永久阻塞采集，而是将消息转存到RAM环形缓存。

```
Queue未满 → 正常入队
Queue已满 → 写入离线环形缓存
```

这是一种背压处理策略，目标是保证采集任务继续运行。

------

# 7. EventGroup：统一管理网络状态

## 7.1 为什么不使用多个普通布尔变量

如果分别使用：

```
bool wifiConnected;
bool mqttConnected;
```

多个任务并发访问时，需要额外加锁，而且难以等待多个组合条件。

EventGroup可以使用一个对象表达多个状态位：

- `BIT0`：Wi-Fi已连接；
- `BIT1`：MQTT已连接。

## 7.2 各任务如何使用

网络管理任务负责设置和清除：

```
Wi-Fi连接成功 → 设置WIFI位
MQTT连接成功 → 设置MQTT位
Wi-Fi断开 → 同时清除WIFI位和MQTT位
```

上传任务读取MQTT状态位：

```
MQTT位存在 → 尝试发布
MQTT位不存在 → 写入缓存
```

Wi-Fi断开时同时清除MQTT位，是因为MQTT依赖底层TCP/IP连接。

## 7.3 EventGroup不用于传递业务数据

EventGroup适合表达“现在处于什么状态”，不适合保存温度、重量等数据。

因此：

- 网络状态使用EventGroup；
- 遥测消息使用Queue；
- 当前最新数值使用SharedState。

------

# 8. SharedState：保存当前最新状态

除了需要上传的历史消息，OLED和HTTP还需要随时查看当前状态。

因此系统维护`SharedState`，保存：

- 最新温湿度；
- 最新重量；
- 最新GPS；
- 网络连接状态；
- 采样周期；
- 离线缓存数量；
- 重连次数；
- 最近一次成功时间。

## 为什么不全部使用Queue

Queue中的消息会被上传任务消费。OLED和HTTP如果也从同一个Queue读取，就可能抢走本应上传的数据。

因此两者职责不同：

| 数据结构    | 适用场景                 |
| ----------- | ------------------------ |
| Queue       | 需要按顺序消费的历史消息 |
| SharedState | 多个模块读取当前最新值   |

## 快照读取模式

OLED和HTTP不会拿着锁完成整个显示或页面生成过程，而是：

```
获取stateMutex
      ↓
复制SharedState
      ↓
释放stateMutex
      ↓
使用本地副本完成绘图或JSON生成
```

这样可以缩短临界区，避免慢操作长期占用互斥锁。

------

# 9. Mutex：保护共享资源

## 9.1 `stateMutex`

保护`SharedState`。

可能并发访问它的任务包括：

- 传感器任务；
- GPS任务；
- 网络任务；
- 上传任务；
- OLED任务；
- HTTP任务。

没有锁时，一个任务可能在另一个任务更新结构体的过程中读取，得到不一致的数据。

## 9.2 `mqttMutex`

保护`PubSubClient`。

- 网络任务会执行`connect()`和`loop()`；
- 上传任务会执行`publish()`。

`PubSubClient`不是线程安全对象。如果两个任务同时操作其内部网络缓存和Socket状态，可能造成数据损坏或连接异常。

## 9.3 `cacheMutex`

保护RAM环形缓存的：

- 数据数组；
- 头指针；
- 当前数量。

上传任务可能一边补发，另一个路径又在写入失败消息，因此需要互斥访问。

## 9.4 `i2cMutex`

保护OLED和I²C总线。

当前主要由OLED任务使用，同时为以后接入其他I²C设备保留统一的总线保护机制。

## 9.5 为什么使用Mutex而不是普通二值信号量

Mutex专门用于资源互斥，并支持优先级继承。

如果低优先级任务持有锁，而高优先级任务等待该锁，FreeRTOS可以临时提升持锁任务的优先级，使它尽快完成临界区并释放锁，降低优先级反转的影响。

------

# 10. RAM环形缓存与并发关系

当出现以下情况时，数据进入离线缓存：

- MQTT未连接；
- MQTT发布失败；
- Telemetry Queue已满。

缓存使用固定长度数组：

- 长度为48条；
- 使用`head`和`count`维护；
- 写入和读取复杂度为O(1)；
- 不需要频繁动态分配内存；
- 满时覆盖最旧数据。

网络恢复后，上传任务每轮最多补发4条，每条之间短暂让出CPU。

这样做是为了避免：

```
网络恢复
    ↓
一次性补发几十条
    ↓
占满MQTT链路
    ↓
新数据、心跳和其他任务得不到处理
```

当前缓存位于RAM，设备掉电后数据会丢失。NVS目前用于采样周期等参数持久化，不等同于遥测持久队列。

# 11. 完整运行流程

## 正常联网

```
1. GPS任务持续解析定位并更新SharedState
2. 传感器任务周期读取DHT22和HX711
3. 传感器任务合并最新GPS，构造TelemetryMessage
4. 更新SharedState
5. 将消息写入Telemetry Queue
6. 上传任务从Queue中取出消息
7. EventGroup显示MQTT已连接
8. 上传任务获取mqttMutex
9. 调用MQTT publish上报云端
10. OLED和HTTP从SharedState读取最新状态
```

## 网络断开

```
1. 网络任务发现Wi-Fi或MQTT断开
2. 清除EventGroup状态位
3. 网络任务按周期尝试重连
4. 传感器和GPS任务继续运行
5. 上传任务发现MQTT不可用
6. 新遥测写入RAM环形缓存
```

## 网络恢复

```
1. 网络任务重新连接Wi-Fi和MQTT
2. 设置EventGroup状态位
3. 上传任务发现MQTT恢复
4. 从环形缓存中按顺序取历史消息
5. 每轮最多补发4条
6. 补发期间继续处理新的Queue消息
```

------

# 12. 这套设计最终解决了什么

对应简历中“降低高负载场景下的网络阻塞与资源竞争”，可以具体解释为：

- 网络重连不会直接停止传感器采集；
- GPS由独立任务持续读取，降低UART数据丢失风险；
- 采集任务不等待MQTT发送；
- 网络维护与遥测上传职责分离；
- HTTP和OLED等辅助功能采用较低优先级；
- 多任务访问MQTT客户端和共享状态时有明确互斥机制；
- Queue和共享快照分别承担历史消息与最新状态；
- 网络断开后仍然采集，并在恢复后限速补发。

------

# 13. 当前设计的边界

这是一套软实时物联网终端架构，不是严格硬实时系统。

当前仍有以下改进空间：

- 传感器周期使用相对延时，存在累计漂移，严格周期可改用`vTaskDelayUntil()`；
- 任务优先级和栈大小需要通过运行时统计继续验证；
- 应监控任务栈High Water Mark和最小剩余Heap；
- 固定重连周期可改成指数退避加随机抖动；
- RAM缓存掉电丢失，关键数据可设计Flash或FRAM持久队列；
- 应统一锁获取顺序，避免复杂版本中产生死锁；
- I²C互斥锁当前更多是扩展性设计；
- 双核绑定降低干扰，但不等于绝对实时隔离。

主动说明这些边界，比把系统描述成“工业级完美实现”更可信。

# 14. 面试口述版

> 这个终端需要同时处理传感器采集、GPS连续解析、Wi-Fi/MQTT通信、HTTP服务和OLED显示。如果全部写在一个`loop()`里，网络重连或HTTP请求等不确定时延操作会拖慢整个执行流，造成采样抖动、GPS串口数据积压，甚至影响MQTT心跳。  
>
> 所以我将业务拆成六个FreeRTOS任务：Core 0运行网络管理、遥测上传和HTTP服务，Core 1运行传感器采集、GPS解析和OLED显示。网络管理优先级最高，OLED优先级最低。  
>
> 任务间我根据数据语义选择不同机制：采集和上传通过Queue传递完整遥测快照，EventGroup表达Wi-Fi和MQTT连接状态，SharedState保存当前最新数据；对SharedState、MQTT客户端、离线缓存和I²C总线分别使用Mutex保护。断网时采集继续运行，遥测进入RAM环形缓存，恢复后限速补发。这样将网络通信与周期性采集隔离，并减少多任务并发访问造成的资源竞争。
