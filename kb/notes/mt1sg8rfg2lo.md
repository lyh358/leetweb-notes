# =={pink}01 select\poll\epoll 区别==

核心答案：=={green}三者均为 **Linux IO 多路复用机制**，用于**监听多个文件描述符（FD）的读写事件**==，=={yellow}**核心差异**在 **FD 管理方式、效率、底层实现**，epoll 是高性能主流方案。==关键对比表：

| 特性 | select | poll | epoll |
| --- | --- | --- | --- |
| FD 管理 | =={yellow}数组==，最大 FD 受限（默认 =={yellow}1024==） | =={yellow}链表==（pollfd 数组），=={yellow}无 FD 数量限制== | =={yellow}红黑树 + 就绪链表==，=={yellow}无 FD 数量限制== |
| 效率 | =={yellow}轮询==所有 FD，=={yellow}O (n)==，FD 越多越慢 | =={yellow}轮询==所有 FD，=={yellow}O (n)==，仅解决数量限制 | =={yellow}仅遍历就绪 FD，O (1)==，高性能 |
| 触发方式 | 仅水平触发（LT） | 仅水平触发（LT） | 支持 LT / 边缘触发（ET，更高效） |
| 内存拷贝 | =={yellow}**每次调用拷贝**整个 FD 集合==到内核 | =={yellow}**每次调用拷贝** pollfd 数组==到内核 | =={yellow}**仅初始化时拷贝**==，后续共享内存 |
| 适用场景 | 少量 FD、兼容性要求高 | 中量 FD、突破 1024 限制 | 大量 FD（如高并发服务器） |

- 补充：边缘触发（ET）仅在 FD 状态变化时通知（如从无数据到有数据），需一次性读完缓冲区；水平触发（LT）只要有数据未处理就持续通知。

# 02 socket 客户端和服务器端收发函数 flow

## (1) TCP 服务器端流程

- 关键函数说明：
  - `socket()`：创建套接字，返回 FD；
  - `bind()`：绑定本机 IP 和端口，避免随机端口；
  - `listen()`：设置监听队列长度（如`listen(fd, 5)`，5 为半连接队列大小）；
  - `accept()`：返回新的通信 FD（与客户端一一对应），原监听 FD 仍可用；
  - `recv()/send()`：基于新 FD 收发数据，可循环读写直到数据传输完成。

## (2) TCP 客户端流程

- 关键差异：客户端无需`bind()`（系统自动分配随机端口），直接`connect()`发起连接。

## (3) UDP 流程（无连接）

- 服务器端：`socket() → bind() → recvfrom()/sendto()`（需指定对方 IP + 端口）；
- 客户端：`socket() → sendto()/recvfrom()`（无需`connect`，每次收发指定服务器地址）。

# 03 socket 传入参数

核心答案：`socket()`函数是创建套接字的入口，核心参数定义套接字的协议族、类型、具体协议，函数原型：

```cpp
int socket(int domain, int type, int protocol);
```

参数详解：

| 参数 | 取值及作用 |
| --- | --- |
| domain | 协议族（地址族）：- `AF_INET`：IPv4 网络协议（最常用）；- `AF_INET6`：IPv6；- `AF_UNIX`：本地进程间通信。 |
| type | 套接字类型：- `SOCK_STREAM`：流式套接字（TCP，可靠、有序、面向连接）；- `SOCK_DGRAM`：数据报套接字（UDP，不可靠、无连接）；- `SOCK_RAW`：原始套接字（如 Ping、抓包）。 |
| protocol | 具体协议：- 0：自动匹配 type 对应的默认协议（如`SOCK_STREAM`→TCP，`SOCK_DGRAM`→UDP）；- `IPPROTO_TCP` / `IPPROTO_UDP`：显式指定。 |

# 06 TCP 和 UDP 区别

核心答案：TCP 和 UDP 是传输层核心协议，核心差异在可靠性、连接性，适配不同业务场景。

| 特性 | TCP | UDP |
| --- | --- | --- |
| 连接性 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠传输（重传、确认、排序、校验） | 不可靠（无确认、重传，可能丢包） |
| 有序性 | 保证数据有序到达 | 无序，可能乱序 |
| 拥塞控制 | 支持（cwnd 调整速率） | 无，发送速率不受限 |
| 开销 | 高（头部 20‑60 字节，握手 / 挥手） | 低（头部 8 字节） |
| 适用场景 | 文件传输、HTTP、邮件（需可靠） | 音视频、直播、DNS（需高速） |

# 07 TCP 粘包

核心答案：TCP 粘包是连续发送的小数据包被合并成一个大数据包接收，本质是 TCP 的 “流式传输” 特性（无消息边界）。

## (1) 粘包原因

1. 发送方：Nagle 算法合并小数据包（减少网络交互）；
2. 接收方：缓冲区未及时读取，多个数据包堆积；
3. 网络：数据包合并传输（如 MTU 限制）。

## (2) 解决方法（核心是定义消息边界）

1. **定长包**：固定每个数据包长度（如每次发 1024 字节，不足补 0）；
2. **分隔符**：数据包末尾加特殊分隔符（如`\r\n`，HTTP 用此）；
3. **包头 + 长度**：包头固定字节数，包含数据长度（最常用）：

```undefined
包头（4字节，存储数据长度） + 数据体（实际内容）
```

- 示例：接收方先读 4 字节获取长度，再按长度读取数据体，避免粘包。

# 11. TCP 为什么会粘包？怎么解决？

- **考察场景**
考察你是否理解 TCP 是字节流协议，不保留应用层消息边界。
- **底层实现原理**

1. TCP 只保证字节流可靠、有序，不保证一次 `send()` 对应一次 `recv()`。
2. 多次小包可能被 TCP 合并发送，接收端一次读到多条消息，这就是 “粘包”。
3. 一条大消息也可能被拆成多次接收，这叫 “拆包”。
4. 本质原因是：TCP 面向流，应用层需要自己定义消息边界。
5. 解决方法通常是：固定长度、分隔符、长度字段、TLV 协议。

- **代码说明**

```cpp
/* 常见协议头：长度 + 数据 */
struct packet_header {
    uint32_t len;  // 后面payload长度，网络字节序
};
```

发送：`[ len ][ payload ]`

接收：

1. 先读固定长度 header
2. 解析 payload 长度
3. 再循环读满 payload

# 15. 阻塞 IO、非阻塞 IO、同步 IO、异步 IO 的区别？

- **考察场景**
考察你是否理解 **等待数据** 和 **数据拷贝完成** 这两个阶段的区别。
- **底层实现原理**

1. **阻塞 IO**：调用 `read()` 后，如果没数据，线程一直睡眠等待。
2. **非阻塞 IO**：没数据时立即返回 `EAGAIN/EWOULDBLOCK`，应用自己稍后再试。
3. **同步 IO**：数据准备和拷贝阶段仍然由调用线程参与，常见阻塞 / 非阻塞 socket 都属于同步 IO。
4. **异步 IO**：应用发起请求后立即返回，内核完成数据准备和拷贝后再通知应用。
5. 所以重点是：**阻塞 / 非阻塞描述等待方式，同步 / 异步描述完成方式。**

- **延申知识点**
- select/poll/epoll 属于同步 IO 还是异步 IO
- Reactor 和 Proactor 的区别

# 16. epoll 的 ET 模式为什么必须使用非阻塞 socket?

- **考察场景**
考察你是否理解边缘触发只在状态变化时通知一次。
- **底层实现原理**

1. epoll 的 **LT 水平触发**：只要 fd 还有数据没读完，就会一直通知。
2. epoll 的 **ET 边缘触发**：只有状态从 “无数据” 变成 “有数据” 时通知一次。
3. ET 模式下，如果一次没有把 socket 缓冲区读空，后面可能不会再通知。
4. 所以必须用非阻塞 socket 循环读，直到 `EAGAIN`，表示真的读空了。
5. 如果用阻塞 socket，循环读可能卡死在 `read()`，导致整个事件循环被阻塞。

- **延申知识点**
- epoll LT 和 ET 的区别
- epoll 为什么适合高并发连接

# 17. connect 失败或超时怎么处理？

- **考察场景**
考察你是否会处理网络不可达、服务未启动、弱网、非阻塞连接等情况。
- **底层实现原理**

1. `connect()` 失败要看 `errno`，比如 `ECONNREFUSED`、`ETIMEDOUT`、`ENETUNREACH`、`EHOSTUNREACH`。
2. 阻塞 `connect()` 可能卡很久，嵌入式里通常用 **非阻塞 connect + select/epoll** 超时控制。
3. 非阻塞 connect 返回 `EINPROGRESS` 不代表失败，而是连接正在建立。
4. 等待 socket 可写后，用 `getsockopt(SO_ERROR)` 判断最终连接结果。
5. 失败后要做**退避重连**，不要死循环高频重连打满 CPU 或网络。

**18. TCP keepalive 和应用层心跳有什么区别？**

- 考察场景
  考察你是否理解 内核保活 和 业务保活 的区别。

- 底层实现原理
1. TCP keepalive 是 TCP 协议栈提供的保活机制，由内核发送探测包。
2. 它主要判断 TCP 连接是否还活着，但默认周期通常很长，不适合快速业务检测。
3. 应用层心跳 是业务协议自己定义的 ping/pong 消息，可以带设备状态、时间戳、序列号。
4. 应用层心跳能更快发现业务无响应，比如服务器进程卡死但 TCP 连接还没断。
5. 所以区别是：keepalive 保连接，应用心跳保业务状态。

**19. UDP 如何实现可靠传输？**

- 考察场景
考察你是否理解 UDP 本身不可靠，但应用层可以补可靠机制。
- 底层实现原理

1. UDP 不保证到达、不保证顺序、不保证不重复。
2. 要可靠，就要在应用层增加 序号、ACK、超时重传、去重、乱序重排。
3. 每个包带 `seq`，接收端收到后回复 ACK。
4. 发送端超时没收到 ACK，就重发该包。
5. 如果还要提高效率，可以做 滑动窗口、选择重传、FEC 前向纠错。

```rust
可靠 UDP 流程：
发送 data(seq=1)
-> 接收端校验
-> 返回 ack(seq=1)
-> 发送端收到 ACK 后删除缓存
-> 超时未收到 ACK 则重传

需要处理：
1. 丢包 -> 重传
2. 乱序 -> 按 seq 重排
3. 重复包 -> 去重
4. 数据损坏 -> checksum 校验
```

**20. 大文件或 OTA 升级如何设计传输协议？**

- 考察场景
考察你是否理解 OTA 不是简单下载文件，而是要保证完整性、断点续传、掉电安全和回滚。
- 底层实现原理

1. 大文件要 分片传输，每片带序号、长度、CRC/hash，方便校验和重传。
2. 设备端要支持 断点续传，记录已下载 offset，网络断开后从断点继续。
3. 下载完成后要做 整包 hash / 签名校验，防止文件损坏或被篡改。
4. 写 Flash/eMMC 时要考虑 掉电保护，常用 A/B 分区或临时分区，验证成功后再切换启动标志。
5. 所以 OTA 协议核心是：分片、校验、续传、验签、原子切换、失败回滚。

**21. 网络字节序和主机字节序是什么？**

- 考察场景
考察你是否理解 不同 CPU 大小端不同，网络协议必须统一字节顺序。
- 底层实现原理

1. 主机字节序 是 CPU 本地存储多字节数据的方式，可能是小端，也可能是大端。
2. 网络字节序 规定统一使用 大端序 Big Endian。
3. TCP/IP 协议头里的端口、IP、长度等多字节字段，都要按网络字节序传输。
4. 小端 CPU 发送前要把主机序转换成网络序，接收后再转回来。
