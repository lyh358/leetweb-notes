## 3. 业务背景：为什么基站需要信道估计

无线信号从基站到终端会经历衰落、多径、噪声和相位旋转。接收端观测可简化为：

```text
Y = H·X + N
```

- `X`：已知导频或发送符号；
- `Y`：接收符号；
- `H`：需要估计的复数信道响应；
- `N`：噪声。

信道估计的目标是根据 SRS/DMRS 等已知参考信号估计 `H`，供均衡、波束赋形、检测和调度使用。误差会沿后续链路放大，因此既要求精度，也要求低时延和稳定吞吐。

- SRS：终端发送的上行探测参考信号，帮助基站感知上行信道。
- DMRS：解调参考信号，与业务信道相关，用于解调时估计信道。
- RB：Resource Block，频域资源分配基本单位；10RB/20RB 会影响频域张量长度。
- L1：物理层，靠近硬实时数据面，时延预算严格。

AI 方案不是凭空替代传统估计，而是用学习到的非线性映射增强粗估计，提升复杂信道条件下的恢复能力。工程上仍需与传统流程、业务门限和硬件预算共同评估。

## 4. BESA_AI 总体架构

```text
L1 IPC 输入 SRS/DMRS
        ↓
SPF：生成粗粒度信道估计/特征
        ↓

        ↓

        ↓

        ↓

```

部署链路：

```text
PyTorch .pth
   ↓ 导出
ONNX 静态计算图
   ↓ ATC 编译、图优化、算子选择与融合

   ↓ ACL Runtime
```

C++ 侧通常完成 ACL 初始化、Device/Context/Stream 创建、模型加载、Host/Device 内存管理、异步执行与 IPC 对接。`aclmdlExecuteAsync` 允许执行挂到 Stream 上；真正获得并行收益还要看前后处理、拷贝依赖、缓冲区复用和同步点。

## 5. SPF_27B_10RB 模型结构

### 5.1 基本信息

| 项目 | 数值/结构 |
| --- | --- |
| 输入、输出 | FP32，`(1,4,32,32,1)` |
| 主干 | 4 层 Transformer |
| 参数量 | 25,428 |
| 主要算子 | Conv 18、MatMul 8、Softmax 4、Tanh 4 |
| 总计算量 | 约 48.9M MACs |
| 计算组成 | Cube 61.8%，Vector 38.2% |
| 10RB/20RB | 权重相同，频域长度主要为 32/48 |

输入先去掉末尾单例维，形成 4D 骨干特征。每层大体执行：

```text
x
├─ LayerNorm
├─ Q/K/V 投影（Conv）
├─ Q·Kᵀ
├─ Scale
├─ Softmax
├─ Score·V
├─ 输出投影（Conv）
├─ 残差 Add
├─ LayerNorm
├─ FFN + GELU
└─ 残差 Add
```

### 5.2 注意力细节

标准缩放点积注意力：

```text
S = QKᵀ / √d_k
P = softmax(S)
O = PV
```

除以 `√d_k` 是为了避免维度增大后点积方差过大，Softmax 进入饱和区导致梯度或数值分辨率变差。推理侧虽没有反向传播，但缩放仍属于训练得到的函数语义，不能随意删除。

多头注意力让不同 Head 学习不同子空间关系。该模型规模小、Shape 固定，问题并不是计算量绝对巨大，而是小算子多、融合敏感、调度和 GM 往返占比高。

### 5.3 Conv 为什么出现在 Transformer 中

1×1 或小卷积可以承担通道投影，语义类似线性层，同时适配已有张量布局和昇腾算子路径。Conv、MatMul 最终是否高效，取决于 Shape、数据格式、Cube 对齐和编译器选算子，不能仅凭算子名字判断。

### 5.4 GELU 与 Tanh

常见 GELU 近似式：

```text
GELU(x) ≈ 0.5x[1+tanh(√(2/π)(x+0.044715x³))]
```

也可用 Erf 精确表达：

```text
GELU(x) = 0.5x[1+erf(x/√2)]
```

数学表达更简洁或理论运算数更少，不代表在 NPU 上更快；CANN 对特定子图的融合支持决定了实际 Kernel 数和数据搬运。

## 6. Ascend 部署工具链

### 6.1 ONNX、ATC、OM、ACL 各自做什么

- ONNX：跨框架静态图表示，保存算子、权重、拓扑和 Shape 信息。
- ATC：离线编译器，将 ONNX 解析为目标 SoC 可执行 OM，期间做 Shape 推导、算子映射、数据格式选择、融合和内存规划。
- OM：面向指定 Ascend 芯片/CANN 版本的离线模型，不是通用模型格式。
- ACL：运行时 API，负责设备、上下文、Stream、内存、模型加载、执行和同步。
- msprof：采集模型、Task/Kernel、时间线和硬件利用信息，帮助判断计算、搬运、调度或同步瓶颈。

### 6.2 为什么固定 Shape 有价值

固定 Shape 后，编译器能提前知道内存大小、布局和算子参数，动态 Shape 推导链可被折叠，融合模式更容易匹配。代价是失去运行时灵活性；多配置场景可以准备多个 OM，或使用平台支持的动态档位。

### 6.3 基线如何建立

正确基线应固定：硬件、CANN/驱动、模型、精度模式、输入 Shape、预热次数、正式循环次数和计时边界。

典型步骤：

1. ATC 编译原始 ONNX，保存日志和 OM。
2. 使用同一输入做 CPU ONNX 与 NPU OM 数值对比。
3. 预热，排除首次加载、缓存和初始化开销。
4. 循环执行，统计均值、分位数和抖动；明确是否包含 H2D/D2H。
5. 用 msprof 采样，查看子图、Kernel、数据搬运与时间线。
6. 每次只改变一个变量并重新编译，防止错误归因。

基线结果：OM 平均约 572 μs；CPU ONNX 约 7171 μs；NPU 加速约 12.5×；MSE 约 `4.70e-7`；余弦相似度 `0.999999`。

## 7. P0：计算图优化的完整闭环

### 7.1 现象与根因

原始 ONNX 有 618 个节点，其中包含大量：

| 算子 | 原始数 | 问题 |
| --- | ---: | --- |
| Shape | 36 | 固定输入下运行时读取维度没有必要 |
| Gather | 36 | 从 Shape 中取维度，随上游一起可常量化 |
| Unsqueeze | 96 | 大量由导出器生成的动态维度拼装 |
| Constant | 226 | 部分折叠后失去消费者，成为死节点 |

这些节点未必计算量大，但会隔开本可相邻的主算子，使 ATC 融合模式匹配失败，并引入调度、中间张量和 GM 读写。

### 7.2 为什么通用 simplifier 不够

通用简化器可能因版本、动态 Shape、算子语义或运行时依赖无法完全推导，甚至发生兼容性崩溃。因此采用受控的手工 Shape 注入、迭代常量折叠和图可达性清理。关键原则不是“看到节点就删”，而是证明其输出在固定输入 Shape 下为常量，或证明它不再影响图输出。

### 7.3 实现方法

1. 固定模型输入 Shape。
2. 为关键中间张量注入 `KNOWN_SHAPES`，弥补 ONNX shape inference 不能完整推导的部分。
3. 对输入全为常量的节点执行计算，以 Constant 替换其输出。
4. 重复最多 30 轮，直到没有新节点可折叠；之所以迭代，是上一轮折叠会让下游节点新满足“全常量输入”。
5. 从 graph outputs 反向遍历依赖，保留所有可达节点，删除不可达节点与无消费者 initializer，即 DCE。
6. 运行 ONNX checker/shape inference，使用 ORT 做数值对比。
7. 必须重新 ATC 编译生成新的 OM，再执行 NPU 精度与性能回归。

反向 DCE 的核心伪代码：

```text
worklist = graph.outputs
while worklist not empty:
    tensor = pop(worklist)
    producer = producer_of(tensor)
    if producer not visited:
        mark producer
        push all producer.inputs
remove all unmarked nodes
```

这种方法比“正向找无用节点”稳健，因为最终输出定义了保留闭包；但若模型有隐式副作用算子，需要额外处理。纯推理 ONNX 图通常是函数式数据流。

### 7.4 两个真实 Bug

**Bug 1：错误的 KNOWN_SHAPES。** 中间骨干曾误写为 `[1,4,4,32]`，正确值是 `[1,32,16,32]`。ATC 仍可能编译通过，但运行时在 Reshape 处失败。教训是“可编译”不等于“语义正确”；必须逐层核对元素总数、Transpose/Reshape 顺序并运行真实 OM。

**Bug 2：加载旧 OM。** 修改 ONNX 后未重新 ATC，验证脚本仍加载旧产物，造成“优化无效”的假象。解决方法是给产物带版本/哈希、清理输出目录、核对编译时间，并在日志打印模型路径和时间戳。

### 7.5 结果与为什么会加速

- 节点 `618→272`，约减少 56%。
- Shape `36→0`，Gather `36→0`，Unsqueeze `96→1`，Constant `226→88`。
- ATC 多个碎片子图收敛为单一主要融合子图。
- 时延 `572→324 μs`；全开融合约 `320 μs`。
- 余弦相似度维持 `0.999999`。

提速来自三部分：减少无效调度、减少中间张量读写、恢复主算子融合。不能把 ONNX 节点减少比例直接等同于时延下降比例。

## 8. P1：GELU 替换为什么失败

### 假设

Erf 表达理论上可避免 Tanh 近似中的部分乘加，可能降低 Vector 工作量。

### 验证

- ORT：余弦 `1.0`，MSE `7.07e-9`，数学替换满足数值要求。
- NPU：原 Tanh 全融合约 `320 μs`；Erf 版本约 `458 μs`。

### 根因

CANN 能识别 Tanh-GELU 特定模式并融合；Erf 图被拆成多个 Kernel。额外启动、同步和中间结果落 GM 的成本，超过理论算术节省。

### 决策

回退 Erf 方案。结论是“算法等价 ≠ 编译图等价 ≠ 硬件性能等价”。优化流程必须观察 ATC 编译结果和设备实测。

## 9. P2：混合精度与量化探索

| 策略 | 时延 | 结论 |
| --- | ---: | --- |
| FP32 P0 全融合 | 320 μs | 对照基线 |
| allow_mix_precision | 318 μs | 基本未发生有效降精度 |
| force_fp16 | 540 μs | 明显退化 |
| 手工全 FP16 | 605 μs | Cast/融合问题更严重 |
| mixlist | 531 μs | 未恢复原融合收益 |
| INT8 标准 QDQ | ATC 失败 | 当前工具链不接受该路径 |

### 为什么 FP16 会变慢

- 输入输出或敏感算子仍需要 FP32，插入 Cast。
- Cast 把原本连续的融合模式切断。
- 小模型、小 Shape 下，转换与 Kernel 调度成本相对更高。
- 主要瓶颈不一定是带宽；Vector 算子在该芯片/版本下也未必具有理想 FP16 加速路径。

### 为什么自动混精度几乎不变

编译器可能为了精度和算子支持保留大量 FP32，或最终图与原路径高度相同。因此必须查看编译日志/图，而不是看到配置参数就认定模型已经混精度。

### INT8 QDQ 为什么失败

标准 ONNX `QuantizeLinear/DequantizeLinear` 并不保证 ATC 当前版本直接接受。昇腾量化通常需要 AMCT 等专用链路、校准数据和平台支持的量化表达；当前 CANN 8.0.RC3 环境下 `customize_dtypes` 也存在问题，AMCT 不可用，所以实验止于编译阶段。

### 如果继续做量化

1. 准备有代表性的 SRS/DMRS 校准集，覆盖幅相、SNR 与工况。
2. 使用匹配 CANN 版本的 AMCT/官方量化流程。
3. 优先对 Conv/MatMul 权重和激活量化，Softmax、归一化、输出等敏感部分保留高精度。
4. 检查量化前后融合图与 Cast/反量化边界。
5. 同时验收时延、吞吐、MSE、余弦和复数相关性。

## 10. FusedAttention 自定义算子

### 10.1 目的

把 `QKᵀ → Scale → Softmax → PV` 从多个 Kernel 融合为一个算子，减少中间分数矩阵写回 GM、Kernel 调度和格式转换。其价值在小 Shape、调度占比高的模型上可能大于单纯减少 MACs。

### 10.2 Ascend 自定义算子的组成

- 算子原型/注册：声明输入输出、属性、dtype 和 Shape 推导。
- Host 侧 Tiling：依据 Shape 和片上容量选择分块，生成 TilingData，设置 blockDim 和 workspace。
- Kernel：在 AI Core 上执行 CopyIn、Compute、CopyOut。
- ONNX 适配插件：把自定义 ONNX 节点映射到昇腾算子。
- 图替换：识别原注意力子图，替换成自定义节点。
- 编译与部署：op build/安装、ATC 编译、OM 推理、精度/性能验证。

### 10.3 基础 Kernel 的逻辑

```text
GM 中读取 Q、K、V
  → 片上计算 QKᵀ
  → 乘 Scale
  → 行方向稳定 Softmax
  → 与 V 相乘
  → 写回输出 O
```

稳定 Softmax 应使用：

```text
m_i = max_j(s_ij)
p_ij = exp(s_ij - m_i) / Σ_j exp(s_ij - m_i)
```

减最大值避免指数溢出；若做分块/在线 Softmax，还要维护每行的局部最大值和归一化和，并正确合并不同块。

### 10.4 Tiling 怎么考虑

Tiling 受 Head 数、序列长度、head_dim、dtype、UB/L1/L0 容量、对齐约束和 Cube tile 限制共同影响。Host 侧应计算每个核负责的 Head/行块、尾块长度、GM 偏移和临时空间。TilingData 必须与 Kernel 解析结构一致，否则会出现越界或错误结果。

### 10.5 深度优化方案 `[尚未实测]`

- 多核按 Head：不同 Head 无数据依赖，天然可分配给不同 AI Core；尾部需处理 Head 数不能整除核数。
- Ping-Pong：用两组片上 Buffer，使第 `n+1` 块搬入与第 `n` 块计算重叠，降低等待。
- GM→L1→L0：大块从 GM 搬到 L1，再按 Cube 需要送入 L0A/L0B，结果在 L0C 累加，减少反复访问 GM。
- 中间结果驻留：让 Score/概率尽量留在片上，避免完整矩阵写回。
- 尾块与对齐：不足 tile 的区域要 mask/pad，确保 Softmax 不把填充值计入归一化。

### 10.6 为什么当前不能报加速数字

基础报告处于“开发完成、待 ATC 编译验证”；当前 `SetBlockDim=1`，单核串行。多核、双缓冲和三级流水属于方案设计。因此只能讲目标、实现思路、风险和验证计划，不能把 `320→200 μs` 或 `95 μs` 等估算当成结果。

## 11. 精度验证与逐算子调试

### 11.1 forward_cvsa.py 端到端流程

1. 初始化 ACL、加载 OM。
2. 预分配 Device 输入输出 Buffer，避免每轮重复分配干扰计时。
3. H2D 拷贝输入。
4. 预热并多轮执行 ACL 推理，记录稳定时延。
5. D2H 获取输出。
6. 将实部/虚部恢复成复数信道矩阵。
7. 对业务约定维度归一化，计算复数相关性；同时计算 MSE/余弦等指标。
8. 汇总样本均值和低分样本，常用业务门限为平均相关性不低于 0.99。

### 11.2 三类指标的区别

```text
MSE = mean((x-y)²)
cos = (x·y) / (||x|| ||y||)
complex corr = |Σ H_ref·conj(H_pred)| / √(Σ|H_ref|² Σ|H_pred|²)
```

- MSE 对绝对数值误差敏感，受量纲和幅值影响。
- 余弦关注方向/形状，整体倍乘时仍可能很高。
- 复数相关性同时考虑复信号的幅相结构，更贴近信道估计业务，但也不能替代所有绝对误差检查。
- 实际验收应多指标并用，并看最差样本，而不只看均值。

### 11.3 单算子 dump 的格式陷阱

昇腾内部 Conv 输出可能是 Fractal/5D 私有格式。若直接按逻辑 NCHW/ND 解释字节，相关性会很低，但这不一定是计算错误。排查顺序：核对 descriptor、真实 storage shape、dtype 和 format；执行正确 TransData/反排布；再比较下游节点和端到端输出。若端到端正确、单点异常，优先怀疑格式解析和 dump 对齐。

## 12. 性能分析方法论

### 12.1 理论计算和实测为何有差距

约 48.9M MACs 的理论估计只覆盖理想计算吞吐；实测还包含 Kernel 启动、数据搬运、格式转换、小 Shape 利用率、同步和编译器生成质量。该模型 Cube 计算并不一定是唯一瓶颈，Vector、MTE 与调度常会主导。

### 12.2 Roofline 思维

用算术强度 `MACs / bytes` 判断更偏计算受限还是带宽受限。算术强度低时应优先减少搬运、提高复用和融合；算术强度高时再关注 Cube/Vector 利用率。但实际还要结合 Kernel 粒度和小矩阵利用率。

### 12.3 为什么节点少不必然更快

节点数只是线索：一个大 MatMul 可能比几十个 Shape 节点耗时更多；反之，很多零碎小节点会带来显著调度和 GM 成本。必须比较最终 ATC 图、Kernel 时间线和端侧实测。

### 12.4 优化优先级

1. 先保证正确性和可复现基线。
2. 优先做低风险图清理和融合恢复。
3. 再做算法等价改写与精度策略实验。
4. 通用编译器无法解决时，再投入自定义算子。
5. 每层优化都保留回退版本和对照数据。

## 13. 生产化设计与风险

- 模型与 OM 应绑定 SoC、CANN、Shape、精度策略和校验哈希。
- 启动时检查输入输出数量、Shape、dtype 和 Buffer 字节数。
- 使用内存池和预分配减少抖动；异步 Stream 要明确依赖与同步点。
- 超时、ACL 错误、NaN/Inf、相关性异常应有监控和降级策略。
- 可保留传统信道估计或旧 OM 作为回退路径。
- 版本发布需同时回归性能分布、业务精度、压力和长稳，而非只测单样本均值。
- 10RB/20RB 频域长度不同，即使权重共享，也要验证不同 OM/动态档位的 Shape 和 Tiling。

## 14. 典型技术权衡

| 选择 | 收益 | 代价/风险 |
| --- | --- | --- |
| 静态 Shape | 更强的编译期推导、融合与内存规划 | 灵活性下降，多配置需多 OM/档位 |
| 图级优化 | 风险低、收益可验证 | 受导出图和编译器规则限制 |
| FP16/INT8 | 理论带宽/吞吐收益 | Cast、精度、算子支持和量化工具链风险 |
| 自定义算子 | 控制融合、搬运和并行 | 开发维护成本高，跨版本适配复杂 |
| 多 Stream | 可重叠任务、提高吞吐 | 单帧时延未必下降，依赖和 Buffer 更复杂 |
| 大 Batch | 提高吞吐和利用率 | 增加等待和单帧时延，不一定适合 L1 |

## 15. 1 分钟项目介绍

> 我在华为实习主要做 5G 基站 L1 AI 信道估计模型的昇腾部署优化。目标模型是 4 层 Transformer，部署在 Ascend 310P3，输入输出是固定的 `(1,4,32,32,1)`。我先打通 ONNX 到 OM、ACL 推理和精度对比，并用 Profiling 建立 572 微秒基线。分析后发现导出图包含大量动态 Shape 推导节点，它们计算量不大，但切断了 ATC 的融合。我通过静态 Shape 注入、最多 30 轮常量折叠和从输出反向 DCE，把节点从 618 降到 272，使多个碎片子图收敛，时延降到 324 微秒，全开融合为 320 微秒，下降 44.1%，余弦相似度保持 0.999999。之后我还评估了 GELU 改写和 FP16/INT8，但都因融合或工具链问题没有采用；FusedAttention 做到了基础算子工程和深度优化设计，尚未完成端到端实测。

## 16. 3 分钟项目介绍

> 项目属于 BESA_AI 的 SPF 信道估计模块，输入是 L1 的 SRS/DMRS 相关特征，模型经过注意力和 FFN 增强后输出复数信道估计。我的职责是部署侧优化，不涉及重新训练。首先我梳理了 4 层 Transformer 的算子和 Shape，完成 ONNX→ATC→OM、Python ACL 推理、CPU/NPU 数值对比，并固定测试环境建立 572 微秒基线。
>
> Profiling 和图分析显示，原始 ONNX 有 618 个节点，其中 Shape、Gather、Unsqueeze 和 Constant 占比很高。因为输入 Shape 实际固定，这些运行时 Shape 链没有业务价值，却让 Conv、LayerNorm、Add 等融合模式无法连续匹配。通用简化工具不稳定，我做了受控简化器：先注入已知中间 Shape，再迭代常量折叠，最后从输出反向做 DCE，并对每版模型重新执行 checker、ORT 对比、ATC 编译和 OM 回归。最终节点降到 272，ATC 主要子图由十多个碎片收敛为一个，时延降到 324 微秒，全开融合为 320 微秒，余弦相似度仍为 0.999999。
>
> 后续我没有只挑成功结果。我尝试把 Tanh-GELU 改为 Erf，ORT 精度完全通过，但 NPU 反而从 320 退化到 458 微秒，原因是破坏了 CANN 专属融合。FP16/INT8 也受到 Cast、Vector 路径和量化工具链限制，没有收益，所以都回退。最后完成了基础 FusedAttention 的 Host Tiling、Kernel 和 ONNX 替换工程，并设计多核 Head、Ping-Pong 和片上流水；这部分还没完成 OM 实测，我会明确作为原型和方案讲。最大的收获是端侧优化必须围绕“最终编译图、真实硬件实测和业务精度”三者闭环，不能只看理论 MACs。

## 17. 面试回答框架

遇到任何技术追问，按以下顺序回答：

> 现象/目标 → 约束 → 假设 → 实现 → 验证 → 结果 → 权衡/下一步

例如“为什么做常量折叠”：固定 Shape 使动态推导可常量化；迭代折叠让下游继续变常量；DCE 删除失去消费者的节点；重新 ATC 后融合恢复；最终用 572→320 μs 和 cos 0.999999 同时证明性能收益与正确性。
