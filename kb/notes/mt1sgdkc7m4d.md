# 八、设计模式

# 01 手写单例模式

饿汉式单例和懒汉式单例是两种常见的单例模式实现方式，它们的应用场景有所不同。

饿汉式单例是指在类加载的时候就已经创建好了单例对象，因此不存在线程安全问题，可以直接使用。适用于单例对象较小且在系统运行期间必然会被多次调用的情况。例如，日志记录器、配置文件管理器等。

懒汉式单例是指单例对象在第一次被使用时才创建，因此需要进行线程安全考虑。适用于单例对象较大且不一定每次都会被调用的情况。例如，数据库连接池、网络连接池等。

需要注意的是，在多线程环境下，懒汉式单例可能会出现线程安全问题，需要采取相应的措施进行保护，比如使用 synchronized 或 Lock 等机制来保证线程安全。而饿汉式单例由于在类加载的时候就创建了实例，不存在线程安全问题，因此更加简单易用。但是由于实例对象在系统启动时就会创建，可能会增加系统的启动时间，也会占用一定的内存空间，因此需要根据实际情况选择合适的实现方式。

**追问 1 懒汉式**

延迟加载  当函数被首次访问才加载

```
#include<iostream>
using namespace std;

class SingleTon{
public:
    static SingleTon* getIntance() {
        if (instance == nullptr) {
            instance = new SingleTon;
        }
        return instance;
    }
private:
    SingleTon() {
        cout << "SingleTon" << endl;
    }
    static SingleTon* instance;
};

SingleTon* SingleTon::instance = nullptr;

int main() {
    SingleTon* t1 = SingleTon::getIntance();
    SingleTon* t2 = SingleTon::getIntance();

    system("pause");
    return 0;
}
```

# 02 观察者模式

观察者模式（Observer Pattern）是一种常见的设计模式，用于实现对象之间的发布‑订阅关系。在观察者模式中，当一个对象的状态发生改变时，所有依赖于它的对象将自动得到通知并更新。这种模式提供了一种简洁的方式，用于解耦发布者和订阅者之间的耦合关系。

以下是观察者模式的几个角色：

1. **主题（Subject）**：也称为可观察对象或发布者，负责维护一组观察者，并在状态发生变化时通知观察者。
2. **观察者（Observer）**：订阅主题的对象，在主题状态发生变化时接收通知并进行相应的更新操作。
3. **具体主题（Concrete Subject）**：是主题的具体实现，维护观察者对象列表，并在状态变化时通知观察者。
4. **具体观察者（Concrete Observer）**：是观察者的具体实现，定义了在接收到通知时所采取的具体行为。

观察者模式的工作流程如下：

1. 主题对象维护一个观察者列表，并提供方法用于添加、删除和通知观察者。
2. 观察者对象订阅感兴趣的主题，并提供一个更新方法，用于接收主题的通知，并根据需要进行相应的处理。
3. 当主题的状态发生变化时，它会依次通知所有订阅的观察者对象。
4. 每个观察者在接收到通知后会执行对应的更新操作。

观察者模式的优点包括：

- 解耦性：主题和观察者之间的关系被解耦，使得它们可以进行修改和扩展，而不会影响彼此。
- 扩展性：可以方便地添加或删除观察者对象，且主题对象不需要知道具体的观察者实现。
- 灵活性：观察者对象可以根据需要自由选择订阅感兴趣的主题。

```
Subject  =>  Observer(Observer1 Observer2 Observer3)
```

> 首先，定义抽象基类 Observer，然后写出它的派生类具体的观察者实现，提供回调的接口
>
> 其次，在 Subject 主题类中添加观察者和对应 msgid 的 map 绑定关系（`unordered_map<int, list<Observer*>> _subMap;`）
>
> 最后，根据不同的 msgid，发送到对应的 Observer

# 03 工厂模式的核心

- **考察场景**

这个问题一般考察你是否理解 **为什么创建对象时不直接 `new`，而要专门抽一层工厂**。

核心是在看你是否明白 **创建和使用解耦** 这件事。

- **底层实现原理**

1. 工厂模式的核心是 **把对象的创建过程封装起来**，调用方只关心 “我要什么对象”，不关心 “这个对象怎么创建出来”。
2. 这样可以把 **对象创建** 和 **对象使用** 解耦，调用方不需要依赖具体类，而是依赖统一接口。
3. 当后续要新增产品类型或修改创建逻辑时，通常只需要改工厂，不需要大面积改业务代码。
4. 所以它的本质就是：**统一入口管理对象创建，降低耦合，方便扩展和替换实现。**

### 代码说明

```
class Product {
public:
    virtual void run() = 0;
};

class ProductA : public Product {
public:
    void run() override {}
};

class ProductB : public Product {
public:
    void run() override {}
};

class Factory {
public:
    static Product* create(int type) {
        if (type == 1) return new ProductA();
        if (type == 2) return new ProductB();
        return nullptr;
    }
};
```

这里的核心不是 `new` 本身，

而是：

- 创建入口统一放到 `Factory`
- 外部只通过工厂拿对象
- 外部不用直接依赖 `ProductA / ProductB`

  - 简单工厂、工厂方法、抽象工厂的区别
  - 工厂模式和策略模式的区别

# 04 建造者模式 Cpp 实现

- **考察场景**

这个问题一般考察你是否理解 当一个对象创建步骤很多、参数很多时，怎么把 “构建过程” 和 “对象本身” 分开。

建造者模式特别适合 **复杂对象分步骤构造** 的场景。

- **底层实现原理**

1. 建造者模式核心是把 **复杂对象的创建过程拆成多个步骤**，比如先配 A，再配 B，再配 C。
2. 调用方不直接关心对象内部怎么组装，而是通过 `Builder` 按步骤构建。
3. 这样可以做到 **同样的构建流程，生成不同表示**，也能避免构造函数参数过多。
4. 一般会有几个角色：`Product`（产品）、`Builder`（抽象建造者）、`ConcreteBuilder`（具体建造者）、`Director`（指挥者，可选）。
5. 所以它的本质就是：**把复杂对象的创建过程独立出来，按步骤构建，降低创建逻辑的复杂度。**

### 代码拆解

1. `Computer` 是最终要构造出来的产品。
2. `ComputerBuilder` 定义构建步骤，比如建 CPU、RAM、Disk。
3. `GamingComputerBuilder` 和 `OfficeComputerBuilder` 实现不同的构建细节。
4. `Director` 负责统一安排构建顺序。
5. 这样调用方只需要告诉 `Director` 用哪个 `Builder`，不需要自己处理每一步细节。

- 延申知识点
  - 建造者模式和工厂模式的区别
  - Director 为什么是可选的

# 05 各种设计模式具体的应用场景

- **考察场景**

这个问题一般考察你是否真的理解 设计模式不是背定义，而是解决什么问题、该在什么场景下用。

核心是在看你能不能把 **模式和实际开发问题对应起来**。

- **底层实现原理**

1. 设计模式本质上是对 **高频设计问题的通用解法总结，不是语法技巧。**
2. 选模式时核心看 3 点：对象怎么创建、对象之间怎么组织、行为怎么扩展。
3. 一般可以分成 **创建型、结构型、行为型**，分别解决 “怎么造对象” “怎么组装对象” “怎么让对象协作”。
4. 真正应用时，不是为了套模式，而是当代码出现 **耦合高、扩展难、分支多、职责混乱** 时，再选合适模式。
5. 所以回答这类题，重点不是全背，而是说清 **每种模式对应的典型问题和落地场景。**

### 代码说明

```
/* 设计模式可先这样分类记忆 */
// 创建型：解决“对象怎么创建”
// 结构型：解决“对象怎么组合”
// 行为型：解决“对象怎么协作”
```

```
/* 一个快速判断思路 */

// 类/模块组合复杂  -> 结构型
// 行为分发/流程变化多 -> 行为型
```

## 创建型模式应用场景

### 单例模式

适合系统里 **某个类只需要一个实例** 的场景。

常见：日志类、配置管理器、线程池、对象池、驱动管理器。

### 工厂模式

适合 **根据条件创建不同对象，不想让业务层到处 `new`** 的场景。

常见：不同协议解析器、不同数据库对象、不同消息处理器创建。

# 设计模式场景

## 创建型模式

- **抽象工厂模式**

  适合 **一整组相关对象一起创建** 的场景。

  常见：跨平台 UI 组件库，一次生成 Windows 风格按钮、文本框、菜单；或不同 SoC 平台的一套外设适配对象。

- **建造者模式**

  适合 **复杂对象按步骤构建，并且参数很多、构造过程固定** 的场景。

  常见：构建 HTTP 请求对象、复杂配置对象、SQL 查询对象、复杂设备初始化参数。

- **原型模式**

  适合 **已有对象复制比重新创建更方便或更高效** 的场景。

  常见：配置模板复制、复杂对象克隆、预初始化对象批量生成。

## 结构型模式应用场景

- **适配器模式**

  适合 **新旧接口不兼容，但又想复用旧代码** 的场景。

  常见：老库接口适配新框架、第三方 SDK 接入统一接口、不同厂商驱动接口统一。

- **桥接模式**

  适合 **抽象和实现两个维度都可能变化** 的场景。

  常见：图形渲染接口和平台实现分离，设备类型和通信方式分离。

- **装饰器模式**

  适合 **在不改原类的前提下动态增强功能** 的场景。

  常见：给流对象加缓存、加加密、加日志；给业务处理链增加统计、鉴权。

- **代理模式**

  适合 **控制对真实对象的访问** 的场景。

  常见：远程代理、虚拟代理、权限控制代理、懒加载代理。

- **外观模式**

  适合 **子系统很复杂，想对外提供一个简单入口** 的场景。

  常见：一键初始化多模块、封装复杂 SDK、封装视频采集启动流程。

- **组合模式**

  适合 **树形结构统一处理** 的场景。

  常见：文件系统目录 / 文件、菜单 / 子菜单、组织架构、UI 组件树。

- **享元模式**

  适合 **大量细粒度对象复用，降低内存开销** 的场景。

  常见：字符对象、棋子对象、地图格子类型、图标缓存。

## 行为型模式应用场景

- **策略模式**

  适合 **同一类问题有多种算法 / 策略可切换** 的场景。

  常见：排序策略、支付方式、压缩算法、调度算法、限流算法。

- **观察者模式**

  适合 **一个对象状态变化，需要通知多个对象** 的场景。

  常见：消息订阅、事件回调、GUI 事件响应、配置热更新。

- **责任链模式**

  适合 **请求需要经过多个处理节点，且谁处理不固定** 的场景。

  常见：审批流、过滤器链、网络协议栈处理链、日志处理链。

- **状态模式**

  适合 **对象行为随状态变化而变化，并且状态分支很多** 的场景。

  常见：订单状态流转、TCP 连接状态、设备工作状态机。

- **命令模式**

  适合 **把请求封装成对象** 的场景。

  常见：遥控器命令、撤销 / 重做、任务队列、线程池任务封装。

- **模板方法模式**

  适合 **流程固定，但某几个步骤可变** 的场景。

  常见：驱动初始化流程、算法框架骨架、测试执行流程。

- **迭代器模式**

  适合 **不暴露容器内部结构，顺序访问元素** 的场景。

  常见：遍历自定义容器、统一访问不同数据结构。

- **中介者模式**

  适合 **多个对象之间相互引用太乱，想集中协调** 的场景。

  常见：聊天系统、UI 控件联动、模块调度中心。

- **备忘录模式**

  适合 **保存对象历史状态，后续恢复** 的场景。

  常见：撤销操作、编辑器历史记录、配置回滚。

- **访问者模式**

  适合 **数据结构稳定，但作用在其上的操作经常增加** 的场景。

  常见：编译器 AST 遍历、文件系统统计、对象结构报表导出。

- **解释器模式**

  适合 **有简单语法规则，需要解释执行** 的场景。

  常见：表达式解析、规则引擎、小型脚本语言。

## 实际开发里最常见的一批

- 单例：配置中心、日志模块
- 工厂：对象创建入口统一
- 策略：不同算法切换
- 观察者：事件通知
- 状态：状态机
- 责任链：过滤器 / 审批流
- 装饰器：功能增强
- 适配器：兼容旧接口
- 模板方法：流程框架复用
