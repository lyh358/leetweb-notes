# 三、OTA

## 01 固件升级的时候 check 了什么（查3项）

固件升级的检查是全流程、分层级的，核心分为「接收阶段」「写入阶段」「启动阶段」三大环节

升级时先=={pink} 验**身份**（谁发的）==、再 =={pink}验**完整性**（包没坏）==、最后 =={pink}验**合法性**（能跑不会砖）==。

## 02 固件升级后如何判断是否成功（判断5项）

| 判断维度 | 验证目标 | 失败风险点 |
| --- | --- | --- |
| =={yellow}**固件完整**性== | 写入 Flash 的固件与源固件完全一致，无字节篡改 / 丢失 | 传输 / 写入过程中比特翻转、Flash 擦写异常 |
| =={yellow}**启动合法**性== | 新固件能正常启动，适配当前硬件 / 芯片，无启动卡死、硬 Fault | 跨型号刷写、固件段地址越界、指令集不兼容 |
| =={yellow}**版本一致**性== | 新固件版本号符合预期（≥旧版本），无降级 / 重复升级 | 版本号校验遗漏、标记写入错误 |
| =={yellow}**功能可用**性== | 核心外设 / 业务功能正常，无初始化失败、功能缺失 | 固件逻辑 BUG、外设驱动不匹配 |
| =={yellow}**运行稳定**性== | 长时间运行无崩溃、无异常重启、关键指标（如通信、控制）正常 | 隐性 BUG（如内存泄露、时序错误） |

## 03 固件升级只做长度校验的话会有问题吗，如果让你设计个完善的方案的话，比如这种固件的检查可以用哪些方式检查

**=={yellow}完善的固件检查==**=={yellow}需覆盖「==**=={yellow}完整性、合法性、安全性、兼容性==**=={yellow}」四大维度==，以下是各维度的核心检查方式及适用场景：

| 检查维度 | 核心方式 | 原理 | 优势 |
| --- | --- | --- | --- |
| =={pink}完整性校验== | **CRC32/CRC64** | 对固件全量数据计算循环冗余校验值，与固件附带的 CRC 值比对 | 计算快、资源占用低（裸机 / 低性能 MCU） |
|  | **MD5/SHA‑1** | 哈希算法生成 128/160 位唯一摘要，比对固件附带的哈希值 | 抗碰撞性优于 CRC，可检测任意字节篡改 |
|  | **SHA‑256** | 生成 256 位摘要，抗破解性远高于 MD5/SHA‑1 | 安全性高，符合国密 / 国际安全标准 |
| =={pink}合法性校验== | **魔数**（Magic Number） | =={yellow}固件头部固定字节==（如 0x53544D33，对应 "STM3"），标识固件有效性 | 快速过滤非目标固件 |
|  | **芯片 ID / 硬件版本校验** | =={yellow}固件中写入适配的芯片型号==（如 0x407）、硬件版本（V2.1），与 MCU 读取值比对 | 防止跨型号 / 跨硬件版本刷写 |
|  | **固件版本校验** | =={yellow}固件头部写入版本号==（如 V1.2.3），确保升级后版本≥当前版本 | 防止降级刷写、重复刷旧固件 |
|  | **分区标识校验** | 校验=={yellow}固件适配的 Flash 分区==（如 A 区 / 运行区、B 区 / 升级区） | 防止固件写入错误分区导致启动失败 |
| =={pink}安全性校验== | **非对称加密签名**（RSA/ECC） | 固件哈希值用私钥签名，MCU 用公钥验签，确认固件来源合法 | 防篡改 + 防伪造，无法伪造合法固件 |
|  | **国密算法**（SM2/SM3） | 国产加密算法，替代 RSA/SHA，符合国内安全合规要求 | 适配国内政策，抗破解性强 |
| =={pink}兼容性校验== | **功能配置校验** | 固件中写入=={yellow}支持的外设 / 功能==（如支持 CAN、不支持 4G），=={yellow}与 MCU 配置比对== | 防止固件功能与硬件不匹配 |
|  | **段校验**（代码 / 数据段） | 校验=={yellow}固件各段（如.text/.data）的地址、长度是否在 Flash 合法范围内== |  |

## 04 升级重启时，如果还有数据正在处理怎么办？

1. **双固件分区设计（主流 OTA 方案）**
将=={yellow}{pink} Flash== 分为=={yellow}「===={yellow}运行分区（A 区=={yellow}=={yellow}）===={yellow}」==和=={green}「升级分区（B 区）」==：

- OTA 时先将=={pink}新固件写入 B 区，不影响 A 区==当前运行的业务；
- 新固件=={pink}校验通过后，仅切换分区标记==，=={pink}重启后从 B 区启动==；
- =={green}重启前 A 区的业务数据可暂存到「共享备份区」==，B 区启动后直接读取恢复。

1. **双 MCU 架构（高实时性场景）**
用两个 MCU 分工：

- =={yellow}MCU1：负责核心**业务数据处理**、**外设控制**=={yellow}（=={pink}无 OTA 功能，永不重启==）；
- =={yellow}MCU2：负责 ==**=={yellow}OTA 升级、通信交互==**，=={pink}升级重启时仅 MCU2 重启==，=={pink}MCU1 继续处理数据==，=={pink}两者通过 SPI/I2C 共享数据==。

## 05 如何判断 flash 哪个扇区的使用率是最小的

STM32 不同系列（如 F1/F4/F7/H7）的 Flash 扇区划分差异较大，需先确定芯片的扇区地址范围和大小：

| 系列 | 扇区特征 |
| --- | --- |
| STM32F103 | 小容量 / 中容量：前 4 个扇区 1KB，第 5 扇区 16KB，后续扇区 32KB；大容量：扇区大小统一 2KB |
| STM32F407 | 扇区 0~~3：16KB，扇区 4：64KB，扇区 5~~11：128KB（共 12 个扇区） |
| STM32H743 | 扇区大小可配置，默认通常为 128KB/256KB（需参考芯片手册） |

=={green}使用率 = 已使用字节数 / 扇区总字节数==

=={yellow}核心是看扇区内**有效数据占总容量的比例**==

空闲率 = 1‑使用率（空闲率最大 → 使用率最小）

统计「已使用字节数」的两种场景（按需选择）：

**场景 1：Flash 存储自定义数据（如参数、日志）**

假设你在 Flash 中按「有效数据标记 + 数据内容」的格式存储数据，需遍历扇区，统计**有效数据的字节数**。

**场景 2：检测扇区是否为擦除态（全 0xFF）**

Flash 擦除后所有字节为 0xFF，若某地址不是 0xFF，视为「已使用」。此方法适用于无自定义数据格式的通用场景。

## 06 OTA 升级过程中 断电 如何处理

- **考察场景**
考察嵌入式 OTA 升级可靠性设计，重点是升级中断电后设备不能变砖，必须能回滚或继续启动旧版本。
- **底层实现原理**

1. OTA =={pink}不能==直接=={pink}覆盖==当前=={pink}正在运行的固件==，否则写到一半断电，启动区固件损坏，设备可能无法启动。
2. 常见做法是=={pink}双分区设计==，也叫 A/B 分区：当前=={yellow}运行 A== 分区，新固件下=={yellow}载到 B==分区，=={green}校验成功==后再=={green}切换启动标志==。
3. =={pink}Bootloader== 是关键，它负责=={green}上电后判断===={pink}启动哪个固件分区==，而不是应用程序自己决定。
4. =={yellow}新固件写入完成后==，=={yellow}需要做== CRC、Hash、签名=={yellow}校验==，确认镜像完整且可信，=={yellow}再更新 OTA 状态。==
5. =={pink}切换到新固件后==不能马上认为升级成功，=={pink}新固件需要正常启动并主动上报确认==，=={pink}Bootloader 才把它标记为稳定版本==。
6. =={green}如果升级过程中断电，Bootloader 根据状态机判断：旧固件仍然有效就继续启动旧版本；新固件未完成就丢弃或继续下载。==
7. 如果=={green}新固件启动失败==、看门狗复位、没有确认成功，=={green}Bootloader 应该回滚到旧固件==。

**典型状态机**

```sql
1  IDLE：正常运行旧固件
2  DOWNLOADING：正在下载新固件
3  DOWNLOADED：新固件下载完成
4  VERIFY_OK：校验通过
5  PENDING_TEST：准备试运行新固件
6  CONFIRMED：新固件确认成功
7  ROLLBACK：新固件失败，回滚旧版本
```

**Flash 分区示例**

```css
1  Bootloader 区：
2  负责启动选择、校验、回滚
3
4  App A 区：
5  当前稳定固件
```

### 1. Bootloader 如何设计 A/B 分区？

1. **=={pink}分区规划（5分区）==**
=={yellow}Flash 划分为：==**=={yellow}App A（运行区）==**=={yellow}、==**=={yellow}App B（备份升级区）==**=={yellow}、==**=={yellow}Bootloader区==**=={yellow}、==**=={yellow}OTA元数据区==**=={yellow}、==**=={yellow}参数区==**。=={green}A/B 两个 App 分区大小完全一致==。
2. **=={pink}元数据保存OTA状态==**
=={yellow}元数据分区记录：==**=={yellow}当前有效启动分区==**=={yellow}、==**=={yellow}升级状态==**=={yellow}、==**=={yellow}校验信息==**=={yellow}、==**=={yellow}是否需要回滚==**=={yellow}。==应用层 OTA 把新固件下载到非运行的分区（比如当前跑 A，则写到 B 分区）。
3. **=={pink}Bootloader 启动逻辑==**

- **判断启动分区**：=={yellow}上电读取 OTA 元数据==，判断应该=={green}启动 A 还是 B== 分区。
- **完整性校验**：=={green}加载待启动 App 镜像==，做完整性校验。
- **尝试启动新固件/回滚**：如果标记为`PENDING_TEST`=={green}（待测试新固件）：尝试启动新分区==；如果=={green}多次启动失败，自动设置==`ROLLBACK`=={green}，切回旧分区==。
- **更新OTA状态**：设备=={green}应用层运行正常==后，=={green}主动设置==`CONFIRMED`=={green}确认新固件有效，取消回滚逻辑。==
. **=={pink}回滚机制==**
      =={yellow}新固件启动崩溃、校验失败，Bootloader 放弃该分区，切换到老的可用 App 分区运行。==

### 2. OTA 镜像 CRC、Hash、签名校验

1. **CRC 校验**：
检测传输过程中偶然比特错误。对固件镜像计算 CRC，下载完后本地重新计算 CRC 和包内的 CRC 对比；只能检查意外损坏，**不能防篡改**。
2. **Hash（SHA256 等）**：
计算固件完整哈希摘要，判断固件有没有被改动。比 CRC 抗篡改能力更强；但是如果攻击者替换固件同时替换哈希值，校验会被绕过。
3. **数字签名校验（安全核心）**

- 服务器端：用私钥对固件 Hash 值做签名，OTA 包带上固件 + 签名。
- 设备端内置**公钥**，不保存私钥。
- 设备：计算固件 Hash，使用内置公钥验证签名合法性。
- 作用：防止固件被恶意篡改、伪造升级包；即使网络被劫持，非法固件无法通过签名校验。

> 一般工程组合流程：下载完成 → CRC 快速校验 → 计算固件 Hash → 验证数字签名，全部通过才允许进入试运行状态。

**流程文字梳理**

1. **IDLE**：设备运行 A 分区旧固件，处于空闲状态。云端下发升级任务，进入`DOWNLOADING`。
2. **DOWNLOADING**：把新固件下载到未使用的 B 分区 Flash。下载结束切换到`DOWNLOADED`。
3. **DOWNLOADED**：固件已经完整写入 B 分区，执行校验流程：CRC 完整性校验 → SHA 哈希 → 数字签名校验。校验成功进入`VERIFY_OK`；校验失败直接丢弃固件，回到 IDLE。
4. **VERIFY_OK**：校验全部合法。修改 OTA 元数据，标记状态为`PENDING_TEST`，设备重启。
5. PENDING_TEST
：上电后 Bootloader 读取元数据，尝试启动 B 分区的新固件：

- ✅ 分支：新固件启动成功，业务应用运行正常，应用层主动写元数据标记`CONFIRMED`，A/B 分区角色交换，回到 IDLE，升级完成。
- ❌ 分支：新固件反复崩溃、启动失败，Bootloader 识别异常，标记`ROLLBACK`，放弃 B 分区，切回 A 分区旧固件，回到 IDLE，完成回滚。

**关键要点**

1. `PENDING_TEST`是风险窗口期：新固件还没有被确认，一旦异常就必须回滚。
2. **CONFIRMED 确认动作由应用程序完成，不是 Bootloader**：Bootloader 只负责检测启动是否成功，业务逻辑是否正常由上层应用判断。
3. ROLLBACK 之后，B 分区里的坏固件不会立刻擦除，下次 OTA 下载的时候会被覆盖。
