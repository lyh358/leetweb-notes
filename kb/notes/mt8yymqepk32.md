## 1) PyTorch 动态图与静态图的区别

## 动态图是什么？

PyTorch 默认是**动态图**，也叫 eager execution。

意思是：==**代码执行到哪，计算图就临时构建到哪**==。

所以动态图的特点是：

- 写法像普通 Python，调试方便；
- ==**可以用 `if`、`for`、动态 shape、变长序列**==；
- ==**模型结构可以随输入变化**==；
- ==适合训练==和科研实验；
- 但==**部署优化不方便**==，因为图不是提前固定的。

动态图**运行时才知道走哪个分支**。

## 静态图是什么？

静态图是指：==**模型计算流程在运行前就已经确定下来**==。

也就是说，**先把模型变成一张固定的计算图**：

```
Input -> Conv -> ReLU -> MatMul -> Softmax -> Output
```

然后**芯片编译器可以提前分析整张图**。

静态图的特点是：

- **计算流程固定**；
- ==**适合部署和编译优化**==；
- 可以做==**算子融合、内存复用、常量折叠**==；
- 更容易在 NPU、DSP、AI 加速器上运行；
- 但对**动态控制流、动态 shape、变长输入支持较差**。



## 2) ONNX 的作用、opset 是什么

## ONNX 是什么？

ONNX，全称 **Open Neural Network Exchange**，是一种**模型中间表示格式**。

你可以把它理解成深度学习模型部署里的“通用交换格式”。

**==芯片厂商不可能为每种框架单独适配所有细节，所以通常会走一个中间格式：==**

```
PyTorch -> ONNX -> 芯片编译器 -> 硬件可执行模型
```

在你项目里就是：

```
PyTorch(.pth) -> ONNX -> OM
```

OM 是昇腾 Ascend 平台的离线模型格式，通常由 ATC 编译生成。

### ==ONNX 模型本质上是一张计算图==，里面包括：

- **输入张量信息；**
- **输出张量信息；**
- **节点，也就是算子；**
- 每个算子的类型，比如 Conv、MatMul、Relu、LSTM；
- **权重参数；**
- shape、数据类型等元信息。

## opset 是什么？

opset 是 **operator set version**，也就是 ==ONNX 算子集版本==。

## 为什么 opset 很重要？

因为芯片编译器不一定支持所有 opset。

比如某个 NPU 编译器可能支持：

```
opset 11、12、13
```

但不支持 opset 17 里的某些新算子。



## 3) 算子、计算图、图优化是什么

### 算子是什么？

**==算子就是深度学习模型里的一个基本计算单元。==**

常见算子有：

```
Conv
MatMul
Add
Relu
Sigmoid
Softmax
BatchNorm
LayerNorm
LSTM
Reshape
Transpose
```

### 计算图是什么？

**==计算图就是把模型里的计算过程表示成一张有向图。==**

**==节点是算子，边是张量。==**

### ==图优化是什么？==

**图优化就是编译器在不改变模型输出结果**，或者尽量不改变结果的前提下，**把计算图变得更适合硬件执行。**

目标通常是：

- **减少计算量；**
- **减少访存；**
- 减少中间张量；
- 提高并行度；
- 降低延迟；
- 降低功耗。



## 4) ==常见图优化==

## 4.1 ==算子融合==

**==算子融合就是把多个连续的小算子合成一个大算子。==**

比如：

```
Conv -> BatchNorm -> ReLU
```

可以融合成：

```
ConvBNReLU
```

为什么能加速？

因为原来每个算子都要：

```
从内存读输入 -> 计算 -> 把输出写回内存
```

三个算子就要多次读写中间结果。

融合后可以：

```
读一次输入 -> 连续完成 Conv/BN/ReLU -> 写一次输出
```

==**最大收益是减少访存。**==

**在 AI 芯片上，访存经常比计算更慢、更耗能**，所以算子融合非常重要。

------

## 4.2 ==常量折叠==

常量折叠就是：如果某些计算只依赖常量，那就提前算好，不要运行时再算。

比如：

```
y = x + (2 * 3)
```

编译器可以提前变成：

```
y = x + 6
```

在神经网络里，比如有些 shape 计算、固定参数计算，都可以提前完成。

## 4.3  ==内存复用==

模型推理时会产生很多中间张量。

比如：

```
Tensor A -> Tensor B -> Tensor C -> Tensor D
```

如果 Tensor A 后面不再使用，它占用的内存就可以给 Tensor C 或 Tensor D 复用。

内存复用的目标是减少峰值内存占用。

这对边缘设备和 NPU 很重要，因为片上内存通常很有限。

---

# 5. 量化：FP32、FP16、INT8、PTQ、QAT

## 5.1 FP32

FP32 是 32 位浮点数。

特点：

- 精度高；
- 训练最常用；
- 数值范围大；
- 计算和存储开销较大。

大多数模型训练默认使用 FP32。

---

## 5.2 FP16

FP16 是 16 位浮点数。

相比 FP32：

- 存储减半；
- 带宽压力减小；
- 计算速度通常更快；
- 精度略低；
- 可能出现溢出、下溢、数值不稳定。

GPU 和 NPU 上常用 FP16 加速推理和训练。

---

## 5.3 INT8

INT8 是 8 位整数。

相比 FP32：

- 模型体积约变成 1/4；
- 访存压力明显降低；
- ==推理速度可能大幅提升；
- 功耗更低；
- 但精度损失更明显。

INT8 量化通常需要把浮点数映射到整数。

## 5.4 为什么量化能加速？

因为：

- INT8 数据更小，读写更快；
- INT8 计算单元吞吐更高；
- cache / 片上内存能放更多数据；
- 带宽瓶颈缓解；
- 功耗降低。

但是代价是精度损失。

------

## 5.5 PTQ 是什么？

PTQ 是 Post-Training Quantization，训练后量化。

流程是：

```
已经训练好的 FP32 模型 -> 用少量校准数据统计激活范围 -> 转成 INT8 模型
```

优点：

- 不需要重新训练；
- 部署成本低；
- 快速。

缺点：

- 精度可能下降；
- 对敏感模型不友好；
- LSTM、Transformer、检测模型有时量化难度更高。

------

## 5.6 QAT 是什么？

QAT 是 Quantization-Aware Training，量化感知训练。

流程是：

```
训练过程中模拟量化误差 -> 让模型适应 INT8 误差 -> 导出量化模型
```

优点：

- 精度通常比 PTQ 更好；
- 适合对精度敏感的模型。

缺点：

- 需要重新训练；
- 工程成本更高；
- 训练流程更复杂。

------

## 面试回答模板

你可以说：

> **FP32 精度最高，常用于训练，但计算和存储开销大**。**FP16 用 16 位浮点表示，可以降低带宽和存储压力，在 GPU/NPU 上常用于加速推理。INT8 用 8 位整数表示，速度和功耗优势更明显**，但需要 scale 和 zero point 把浮点映射到整数，可能带来精度损失。PTQ 是训练后量化，不需要重新训练，部署简单但精度可能下降；QAT 是在训练阶段模拟量化误差，让模型提前适应低精度计算，精度通常更好但成本更高。

---



# 6. kernel 调优：访存、tiling、向量化、并行度、数据布局

这里的 kernel 不是 Linux kernel，而是指运行在硬件上的**计算内核**。

比如：

```
Conv kernel
MatMul kernel
LayerNorm kernel
Softmax kernel
```

kernel 调优就是让这些底层算子在目标硬件上跑得更快。

------

## 6.1 访存优化

很多 AI 计算不是算不动，而是“数据搬不动”。

例如矩阵乘法：

```
C = A x B
```

如果每次计算都从外部 DRAM 读 A 和 B，会非常慢。

所以优化目标是：

- 尽量复用数据；
- 减少 DRAM 访问；
- 多用 cache / shared memory / 片上 SRAM；
- 连续访问内存；
- 避免随机访存。

一句话：

> 算得快不如搬得少。

------

## 6.2 tiling

tiling 也叫分块。

大矩阵一次放不进片上内存，所以把它切成小块。

比如：

```
大矩阵 A、B
切成 A_tile、B_tile
每次搬一块到片上内存
计算局部结果
最后合并
```

这样可以提高数据复用。

矩阵乘法中 tiling 非常重要。

没有 tiling：

```
数据频繁从 DRAM 读写
```

有 tiling：

```
一个 tile 搬进片上内存后，重复使用多次
```

------

## 6.3 向量化

向量化就是一条指令处理多个数据。

普通标量计算：

```
一次加一个数
```

向量化计算：

```
一次加 4 个、8 个、16 个数
```

比如 SIMD：

```
a[0:8] + b[0:8]
```

可以一次性完成多个元素相加。

在 CPU 上是 SIMD，在 GPU/NPU 上也有类似的向量/矩阵计算单元。

------

## 6.4 并行度

并行度就是让更多计算单元同时工作。

包括：

- 多线程并行；
- 多核并行；
- 多 block / 多 warp；
- 多计算单元并行；
- pipeline 并行；
- batch 并行。

但是并行不是越多越好。

太多并行可能导致：

- 内存带宽不够；
- 同步开销变大；
- 资源竞争；
- occupancy 下降；
- cache miss 增多。

所以 kernel 调优要平衡计算资源和访存资源。

------

## 6.5 数据布局

数据布局直接影响访存连续性和硬件利用率。

比如卷积输入常见格式：

```
NCHW
NHWC
```

有些硬件喜欢 channel 连续，有些硬件喜欢宽高连续，还有些 NPU 会把 channel 分块。

如果布局不合适，可能导致：

- 访存不连续；
- cache 利用率低；
- 需要额外 transpose；
- 计算单元吃不满。

所以部署时经常会做 layout transform。

------

## 面试回答模板

你可以说：

> **kernel 调优的核心是让算子更匹配硬件执行特性。**常见方向包括**访存优化、tiling、向量化、并行度设计和数据布局优化**。访存优化是为了减少外部内存访问，tiling 是把大矩阵或大张量切成能放进片上内存的小块以提高数据复用，向量化是用一条指令处理多个元素，并行度优化是让多个计算单元同时工作，数据布局优化则是让张量排布更适合硬件连续访问和并行计算。

---

# 7. NPU / GPU / CPU 执行模型差异

## 7.1 CPU

CPU 是通用处理器。

特点：

- 控制能力强；
- 单线程性能强；
- 分支、循环、复杂逻辑处理好；
- cache 层级复杂；
- 适合操作系统、调度、控制流、串行任务；
- 但大规模矩阵计算吞吐不如 GPU/NPU。

CPU 像“全能型工程师”，什么都能干，但做大规模重复计算不一定最高效。

------

## 7.2 GPU

GPU 是高度并行处理器。

特点：

- 有大量计算核心；
- 适合大规模数据并行；
- 对矩阵乘法、卷积、图形计算非常强；
- 依赖高并行度隐藏访存延迟；
- 对分支发散不友好；
- 编程模型常见 CUDA / OpenCL。

GPU 像“很多工人同时干相似的活”。

适合：

```
大 batch
大矩阵乘法
卷积
Transformer
图形渲染
```

------

## 7.3 NPU

NPU 是神经网络专用加速器。

特点：

- 面向深度学习算子设计；
- 对 Conv、MatMul、GEMM、Attention 等有专用优化；
- 通常有片上 SRAM；
- 常配合专用编译器；
- 对支持的算子很快；
- 对不支持的动态控制流、特殊算子比较麻烦。

NPU 像“专用流水线工厂”。

只要模型结构符合它支持的模式，效率很高；但如果出现不支持算子或动态结构，就需要改图、替换算子、固定 shape 或回退 CPU。

------

## 三者对比

| 项目            | CPU      | GPU           | NPU                           |
| --------------- | -------- | ------------- | ----------------------------- |
| 定位            | 通用计算 | 通用并行计算  | AI 专用加速                   |
| 控制流          | 强       | 一般          | 较弱                          |
| 并行能力        | 中等     | 很强          | 很强                          |
| 灵活性          | 最强     | 较强          | 相对弱                        |
| AI 推理能效     | 一般     | 较好          | 通常最好                      |
| 动态 shape 支持 | 好       | 较好          | 通常较弱                      |
| 编译依赖        | 低       | 中            | 高                            |
| 不支持算子处理  | 软件实现 | 自定义 kernel | 可能需要图改写或 CPU fallback |

------

## 面试回答模板

你可以说：

> CPU 是通用处理器，控制流和复杂逻辑能力强，适合系统调度和串行任务；GPU 通过大量核心实现数据并行，适合大规模矩阵和张量计算；NPU 是面向神经网络的专用加速器，通常对 Conv、MatMul 等常见 AI 算子有专门硬件和编译优化，能效高，但灵活性比 CPU/GPU 弱，对动态 shape、复杂控制流和不支持算子更敏感。因此模型部署到 NPU 时，需要更多关注静态图、算子支持、shape 固定和编译器优化。

# 8. 为什么 LSTM 这类动态序列模型在静态编译平台上更难部署

这是你项目里最容易被追问的地方。

## 8.1 ==LSTM 本身有时间步循环==

LSTM 不是简单的一层输入到输出。

它有时间序列递推：

```
t=1: 输入 x1，状态 h0, c0 -> 输出 h1, c1
t=2: 输入 x2，状态 h1, c1 -> 输出 h2, c2
t=3: 输入 x3，状态 h2, c2 -> 输出 h3, c3
...
```

也就是说，==**当前时间步依赖上一个时间步的 hidden state 和 cell state。**==

这会带来两个问题：

1. **有循环依赖；**
2. ==**序列长度可能变化。**==

------

## 8.2 静态编译平台喜欢固定 shape

NPU 编译器通常希望提前知道：

```
输入 shape 是多少
输出 shape 是多少
中间张量多大
每个算子执行多少次
内存怎么分配
```

但 LSTM 常见输入是：

```
(batch_size, sequence_length, input_size)
```

其中 `sequence_length` 可能变化。

比如：

```
样本 A：长度 20
样本 B：长度 50
样本 C：长度 100
```

动态图框架可以运行时决定循环多少次。

但静态编译器会问：

> 你到底循环多少次？我需要提前分配内存、生成执行计划。

这就是矛盾。

------

## 8.3 LSTM 的 hidden state 传递也麻烦

LSTM 需要维护状态：

```
h_t, c_t
```

在 PyTorch 中，这些状态可以自然地在 Python 逻辑里传递。

但是在静态图中，如果模型被编译成固定 OM 模型，执行过程可能是：

```
输入固定张量 -> 执行静态图 -> 输出固定张量
```

如果你想让上一次推理的 hidden state 传给下一次推理，就需要显式设计输入输出接口。

例如：

```
输入：x_t, h_{t-1}, c_{t-1}
输出：y_t, h_t, c_t
```

否则静态模型内部不会像动态图一样灵活维护状态。

------

## 8.4 LSTM 算子本身可能不完全支持

有些 NPU 编译器对 Conv、MatMul、Relu 支持非常成熟。

但对 LSTM、GRU、动态 RNN 这类算子支持可能有限，尤其是：

- 动态 sequence length；
- bidirectional LSTM；
- variable batch；
- packed sequence；
- 非标准激活函数；
- 自定义循环；
- 不同 opset 下的 LSTM 表达差异。

如果 ONNX 里的 LSTM 算子不被目标平台完全支持，编译就可能失败。

------

## 8.5 常见解决办法

### 方法一：固定输入长度

比如统一设定：

```
sequence_length = 20
```

所有输入都 pad 或截断到固定长度。

优点：

- 编译器容易处理；
- 内存可以提前规划；
- 图结构固定。

缺点：

- 太短会丢信息；
- 太长会增加无效计算；
- 对真实变长数据不够灵活。

你项目中“固定输入维度”就是这个思路。

------

### 方法二：滑动窗口

对时序数据使用固定窗口。

比如：

```
[x1, x2, ..., x20] -> 预测 y21
[x2, x3, ..., x21] -> 预测 y22
[x3, x4, ..., x22] -> 预测 y23
```

这样每次输入都是固定 shape：

```
window_size = 20
```

既能适配静态图，又能处理长序列。

你的电池寿命预测项目就可以这么讲。

------

### 方法三：把 LSTM 拆成基础算子

如果平台不支持 LSTM 大算子，可以把它拆成：

```
MatMul
Add
Sigmoid
Tanh
Mul
```

LSTM 内部公式大致是：

```
i_t = sigmoid(W_i x_t + U_i h_{t-1} + b_i)
f_t = sigmoid(W_f x_t + U_f h_{t-1} + b_f)
o_t = sigmoid(W_o x_t + U_o h_{t-1} + b_o)
g_t = tanh(W_g x_t + U_g h_{t-1} + b_g)

c_t = f_t * c_{t-1} + i_t * g_t
h_t = o_t * tanh(c_t)
```

拆成基础算子后，兼容性可能更好，但图会变复杂，性能也不一定最优。

------

### 方法四：使用更适合部署的模型

有时候可以把 LSTM 换成：

- 1D CNN；
- TCN；
- GRU；
- Transformer encoder；
- MLP + 特征窗口；
- 状态空间模型。

但是否能换要看任务需求和精度。

> LSTM 在静态编译平台上难部署，主要是因为它具有时间步循环和 hidden state 递推，序列长度可能是动态的，而 NPU 这类静态编译平台通常需要提前确定输入输出 shape、循环次数和中间张量内存。动态图框架可以在运行时根据输入长度动态构建计算，而静态编译器更倾向于固定 shape 和固定执行路径。另外，LSTM 算子在不同 opset 和不同硬件编译器上的支持程度也可能不同。因此部署时通常需要固定 sequence length、使用 padding 或滑动窗口，把 hidden state 显式作为输入输出，或者把 LSTM 拆成 MatMul、Add、Sigmoid、Tanh 等基础算子来提高兼容性。
