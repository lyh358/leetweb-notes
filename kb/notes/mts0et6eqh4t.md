# 为什么端侧推理 batch_size 大多 = 1

> batch_size=1：每次只处理**1 个样本**（1 张图、1 帧、1 条语音），也叫单帧推理。
> 服务器推理会用大 batch（8/16/32），端侧（手机、车载 SOC、MCU、边缘盒子）几乎普遍 `batch_size=1`。

## 1. 业务场景天然就是单请求

端侧是**流式、实时、事件驱动**：

- 车载感知：摄像头一帧一帧源源不断过来，**每一帧独立处理**，来一帧跑一次推理；不会攒 16 帧凑齐一批再算，攒帧会带来巨大延迟。
- 手机 AI：拍照、实时人像分割、扫码，每次就 1 张输入。
- 语音：逐帧音频流。

> 如果增大 batch，就要**缓存多个输入等待凑批** → 引入排队延迟，实时场景不能接受。
> 服务器不一样：一堆用户请求源源不断，可以攒一批一起算，牺牲延迟换吞吐量。

## 2. 端侧核心指标是**延迟 (latency)**，不是吞吐量 (throughput)

- 服务器：看重**每秒处理多少样本（吞吐量）**，大 batch 可以充分利用 GPU 算力，摊薄算子启动开销，提升 QPS。
- 端侧实时业务：看重**单帧耗时**，要求低时延，比如车载感知要求 < 30ms 一帧。
`batch_size=1` 得到的就是**单样本延迟**，这是系统的硬约束。

> 端侧不关心 “一秒最多能跑多少张图”，关心 “来一张多久出结果”。

## 3. 硬件资源限制

端侧 NPU / 算力：

- 内存（SRAM/DRAM）很小；batch 越大，输入 feature map、中间张量占用内存**近似线性上涨**。
- batch=4，中间张量内存基本翻 4 倍，极易触发内存超限、频繁 DDR 搬运，反而变慢，甚至跑不起来。
车载 SOC、手机 NPU 片上 SRAM 非常宝贵，大 batch 压力巨大。

## 4. 模型 & 算子优化是面向 batch‑1 做的

端侧工具链（TFLite、ONNX Runtime、SNPE、TensorRT‑LLM、车载 SOC 工具链）：

- 量化、算子融合、NPU 硬件指令调度，大量优化针对 `batch=1`。
- 很多端侧算子对动态 batch 支持弱；有些硬件 NPU 甚至**不支持 batch>1**，导出模型时必须固定 batch=1。

> 很多部署要求：ONNX 模型导出 `batch_size=1`（静态 shape），方便 NPU 做编译优化。动态 batch 会损失性能。

## 5. 少数例外：端侧什么时候 batch>1？

1. 非实时离线任务：本地批量处理相册图片，不在乎延迟，可以开 batch。
2. 多任务共享推理：很少见，需要业务允许攒数据。
3. LLM 端侧推理：这里 batch 是并发请求数；本地一般也是 batch=1（单用户对话）；边缘网关多用户才会 batch>1。

## 6. 容易踩的坑

拿服务器训练 / 大 batch 测速结果评估端侧性能，会严重高估：

> 服务器 batch=16 跑出来每张图平均耗时，**不能代表端侧真实单帧性能**。
> 端侧必须固定 batch_size=1 测 latency 才是真实业务表现。
