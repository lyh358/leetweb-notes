# 四、嵌入式AI部署

## =={pink}01 ONNX 底层如何实现？==

**考察场景**

考察 ONNX 的模型表示、计算图结构和推理运行流程，重点是 ONNX 本身是中间表示，不是具体推理引擎。

**底层实现原理**

1. ONNX 的 **=={yellow}本质==**=={yellow}是一套==**=={yellow}开放的模型中间表示规范==****，****=={pink}底层==**=={pink}通常使用 ==**=={pink}Protobuf 序列化定义===={pink}的 ===={pink}模型结构==**=={pink}、==**=={pink}计算图==**=={pink}和==**=={pink}权重==**
2. 一个 **=={yellow}ONNX 模型==**=={yellow}主要由 ==`ModelProto`=={yellow}、==`GraphProto`=={yellow}、==`NodeProto`=={yellow}、==`TensorProto`=={yellow} ==**=={yellow}4部分===={yellow}组成==**：

- `ModelProto`保存整个**=={pink}模型==**=={pink}及==**=={pink}版本信息==。**
- `GraphProto` 表示**=={pink}节点之间的数据依赖==**=={pink}（==**=={pink}图结构==**=={pink}）==。
- `NodeProto` 表示**=={pink}算子==**。
- `TensorProto` 表示**=={pink}权重==**=={pink}或==**=={pink}常量==**。

1. **=={yellow}ONNX 计算图==**=={yellow}通常是==**=={yellow}有向无环图==**=={yellow}，==**=={yellow}节点==****=={yellow}表示==**`Conv`**=={yellow}、==**`Add`**=={yellow}、==**`Relu`=={yellow}等==**=={yellow}标准算子==**=={yellow}，==**=={yellow}边==**=={yellow}表示==**=={yellow}Tensor 数据流==**=={yellow}。==
2. `opset`=={pink} 表示==**=={pink}算子规范版本==**=={pink}。==同一个算子在不同 opset 下，输入形式和语义可能不同，部署端必须支持模型使用的 opset
3. **推理引擎加载 ONNX 后**，会完成**模型解析、合法性检查**、**形状推导、常量折叠、算子融合和内存规划**。
4. **运行时**会把每个**节点映射到具体 kernel**，=={yellow}或者把一段**子图交给 CPU、GPU、NPU 等**Execution Provider**执行**；不支持的节点可能回退到 CPU
5. **ONNX 只定义 “算子语义是什么”**，不规定卷积必须使用 GEMM、Winograd 还是直接卷积，**具体实现**由 **CANN**、TensorRT、**ONNX Runtime**、NCNN、MNN **等后端决定**。


## 02 量化后精度衰减如何处理？

**考察场景**

考察 INT8 量化误差的来源和定位方法，重点是校准数据、量化粒度、敏感层分析以及 QAT。

**底层实现原理**

1. 量化精度下降的本质是浮点数被映射到有限整数范围，产生截断、舍入和饱和误差：

```css
浮点值 x
    ↓ 除以 scale
    ↓ 取整并加 zero_point
    ↓
INT8 数值 q
```

1. 首先确认不是前后处理问题。量化模型必须与浮点模型使用相同的归一化、颜色通道、输入尺寸、数据布局和后处理参数。
2. 校准数据必须覆盖真实业务分布。样本太少、类别不平衡或缺少极端场景，会导致激活范围估计不准确。
3. 权重通常优先使用 `per‑channel` 量化，每个输出通道使用独立 scale，尤其能够降低卷积不同通道数值范围差异带来的误差。
4. 对误差敏感的首层、末层、Softmax、LayerNorm、检测头或小目标分支，可以保留 FP16/FP32，只量化主要卷积和矩阵乘法。
5. 通过逐层对比浮点模型和量化模型的权重、激活输出，找到第一个误差明显放大的节点，而不是直接猜测问题算子。ONNX Runtime 提供了量化调试接口支持权重和激活匹配
6. PTQ 无法达到精度要求时，使用 QAT，让模型在训练阶段模拟量化误差，权重会主动适应整数表示。

**示意图说明**

```markdown
量化后精度下降
    ↓
前处理和后处理是否一致？
    ↓
校准数据是否覆盖真实分布？
    ↓
逐层比较 FP32 与 INT8 激活
    ↓
找到第一个误差明显节点
    ↓
┌──────────────┬──────────────┐
│修改校准方法    │  敏感层保持浮点│
│per‑channel   │  修改算子结构  │
└──────────────┴──────────────┘
    ↓
仍无法满足精度
    ↓
执行 QAT
```

> 排查时不要只比较单个输出值，应同时比较任务指标：

```css
1  分类：Top‑1 / Top‑5
2  检测：mAP / Recall / 小目标 AP
3  分割：mIoU / Dice
4  关键点：OKS / PCK
```

## 03 如何优化模型在嵌入式设备上的推理速度？

**考察场景**

考察端侧部署的系统优化能力，重点是模型、计算图、推理框架、硬件和数据流水线需要联合优化。

**底层实现原理**

1. 优化前必须先做 profiling，区分耗时发生在预处理、模型推理、后处理、内存拷贝还是线程等待，不能只看模型 FLOPs。
2. 模型层面优先减少计算量和访存量，包括降低输入分辨率、减小通道数、减少检测候选框、采用轻量化 backbone 和蒸馏模型。
3. 精度层面可以使用 FP16、BF16、INT8 或混合精度，但前提是目标 CPU、GPU 或 NPU 对该精度有高效硬件指令支持。
4. 图层面应执行常量折叠、无效节点删除、Conv‑BN 融合、算子融合和静态 shape 固化。融合能够减少 kernel 启动和中间 Tensor 的内存读写
5. 必须检查算子是否全部落到加速器。如果一个算子不被 NPU 支持，可能造成：

```undefined
NPU → CPU → NPU
```

这种跨设备拷贝有时比计算本身更慢。ONNX Runtime 也是根据后端能力进行子图划分和回退

1. 内存层面要减少反复申请释放、数据格式转换和 CPU/GPU 拷贝，尽量复用 Tensor、使用内存池或零拷贝接口。
2. CPU 推理需要合理设置线程数、大小核亲和性和数据布局。线程越多不一定越快，过多线程可能造成 Cache 抖动和调度开销。
3. 嵌入式设备还要关注温度和频率。短时间 benchmark 很快，但持续运行后可能因为 CPU/GPU 降频导致实际帧率下降。

**示意图说明**

```markdown
摄像头输入
    ↓
颜色转换 / Resize / Normalize
    ↓
模型推理
    ↓
Decode / NMS / 跟踪
    ↓
显示或业务处理

优化顺序：
先测量各阶段耗时
    ↓
找到真正瓶颈
    ↓
模型压缩 + 图优化
    ↓
选择正确硬件后端
    ↓
减少拷贝和格式转换
    ↓
调整线程、频率和流水线
```

**代码说明**

```undefined

2	首次推理时间
3	预热后平均延迟
```

## 04 为什么部署需要做模型压缩？

**考察场景**

考察训练环境和端侧环境的差异，重点是模型压缩不仅为了减小文件，还为了降低计算、访存、功耗和启动时间。

**底层实现原理**

1. 嵌入式设备的 Flash、RAM 和显存有限，原始训练模型可能无法完整加载，或者加载后没有足够内存保存中间 Tensor。
2. 推理性能经常受内存带宽限制，而不是单纯受算力限制。权重越小，从 DDR 读取的数据越少，Cache 命中率通常越高。
3. 量化可以同时降低模型大小、内存流量和整数运算成本，例如 FP32 转 INT8 后，单个权重存储空间理论上减少到四分之一。
4. 剪枝、蒸馏和轻量化网络能够减少真实计算量，但只有结构化剪枝或后端支持的稀疏格式，才容易转化为实际加速。
5. 模型越大，加载、解密、反序列化和设备初始化时间越长，影响嵌入式设备的启动速度和首次推理延迟。
6. 较少的计算和访存意味着更低的功耗和发热，可以降低持续运行时的降频风险。
7. 模型压缩需要在精度、延迟、吞吐、功耗和开发成本之间取舍，模型文件变小不等于推理一定变快。

**示意图说明**

```markdown
原始模型
├─ 权重大
├─ 计算量大
├─ 中间 Tensor 大
└─ 算子复杂
    ↓
模型压缩
├─ 量化
├─ 剪枝
├─ 蒸馏
├─ 低秩分解
└─ 轻量化结构
    ↓
Flash 占用下降
RAM 占用下降
内存带宽下降
推理延迟下降
功耗和温度下降
```

**需要特别区分：**

```undefined
ZIP 压缩：
只减少模型存储和传输大小，运行前仍要解压

FP16/INT8 量化：
同时影响存储、内存流量和计算路径

非结构化剪枝：
文件可能变小，但硬件不支持稀疏计算时未必加速

结构化剪枝：
减少整个通道或卷积核，更容易获得真实加速
```

## 05 为什么深度学习模型部署需要转换成 ONNX? ONNX 在部署链路中起什么作用？

**考察场景**

考察训练框架与推理框架的解耦，重点是 ONNX 是部署链路中的通用中间表示，而不是最终硬件执行格式。

**底层实现原理**

1. PyTorch 模型包含 Python 对象、动态图语义和训练相关状态，嵌入式运行环境通常不适合直接携带完整 PyTorch。
2. ONNX 把模型转换成标准计算图、标准算子、权重和 Tensor 描述，使模型不再强依赖原训练框架
3. ONNX 在部署链路中主要承担中间表示作用：

```markdown
PyTorch → ONNX → TensorRT
               → ONNX Runtime
               → OpenVINO
               → 芯片厂商 NPU 工具链
```

1. 部署工具可以在 ONNX 图上执行形状推导、常量折叠、算子融合、量化和子图划分。
2. ONNX 统一了算子语义，但不保证所有后端都支持全部算子。遇到不支持的算子，仍然需要改模型、写插件或执行 CPU fallback。
3. ONNX 不是唯一部署路径。例如 NCNN 当前也支持通过 PNNX 从 PyTorch 或 ONNX 转换，具体选择取决于目标推理框架和模型结构
4. 因此更准确的说法是：**很多部署链路需要 ONNX，但并不是所有模型部署都必须经过 ONNX。**

**示意图说明**

```markdown
训练阶段
    PyTorch Model
        ↓
    ONNX 中间表示
        ↓
图检查 / 图优化 / 量化 / 转换
    ↙        ↓        ↘
TensorRT   NCNN     NPU Compiler
    ↓        ↓           ↓
CUDA GPU  ARM/Vulkan    NPU
```

**ONNX 解决的是：**

```undefined
1	训练框架与部署框架解耦
2	算子和数据类型标准化
3	模型结构可视化和检查
4	为后端编译器提供统一输入
```

**ONNX 不直接解决的是：**

```undefined
1	目标硬件 kernel 性能
2	不支持算子的实现
3	具体内存调度
4	量化后的精度保证
5	平台驱动和运行时兼容
```

## 06 PyTorch 模型转换 ONNX 时常见失败原因有哪些？如何解决？

**考察场景**

考察 PyTorch 动态模型到静态计算图的转换限制，重点是算子支持、控制流、动态 shape 和版本兼容性。

**底层实现原理**

1. **存在不支持的 PyTorch 算子。**
导出器找不到对应 ONNX 算子时会失败，可以替换为标准算子、分解算子或注册自定义转换。PyTorch 提供了扩展 ONNX 导出器算子支持的机制
2. **forward 中包含普通 Python 控制流。**
依赖 Tensor 值的 `if`、`for`、`while` 可能被固定成示例输入路径，或者无法导出，需要重写为 Tensor 运算或可导出的控制流形式
3. **动态 shape 描述不完整。**
只用固定尺寸样例导出时，batch、宽高或序列长度可能被固化，部署其他尺寸时失败。
4. **把 Tensor 转换成 Python 数值。**
`tensor.item()`、`int(tensor.shape[0])` 或使用 NumPy 参与 forward，可能切断计算图或把运行时值固化成常量。
5. **opset 与部署后端不匹配。**
opset 太新，部署端可能不支持；opset 太旧，又可能无法表达新算子，应以目标运行时支持范围为准
6. **模型没有切换到推理状态。**
Dropout、BatchNorm 等在训练模式和推理模式下行为不同，导出前通常需要执行 `model.eval()`。
7. **输入类型或结构不稳定。**
字典、嵌套列表、可选输入、自定义对象和不一致 dtype 可能导致导出失败，应尽量整理成明确的 Tensor 输入输出。
8. **自定义算子或后处理无法转换。**
NMS、ROI、Deformable Conv 等算子需要确认目标后端支持情况，必要时将后处理移到 C++ 侧，或者实现后端插件。

> 目前 PyTorch 官方文档将基于 `torch.export` 的 ONNX 导出器作为较新的导出路径，使用时仍需结合当前 PyTorch 版本确认接口。

# 07 ONNX 模型和原始 PyTorch 模型输出不一致，如何定位问题？

## 考察场景

考察模型转换后的正确性验证，重点是先统一输入环境，再通过逐层对比定位第一个发生误差的节点。

## 底层实现原理

1. 首先保证 PyTorch 使用 `eval()` 和 `no_grad()`，关闭 Dropout 的随机行为，并让 BatchNorm 使用保存的运行均值和方差。
2. 两端必须使用完全相同的输入数据，包括 RGB/BGR、NCHW/NHWC、归一化参数、Resize、padding 和 dtype。
3. 不要直接使用 `==` 比较浮点数，应设置合理的绝对误差 `atol` 和相对误差 `rtol`。
4. 如果最终输出不一致，应导出中间节点输出，找到第一个误差明显放大的节点，再检查该算子的属性和输入。
5. 重点检查 `Resize`、`Pad`、`Slice`、`Gather`、`Softmax`、`TopK`、`NMS` 等容易受 opset、坐标模式或轴参数影响的算子。
6. 动态 shape 模型需要检查实际输入尺寸是否落在导出约束内，以及 `Reshape`、`Flatten` 是否错误依赖固定尺寸。
7. 如果 ONNX 在某后端正确，但转到 TensorRT 或 NPU 后错误，应进一步检查低精度计算、算子插件和 CPU/NPU 子图边界。
8. 定位时采用 “二分法” 最快：先比较网络中间位置，再逐步缩小到具体节点，而不是一次导出所有大 Tensor。

PyTorch 和 ONNX Runtime 都提供了用于验证导出模型输出的工具或接口，核心方法仍然是使用相同输入比较输出和中间激活

## 示意图说明

```bash
1 PyTorch 输出 != ONNX 输出
2     ↓
3 检查 eval / no_grad
4     ↓
5 检查前处理和输入 Tensor
6     ↓
7 比较最终输出误差
8     ↓
9 比较中间层 A
10    ├─ 一致 → 问题在 A 之后
11    └─ 不一致 → 问题在 A 之前
12    ↓
13 不断二分
14    ↓
15 定位到具体算子
16    ↓
17 检查属性、opset、shape、精度和后端 kernel
```

## 常见现象：

```css
1 误差从第一层开始：
2 优先检查输入、权重和数据布局
3
4 前面一致，某个 Resize 后突然不一致：
5 检查坐标变换和 align_corners 语义
```

# 08 ONNX 模型转换后有哪些常见优化手段？

## 考察场景

考察计算图优化和硬件适配，重点是图优化、精度转换、静态 shape 和后端编译需要分层处理。

## 底层实现原理

1. 首先运行 ONNX checker 和 shape inference，补全中间 Tensor 的类型和形状，便于后续内存规划和算子融合。形状信息有助于运行时复用 buffer 和提高执行效率
2. 执行常量折叠，把只依赖常量的计算提前完成，例如固定的 `Shape`、`Gather`、`Mul` 和权重变换。
3. 删除无效节点，包括 `Identity`、无用 `Cast`、训练期 `Dropout` 和重复的 `Reshape`。
4. 执行算子融合，例如：

- Conv + BN
- Conv + Add
- Conv + Activation
- MatMul + Add
- Attention
- LayerNorm

ONNX Runtime 将图优化分为基础优化、扩展优化和布局优化

1. 固化输入 shape 可以减少运行时 shape 计算，让后端提前选择 kernel、规划内存和生成优化后的执行计划。
2. 转换为 FP16、INT8 或混合精度，可以减少模型大小和内存带宽，但必须验证目标硬件是否真正支持高效低精度计算
3. 修改数据布局或权重布局，例如 NCHWc、NC4HW4、通道 packing，使数据更符合 SIMD、Tensor Core 或移动 GPU 的访问方式。
4. 将模型离线转换成目标引擎格式，可以减少设备启动时的图优化和编译时间，但生成结果往往与硬件和运行时版本相关。

# 09 什么是 Operator Fusion? 为什么 Conv + BN 可以融合？

## 考察场景

考察图优化的数学基础，重点是算子融合如何减少中间 Tensor、内存访问和 kernel 启动开销。

## 底层实现原理

1. Operator Fusion 的本质是把多个连续算子合并成一个等价算子或一个融合 kernel，保证数学结果基本不变。
2. 融合后不需要把每个算子的结果都写回 DDR，再由下一个算子重新读取，可以减少内存带宽消耗。
3. 对 GPU 而言，融合还可以减少 kernel launch；对 CPU 而言，可以提高 Cache 利用率并减少循环次数。TensorRT 会在构建阶段识别受支持的模式并生成融合 kernel
4. 推理状态下的 BatchNorm 参数是固定常量，因此可以把其缩放和平移操作吸收到卷积权重和 Bias 中。
5. 训练状态下 BN 使用当前 batch 的均值和方差，它们不是固定常量，因此一般不能按照相同方式静态融合。
6. Conv‑BN 融合后，运行时只保留一次卷积，不再单独执行 BN。

# 10 为什么同一个 ONNX 模型转换到 TensorRT、NCNN、MNN 后性能差异很大？

**考察场景**

考察推理框架与硬件后端的实现差异，重点是 ONNX 只统一算子语义，不统一 kernel、内存布局和调度策略。

**底层实现原理**

1. 三种框架面向的主要硬件不同：

- TensorRT 主要针对 NVIDIA GPU。
- NCNN 重点面向移动和嵌入式 ARM CPU、Vulkan GPU。
- MNN 支持 ARM、x86、OpenCL、Vulkan、Metal、CUDA 等多个后端

1. 算子 kernel 实现不同。相同 Conv 可能分别使用 cuDNN、Tensor Core、ARM NEON、Winograd、im2col + GEMM 或手写汇编。
2. 数据布局不同。NCNN 常使用适合向量化的 packed layout，MNN 可能使用 NC4HW4 等内部格式，TensorRT 则根据 tactic 和 GPU 特性选择内部格式。
3. 算子融合能力不同。同一计算图在一个框架中可能融合为单个 kernel，在另一个框架中仍然需要执行多个算子。TensorRT 的构建器会根据支持模式自动执行 layer fusion
4. 低精度支持不同。即使都启用 FP16 或 INT8，不同硬件对低精度指令、数据 packing 和累加精度的支持也不同。
5. 动态 shape 会影响 kernel 选择和内存规划。固定输入尺寸通常能使用更激进的优化，而宽泛的动态范围可能限制融合和 tactic 选择。
6. 不支持算子会造成 fallback 或额外转换。例如部分节点在 GPU 上执行，部分节点回到 CPU，会产生设备同步和内存拷贝。
7. 线程池、内存分配器、workspace、CPU 亲和性、GPU 队列和异步执行策略不同，也会造成明显性能差异。
8. 转换工具质量也会影响结果。转换后可能出现额外的 `Transpose`、`Reshape`、`Cast` 或拆分算子，导致计算量没有变化但访存显著增加。
9. Benchmark 方法必须一致，包括输入尺寸、batch、精度、预热次数、线程数、功耗模式和是否包含前后处理，否则比较结果没有意义。

# 11 TensorRT 从 ONNX 到 Engine 的过程做了哪些优化？

**考察场景**

考察 TensorRT Builder 的模型编译流程，重点是图优化、算子融合、精度选择、Tactic 搜索和显存规划。

**底层实现原理**

1. TensorRT 首先通过 ONNX Parser 解析计算图，将 ONNX 节点、权重、数据类型和 Shape 转换成内部 Network Definition；不支持的算子需要修改模型或实现 Plugin。
2. Builder 会执行常量折叠、无效节点删除和代数化简，例如提前计算只依赖常量的 `Shape`、`Gather`、`Mul` 等节点。
3. TensorRT 会进行算子融合，例如 `Conv + Bias + Activation`、`MatMul + Add`。这样设计是为了减少 Kernel 启动次数和中间 Tensor 的显存读写。
4. Builder 会传播和选择计算精度，包括 FP32、FP16、BF16、INT8 等；实际能否使用低精度取决于 GPU、算子实现以及模型中的精度约束。
5. 同一个算子可能存在多个实现，例如不同的卷积算法、Tensor Core Kernel 和数据布局，这些候选实现通常称为 Tactic。
6. 构建阶段会对候选 Tactic 进行评估，在给定 Shape、精度和 Workspace 条件下选择更合适的实现，所以 Engine 构建时间通常远大于反序列化时间。
7. 动态 Shape 模型需要配置 `min/opt/max` Optimization Profile。范围过宽会增加构建复杂度，也可能使部分只支持固定维度的优化失效。
8. TensorRT 会分析中间 Tensor 的生命周期，让生命周期不重叠的 Buffer 复用同一块显存，降低峰值显存占用。
9. 最终 Engine 保存优化后的网络、Kernel 选择、Tensor 格式和内存规划；Execution Context 则保存一次推理运行所需的动态状态

```undefined

 ↓

 ↓
常量折叠 / 冗余节点删除
 ↓

 ↓
FP32 / FP16 / INT8 精度选择
 ↓
Tactic 搜索与性能评估
 ↓
Tensor 生命周期分析和显存复用
 ↓
序列化 TensorRT Engine
```

## 12 模型转换后如何验证精度和性能是否符合预期？

**考察场景**

考察模型部署验收流程，重点是精度验证和性能验证必须分开，并保证输入、前后处理和测试环境完全一致。

**底层实现原理**

1. 先选择原始 PyTorch FP32 模型作为 Golden Model，后续 ONNX、TensorRT FP16、INT8 模型都与它比较。
2. 两端输入必须完全一致，包括 RGB/BGR、NCHW/NHWC、Resize、Letterbox、归一化、dtype 和数值范围。
3. 先比较原始输出 Tensor，常用最大绝对误差、平均绝对误差、相对误差和余弦相似度。
4. 不能只比较某一个输入样本，应使用覆盖真实场景的数据集，避免模型只在简单样本上表现一致。
5. 最终还要比较任务指标，例如分类 Accuracy、检测 mAP、分割 mIoU。Tensor 数值接近不代表经过 Decode、NMS 后业务指标一定一致。
6. 性能验证要区分纯模型执行时间和端到端时间；端到端时间还包括预处理、数据搬运、后处理和同步。
7. 测试前执行 Warmup，随后统计多次推理的平均延迟以及 P50、P90、P99，并固定 Shape、Batch、线程数、功耗模式和温度状态

## 13 PTQ 和 QAT 的区别是什么？分别适合什么场景？

**考察场景**

考察量化方案选择，重点是 PTQ 不需要重新训练，而 QAT 会在训练阶段模拟量化误差。

**底层实现原理**

1. PTQ 是训练后量化，模型训练完成后再对权重和激活进行低比特转换，不改变原始训练流程。
2. 静态 PTQ 需要使用校准数据统计激活范围；动态 PTQ 则在运行时计算部分激活量化参数，通常更适合特定 CPU 模型。
3. PTQ 的优势是成本低、速度快、不需要重新训练，适合快速部署和原模型量化敏感度较低的场景。
4. QAT 会在训练或微调阶段插入 Fake Quantize，前向过程模拟取整、截断和饱和误差，让权重主动适应量化噪声。
5. QAT 通常能够获得更好的低比特精度，但需要训练代码、代表性数据和额外训练成本。
6. 工程上通常先执行 PTQ；如果精度不满足要求，再尝试敏感层保留浮点、混合精度或 QAT

## 14 INT8 量化的基本流程是什么？

**考察场景**

考察从 FP32 模型到 INT8 模型的完整流程，重点是量化策略、校准、Q/DQ 和后端编译。

**底层实现原理**

1. 首先验证 FP32 模型的正确性，确保 ONNX 输出和原始框架基本一致，否则量化后很难区分是转换问题还是量化问题。
2. 量化前通常执行 Conv‑BN 融合、常量折叠、Shape 推导和冗余节点删除，使计算图更容易被量化工具识别。
3. 确定量化范围，包括只量化权重还是同时量化激活，以及采用对称、非对称、per‑tensor 或 per‑channel。
4. 权重的量化范围可以直接通过模型参数统计；静态激活量化则需要运行校准数据采集激活分布。
5. 根据统计结果计算 Scale 和 Zero Point，将浮点值映射到 INT8 范围。
6. 在 ONNX 中常见的显式量化表示是插入 `QuantizeLinear` 和 `DequantizeLinear`，即 Q/DQ 节点。
7. TensorRT 或 NPU 编译器识别 Q/DQ，将支持的连续子图转换成真正的 INT8 Kernel；不支持的节点可能继续使用 FP16 或 FP32。
8. 最后验证任务精度、逐层误差、INT8 算子覆盖率、推理延迟和内存占用。当前 ONNX Runtime 支持静态量化及多种校准方法；不同 TensorRT 版本的量化接口存在差异，现代部署更常使用显式 Q/DQ 模型

```css
    ↓

    ↓
插入 Q/DQ 节点
    ↓
生成量化 ONNX
    ↓

    ↓

```


## 15 Calibration（校准）的作用是什么？校准数据如何选择？

**考察场景**

考察静态 PTQ 的核心步骤，重点是校准用于统计激活范围，不是重新训练模型。

**底层实现原理**

1. Calibration 的本质是用一批代表性输入运行 FP32 模型，统计各层激活的数值范围或分布。
2. 校准结果用于计算激活 Tensor 的 Scale 和 Zero Point，使有限的 INT8 编码尽可能覆盖真实数据。
3. 量化范围过大时，大量 INT8 编码空间被少数离群值占用，正常值的量化分辨率降低。
4. 量化范围过小时，大量数据会被截断到 -128 或 127，产生明显的饱和误差。
5. 常见校准方法包括 MinMax、Entropy 和 Percentile。MinMax 保留完整范围但容易受离群值影响，Percentile 会裁剪少量极端值。
6. 校准数据应覆盖真实业务分布，包括不同类别、光照、目标大小、背景、摄像头和边界场景，不能只选择容易识别的样本。
7. 校准数据通常不需要标签，但校准集和最终精度测试集最好分开；样本数量没有固定答案，应观察量化参数和精度是否随样本增加趋于稳定

**示意图说明**

```markdown

    ↓
部署端完全相同的预处理
    ↓

    ↓
```

## 16 为什么 INT8 量化会导致精度下降？

**考察场景**

考察量化误差来源，重点是舍入、截断、离群值和逐层误差累积。

**底层实现原理**

1. FP32 数值需要映射到只有 256 个编码的 INT8 空间，连续数值被离散化时必然产生舍入误差。
2. 超出量化范围的数值会被裁剪到边界，产生饱和误差，通常比普通舍入误差更严重。
3. 少量离群值会把 Scale 拉大，使大部分正常值集中在少数几个整数编码中，导致有效精度下降。
4. Per‑tensor 量化让整个 Tensor 共用一个 Scale；如果不同通道的数值范围差异很大，小范围通道会损失更多精度。
5. 每层产生的量化误差会传递到下一层，并可能被卷积、残差加法、激活函数进一步放大。
6. Softmax、LayerNorm、检测框回归、关键点坐标等数值敏感部分，对微小误差更加敏感，通常需要混合精度或 QAT

**示意图说明**

```markdown
FP32 连续数值
    ↓
映射到 INT8 离散网格
    ↓
舍入误差
    + 截断误差
    + 离群值影响
    + 通道范围差异
    + 逐层误差累计
    ↓
任务精度下降
```

**延伸知识点**

为什么轻量模型有时比大模型更难量化

哪些算子通常需要保留 FP16 或 FP32

## 17 如何定位量化后精度下降来自哪些 Layer?

**考察场景**

考察量化调试方法，重点是逐层比较 FP32 和量化模型输出，找到第一个误差明显增大的节点。

**底层实现原理**

1. 保留未经大幅改图的 FP32 模型和对应 Q/DQ 模型，尽量保证节点名称能够对应。
2. 使用完全相同的输入运行 FP32 和 INT8 模型，并导出关键中间节点的输出。
3. 对对应 Tensor 计算最大绝对误差、MAE、MSE、余弦相似度和 SQNR。
4. 重点寻找第一个误差突然变大的节点，而不是只看最终误差最大的节点，因为后面的误差可能只是前面误差的累计。
5. 模型较大时可以采用二分法，先比较网络中间位置，再判断问题位于前半段还是后半段。
6. 对怀疑层单独关闭量化或改成 FP16/FP32，如果任务精度明显恢复，说明该层或其输入是量化敏感点。
7. 如果某层输入已经有明显误差，该层输出误差更大并不代表该层本身有问题，应继续向前追踪。
8. ONNX Runtime 提供浮点模型与量化模型的权重和激活匹配调试接口，可用于采集并比较对应 Tensor

**示意图说明**

```markdown

    ↓                        ↓
FP32 Layer 2 ———— 对比 ———— INT8 Layer 2
    ↓                        ↓
FP32 Layer 3 ———— 对比 ———— INT8 Layer 3
                             ↑
                    第一个误差突增点
```

**优先检查：**

1. 输入量化节点
2. 第一层卷积
3. 检测头或分类输出层
4. LayerNorm / Softmax / Sigmoid
5. 残差 Add
6. 大范围 Concat 后的节点

## 18 一个模型从加载到完成推理，中间经历哪些阶段？

**考察场景**

考察推理 Runtime 的完整生命周期，重点是模型加载、初始化、执行和后处理是不同阶段。

**底层实现原理**

1. 应用先从 Flash、磁盘或内存读取模型文件，并完成 ONNX 解析或 Engine 反序列化。
2. Runtime 检查模型格式、算子版本、输入输出、Shape 和目标硬件兼容性。
3. 原始模型可能在加载阶段执行图优化、子图划分、Kernel 选择或后端编译；预编译 Engine 则已离线完成大部分工作。
4. Runtime 创建执行上下文，加载权重，并申请中间 Tensor、Workspace、命令队列和输入输出 Buffer。
5. 应用对原始数据执行 Decode、Resize、颜色转换、归一化和 Layout 转换。
6. 输入被绑定到 Runtime；如果输入不在目标设备上，还需要执行 CPU 到 GPU/NPU 的映射或拷贝。
7. Runtime 按优化后的执行计划调度 Kernel，处理依赖、异步队列、临时内存复用和异构子图切换。
8. 执行完成后获取输出，进行反量化、Decode、NMS、排序等后处理，再交给业务逻辑。TensorRT Engine 保存优化后的网络与内存策略，Execution Context 保存运行时状态。

**示意图说明**

```markdown
读取模型
    ↓
解析或反序列化
    ↓
图优化 / 后端编译
    ↓
创建执行上下文
    ↓
申请并绑定 Buffer
    ↓
输入预处理
    ↓
CPU → GPU/NPU
    ↓
Kernel 执行
    ↓
GPU/NPU → CPU
    ↓
输出后处理
```

**需要区分：**

```markdown
模型加载时间：
    文件读取、解析、编译、初始化

首次推理时间：
    可能包含延迟初始化、内存分配、Cache 填充

稳定推理时间：
    Warmup 完成后的实际推理延迟
```

## 19 CPU、GPU、NPU 推理有什么区别？为什么 NPU 更适合端侧 AI?

**考察场景**

考察异构计算架构，重点是通用性、并行度、功耗效率和算子支持之间的差异。

**底层实现原理**

1. CPU 是通用处理器，擅长复杂控制流、分支、小算子和前后处理，算子兼容性最好。
2. CPU 的并行计算单元数量有限，大规模卷积和矩阵乘法的吞吐通常不如专用加速器，但小模型和低 Batch 下可能具有较低调度开销。
3. GPU 拥有大量并行计算单元，适合卷积、GEMM、Attention 等规则的大规模并行计算。
4. GPU 的性能依赖并行规模、Kernel 实现和显存带宽，小算子过多或频繁同步时利用率可能较低。
5. NPU 通常包含专用 MAC 阵列、片上 SRAM、低精度计算单元和专用数据流，重点优化神经网络中的卷积和矩阵计算。
6. NPU 通过 Tiling 和片上数据复用，减少权重与激活反复访问外部 DDR，从而降低功耗。
7. NPU 通常针对 INT8、INT16、FP16 等端侧精度进行优化，因此在支持完整的模型上具有较好的性能功耗比。
8. NPU 的主要限制是算子、Shape、Layout 和量化格式受硬件约束；发生 CPU fallback 时，数据搬运和同步可能抵消加速收益。Arm 的端侧 NPU 产品同样以嵌入式推理和能效为主要设计目标。

**示意图说明**

```undefined
CPU
├─通用性强
├─控制流强
└─AI 计算能效相对低

GPU
├─并行计算强
├─模型支持灵活
└─功耗和显存访问较大

NPU
├─专用 MAC 阵列
├─片上 SRAM
├─低精度高能效
└─算子支持受限制
```

**延申知识点**

NPU 的 MAC 阵列和片上 SRAM 如何配合

为什么小模型在 CPU 上有时比 NPU 更快

## 20 为什么模型参数减少后，推理速度不一定提升？

**考察场景**

考察参数量与真实硬件性能的区别，重点是推理延迟还受计算量、激活大小、访存和硬件利用率影响。

**底层实现原理**

1. 参数量主要反映权重存储大小，不等于 FLOPs，也不等于中间激活的数据量。
2. 参数很少的卷积如果输入 Feature Map 很大，仍然可能产生大量计算和内存访问。
3. Depthwise Conv 参数和 FLOPs 较低，但计算密度低、访存比例高，在部分硬件上不一定比普通卷积更高效。
4. 剪枝后通道数如果不能对齐 SIMD 宽度、Tensor Core Tile 或 NPU 通道要求，硬件利用率可能下降。
5. 参数减少后如果引入更多 `Transpose`、`Concat`、`Reshape` 或小算子，会增加 Kernel 启动和中间 Tensor 读写。
6. 当模型存在 CPU fallback 或大规模数据搬运时，整体性能可能由这些部分决定，减少其他层参数几乎没有收益。

**示意图说明**

```markdown
推理延迟
    * 只由参数量决定

推理延迟
    = 计算时间
    + 权重访存
    + 激活访存
    + Kernel 启动
    + Layout 转换
    + 设备同步
    + CPU/GPU/NPU 搬运
```

为什么 Depthwise Conv 在部分硬件上性能较差

## 21 如何判断模型推理瓶颈在计算、内存还是数据搬运？

**考察场景**

考察性能分析能力，重点是结合逐层 Profile、硬件计数器和对照实验定位瓶颈。

**底层实现原理**

1. 先将端到端时间拆成预处理、H2D、模型执行、D2H 和后处理，确认问题是否真的位于模型内部。
2. 计算瓶颈通常表现为卷积或 GEMM 占主要时间，计算单元利用率高，降低 FLOPs 或改用低精度后性能明显提升。
3. 内存瓶颈通常表现为计算单元利用率不高，但 DDR 或显存带宽较高，热点多为大 Feature Map、低计算密度算子。
4. 数据搬运瓶颈表现为 Memcpy、Cache 同步、Layout 转换和设备同步占比高，纯模型执行很快但端到端延迟较大。
5. 可以比较 FP32、FP16 和 INT8：低精度后显著加速，通常说明原来偏计算或带宽瓶颈；变化很小则需要检查调度和搬运。
6. 可以使用 `--noDataTransfers` 或预先将数据放到设备侧，对比是否排除 H2D/D2H 后延迟明显下降。
7. 改变 Batch Size 也能辅助判断：Batch 增大后吞吐显著提高，说明原先计算单元可能没有充分利用。
8. 最终要结合算子级耗时、计算量、输入输出大小和硬件利用率综合判断，不能只依赖单一指标。

**示意图说明**

```markdown
推理速度慢
    ↓
计算单元利用率高？
    ├─ 是 → 计算瓶颈
    └─ 否
        ↓
DDR / 显存带宽高？
        ├─ 是 → 内存瓶颈
        └─ 否
            ↓
Memcpy / Reformat / Sync 占比高？
            ├─ 是 → 数据搬运瓶颈
            └─ 否 → 查小算子、线程调度和 fallback
```

**延申知识点**

什么是算术强度和 Roofline 模型

为什么增加 Batch 通常能提高吞吐

## 22 为什么 CPU 和 NPU 之间的数据拷贝会影响性能？

**考察场景**

考察异构推理的数据路径，重点是拷贝还会附带内存分配、Cache 同步、Layout 转换和执行等待。

**底层实现原理**

1. CPU 和 NPU 可能使用不同的虚拟地址空间、内存分配器或 Buffer 格式，执行前需要重新分配和复制。
2. 图像和中间 Feature Map 数据量较大，复制会占用 DDR 带宽，并与 CPU、GPU、ISP 和 NPU 的正常访存竞争。
3. 即使 CPU 和 NPU 共享物理内存，也可能需要执行 IOMMU 映射、Cache clean/invalidate 和所有权切换。
4. CPU 使用的 NCHW、NHWC 与 NPU 私有通道 Packing 可能不同，边界处还要执行 Reformat 或 Transpose。
5. 为保证 NPU 已完成写入，CPU 读取结果前需要等待 Fence 或同步事件，这会破坏 CPU 和 NPU 的并行流水。
6. 如果模型被切成多个 CPU/NPU 子图，每次切换都会重复产生拷贝、格式转换和同步开销。ONNX Runtime 的 I/O Binding 也是为了避免在每次执行中隐式完成这些设备拷贝。

# 23 什么是 Zero Copy？为什么可以提升推理性能？

**考察场景**

考察端侧多媒体和 AI Pipeline 的内存共享，重点是 Zero Copy 是减少数据复制，不是完全没有同步成本。

**底层实现原理**

1. Zero Copy 的本质是不同模块共享同一块底层 Buffer，只传递句柄、地址描述或 DMA‑BUF fd，而不是复制整块数据。
2. 例如摄像头、ISP、NPU 和显示控制器可以共享 DMA‑BUF，避免每经过一个模块都执行一次 `memcpy()`。
3. 减少复制可以降低 DDR 带宽占用、CPU 使用率、峰值内存和延迟抖动。
4. Zero Copy 不代表零开销，仍可能需要 IOMMU 映射、Cache 同步、Fence 等待和 Buffer 所有权切换。
5. 上下游必须支持兼容的像素格式、Stride、Layout 和内存类型，否则仍然需要颜色转换或数据重排。
6. 真正有效的 Zero Copy 需要从摄像头、预处理、Runtime 到后处理整体设计，只优化某一个接口通常不够。
7. 推理 Runtime 可以通过 I/O Binding 或设备 Tensor 直接绑定设备侧输入输出，避免每次 `Run()` 隐式执行 CPU 与设备之间的复制。

```css
4    ↓ memcpy

6    ↓ memcpy
7  CPU Output Buffer
```

Zero Copy：

```css
3  共享 DMA‑BUF

5    └─ Display 读取
6
7  模块之间传递 Buffer 句柄和 Fence
```

# 24 一个模型部分算子跑 NPU、部分跑 CPU，会有什么影响？

**考察场景**

考察异构子图划分和 CPU fallback，重点是少量不支持算子可能切断整个 NPU 子图。

**底层实现原理**

1. Runtime 会根据 NPU 支持的算子、Shape 和数据类型，把模型划分成 NPU 子图与 CPU 子图。
2. 每次跨越 CPU/NPU 边界都可能产生数据搬运、Cache 同步、Layout 转换和执行同步。
3. 原本连续的算子链被切断后，NPU 无法进行跨边界融合，中间 Tensor 需要重新写回 DDR。
4. 少数 CPU 算子可能成为串行瓶颈，导致 NPU 执行完成后等待 CPU，或者 CPU 执行完成后 NPU 才能继续。
5. 如果 CPU 节点位于模型末尾且 Tensor 很小，例如简单 Decode，影响可能较小；如果节点位于主干网络中间，影响通常更明显。
6. 优化重点不是机械追求 100% NPU 覆盖，而是减少频繁的子图切换，并保证大计算量主干形成连续 NPU 子图。ONNX Runtime 会根据不同 Execution Provider 的能力进行图分区，并由 CPU 执行未分配给加速后端的节点。

# 25 端侧 AI 模型性能评估有哪些核心指标？

**考察场景**

考察模型部署验收标准，重点是不能只看 FPS，还要同时关注精度、延迟、资源、功耗和热稳定性。

**底层实现原理**

1. 任务精度是模型可用性的基础，例如 Accuracy、mAP、mIoU、Recall、PCK。
2. Latency 表示单次输入从开始到获得输出的耗时，通常需要统计平均值以及 P50、P90、P99。
3. Throughput 表示单位时间内处理的样本数量，例如 FPS 或 Samples/s；吞吐高不代表单帧延迟一定低。

```undefined
单次推理能量 = 平均功率 × 单次推理时间
```

1. 长时间持续运行需要监控温度和频率，避免短时间达到性能指标，热稳定后却因降频掉帧。
2. 还应评估模型大小、加载时间、首次推理时间、CPU/GPU/NPU 占用率和端到端业务延迟。准确 Benchmark 必须明确计时范围和测试环境。

# 26 如何准确测量模型推理 Latency？为什么需要 Warmup？

**考察场景**

考察性能测试方法，重点是明确计时边界、处理异步执行，并排除首次初始化和频率变化。

**底层实现原理**

1. 测量前先明确范围，是只测模型 Kernel，还是测包含预处理、拷贝和后处理的端到端延迟。
2. GPU 和 NPU 通常异步执行，推理 API 返回不代表硬件已经完成计算，结束计时前需要等待 Stream、Event 或 Fence。
3. Warmup 可以触发延迟初始化、内存分配、Kernel 加载、Cache 填充和页表建立。
4. Warmup 还可以让 CPU、GPU、NPU 从低功耗状态提升到稳定频率，减少前几次推理的频率波动。
5. 动态 Shape 第一次出现时，Runtime 可能需要重新计算 Shape、选择执行路径或申请 Buffer，因此首次延迟往往更高。
6. Warmup 后应执行足够多次迭代，保存每次延迟，而不是只用总时间除以次数。
7. 最终至少报告平均值、P50、P90、P99 和最大值，实时业务更应关注尾延迟。
8. 测试期间需要固定输入 Shape、Batch、线程数、CPU 亲和性、功耗模式和温度状态。TensorRT 官方性能流程也强调预热、多次测量以及正确区分 GPU 计算和数据传输。

**常见错误：**

```undefined
1  没有等待异步设备完成
2  把 Engine 构建时间算入推理
3  只测试一次并选择最小值
4  Warmup 次数不足
5  测试期间发生温度降频
6  把 Batch 延迟当作单样本延迟
```

**延申知识点**

- 为什么 CUDA Event 比 CPU 时间戳更适合测 GPU Kernel
- P99 Latency 应该如何计算

# 27 模型推理速度慢，如何系统定位性能瓶颈？

**考察场景**

考察完整的性能排查能力，重点是先拆分端到端阶段，再定位到子图、算子和硬件资源。

**底层实现原理**

1. 先建立可复现基线，固定模型、输入、Shape、Batch、精度、线程、Runtime 版本和功耗模式。
2. 将端到端流程拆成采集、预处理、数据搬运、模型执行、后处理和显示，分别记录耗时。
3. 如果模型执行占主要时间，再运行算子级 Profiler，找出 Top 耗时算子，不要平均优化所有节点。
4. 检查编译日志和子图划分，确认是否存在不支持算子、CPU fallback 或频繁 CPU/NPU 切换。
5. 检查是否存在大量 `Transpose`、`Cast`、`Reformat`、Q/DQ 和动态 Shape 相关节点。
6. 对 Top 算子判断是计算瓶颈还是访存瓶颈，再决定减少 FLOPs、减小 Feature Map，还是修改 Layout 和融合方式。
7. 检查输入输出 Buffer 是否反复申请和复制，评估预分配、Buffer 复用、I/O Binding 和 Zero Copy。
8. 观察 CPU 线程调度、中断、上下文切换和大小核分配，避免模型线程和业务线程竞争同一个核心。
9. 长时间运行观察温度、频率和功耗，每次优化后重新验证精度、平均延迟、P99 和峰值内存。TensorRT 官方建议采用 “测量 — 优化 — 重新测量” 的闭环，而不是根据模型结构直接猜测瓶颈。

**示意图说明**

```undefined
1  模型推理慢
2    ↓
3  固定测试环境
4    ↓
5  拆分端到端阶段
6    ↓
7  模型内部是否最慢？
8    ├─否 → 查预处理、拷贝、后处理
9    └─是
10      ↓
11    逐层 Profile
12      ↓
13    检查 fallback / Reformat
14      ↓
15    判断计算 / 访存 / 搬运瓶颈
16      ↓
17    针对性优化
18      ↓
19    重新验证精度和 P99
```

**延申知识点**

- 如何从 Nsight Systems 时间线判断同步瓶颈
- 为什么平均延迟下降后 P99 可能反而升高

# 28 如何优化一个端侧模型的推理速度？

**考察场景**

考察端侧 AI 的综合优化能力，重点是模型、计算图、硬件后端、内存和系统流水线需要联合优化。

**底层实现原理**

1. 优化前先做 Profiling，确认瓶颈位于预处理、数据搬运、模型计算还是后处理。
2. 模型结构层面可以降低输入分辨率、减少通道、使用轻量化 Backbone、结构化剪枝和知识蒸馏。
3. 根据硬件能力选择 FP16、INT8 或混合精度；硬件没有高效低精度 Kernel 时，量化不一定带来加速。
4. 执行常量折叠、Conv‑BN 融合、无效节点删除、算子融合和静态 Shape 固化，减少 Kernel 和中间 Tensor。
5. 替换 NPU 不支持的算子，提高加速器覆盖率，并尽量形成一个连续的大 NPU 子图。
6. 减少 `Transpose`、`Cast`、`Reformat` 和通道 Packing，统一预处理、模型与后端的数据布局。
7. 预分配并复用输入、输出和 Workspace，避免每帧执行 `malloc/free` 或设备内存申请。
8. 使用 I/O Binding、DMA‑BUF 或 Zero Copy，减少 CPU 与 GPU/NPU 之间的数据复制。
9. 使用双 Buffer、环形队列和异步执行，让采集、预处理、推理和后处理形成流水线，而不是串行等待。
10. 调整线程数、CPU 亲和性、中断亲和性和功耗模式，并在热稳定状态下验证平均延迟、P99、内存和精度。

**示意图说明**

```rust
1  端侧推理优化
2  ├─模型结构
3  │   ├─轻量化
4  │   ├─结构化剪枝
5  │   └─知识蒸馏
6  ├─数值精度
7  │   ├─FP16
8  │   ├─INT8
9  │   └─混合精度
10 ├─计算图
11 │   ├─算子融合
12 │   ├─静态 Shape
13 │   └─减少 Reformat
14 ├─硬件覆盖
15 │   ├─减少 CPU fallback
16 │   └─扩大 NPU 子图
17 ├─内存
18 │   ├─Buffer 复用
19 │   └─Zero Copy
20 └─系统
21     ├─异步流水
22     ├─CPU 亲和性
23     └─温度和功耗
```

**典型流水线：**

```undefined

2  时刻 T1：预处理帧 0 | 采集帧 1
```

```css

```

- 为什么端侧模型必须验证热稳定后的 P99 延迟
