1. =={green}雷达内部发生了**什么异常**；==
2. =={green}当前输出的**数据是否仍然可信**；==
3. =={green}售后或整车**怎样读取和定位异常**。==

一条诊断链路通常会包含这些模块（7）：

- **=={yellow}CDD或MCAL==**=={yellow}：提供原始硬件数据；==
- **=={yellow}SWC_DIAG==**=={yellow}：判断数据是否异常；==

- **=={yellow}DCM和UDS==**=={yellow}：输出DTC和冻结帧、响应整车或上位机的诊断请求；==
- **=={yellow}PTC上位机==**=={yellow}：人为制造异常，验证整条诊断链路。==

# PART3——CRC校验功能的具体细节

激光雷达的Flash中不仅存放MCU程序，还保存了**FPGA Bitstream、****各种软硬件模块的参数与配置。**

**Flash数据可能因为各种因素而损坏**，如升级异常、掉电、存储介质异常或数据写入错误。**如果雷达在不知道参数已经损坏的情况下继续运行**，可能导致点云输出不可信。

因此，系统需要在=={yellow}上电阶段通过CRC校验==关键Flash数据的完整性。

## =={pink}四、工站层：产线故障注入与验收闭环==

这个功能的工站层**=={yellow}主要解决一个问题==**：

> =={yellow}CRC属于**上电自检**，产线想**验证**它能否报故障**，必须先写入故障注入配置**，再**让整机重新上电**；但**电源复位会清空RAM**，所以**注入命令必须跨复位保存**。==

| PTC主/子命令 | 功能 |
| --- | --- |
| =={yellow}0x4F== | **写入NVM故障注入配置**（ST模式+期望故障码） |
| =={yellow}0x10== | **整机电源复位**，触发自检重新执行 |
| =={yellow}0xFF== sub 0x1F | **查询DEM确诊故障列表**，校验0x1E01故障 |
| =={yellow}0x4F read== | **读取当前生效注入配置** |

### =={pink}4.2 为什么需要专门适配==

**普通周期诊断**在设备运行时不断执行，因此**工站下发注入命令后，下一周期就能触发故障**。
但CRC属于 `DIAG_PERIOD_ST`上电自检：
如果工站在**系统已经运行后下发注入，CRC自检早已结束，注入不会生效。**
因此必须：

```undefined
先写入注入配置
→ 再执行电源复位
→ 重新上电时读取注入配置
→ CRC自检执行注入分支
```

=={yellow}原平台如果只把注**入状态保存在RAM中**：==

```undefined
PTC写入RAM
→ 电源复位
→ RAM清空
→ 注入配置丢失
→ CRC正常执行
→ 无法产生期望故障
```

=={yellow}这就是工站适配的**核心问题**。==

### =={pink}最终采用的NVM持久化方案==

### =={yellow}把**上电自检注入信息写入NVM**：==PTC 0x4F写入注入配置

> PTC 0x4F写入注入配置
>     ↓
> 解析诊断ID、事件ID和Fail/Pass指令
> ↓
> 在RAM中更新自检注入状态
> ↓
> 通过CDD参数管理接口写入NVM
> ↓
> 执行0x10电源复位
> ↓
> 重新上电后从NVM恢复注入配置
> ↓
> CRC算法读取注入结果

=={yellow}这样即使整个ECU断电重启，注入配置仍然存在。==

工站下发的命令经过以下模块：

**完整验收流程：**

#### =={yellow}1. 写入强制故障配置==

## 先解释PC1300和遥测UDP是什么

=={yellow}PC1300是激光雷达接收链路中的**SPAD接收与信号处理芯片**，主要负责**接收回波光信号并完成部分片上处理**。==

- 芯片**寄存器状态**；
- DSP和**采样通道信息**；
- **FPGA统计数据**；
- **时间戳和序列号**；
- 其他调试状态。

这些数据=={yellow}主要供研发、台架和DV监控上位机使用==，不是对外输出的点云UDP。
