# 项目梳理

项目定位：这是一个基于**昇腾=={yellow}边===={yellow}缘==计算平台**的**锂电池寿命预测系统**

# 项目背景：

## **为什么要做这个**？

锂电池现在广泛应用在**电动车、储能系统、航天**等场景里，但随着**充放电循环**进行，**电池会持续退化**，容量下降后不仅会影响**系统可靠性**，还可能带来**安全风险**。

所以，提前、准确地预测锂电池的剩余寿命，也就是 RUL，对**电池健康管理**和**系统安全预警**都很关键。

## **你这种数据驱动的方法相较于传统的模型驱动的方法好在哪里？**

模型驱动的方法可解释性强但是在复杂工况下落地难度高

## **为什么选 LSTM，而不是传统RNN?**

- LSTM更容易捕捉到长期时序信息的依赖关系
- LSTM的门控机制
  - LSTM通过引入**细胞状态（Cell State）**和**三个门控开关**来控制信息的流动，从而选择性地记忆或遗忘信息。
  - 遗忘门
  - 输入门
  - 更新细胞状态
  - 输出门

因为电池退化本质上是一个**长时序问题**，前面很多循环的信息会影响后面的寿命状态。**普通 RNN 虽然也能建模序列**，但容易出现梯**度消失和梯度爆炸**，难以**稳定捕捉长期依赖**。LSTM 通过**门控机制**能更好地**保留长期时序信息**，所以更适合建模电池长期退化过程。

- 梯度消失：反向传播过程中，前面层的梯度变得非常小，导致参数几乎不更新，模型学不动
- 梯度爆炸：前面层的梯度变得非常大，参数更新幅度太大

## 为什么还要选择在昇腾板端平台部署这个算法？

我之所以要把算法部署到昇腾板端，不是为了单纯证明模型能跑，而是为了把一个 PC 端的离线预测算法，真正变成一个能服务 BMS 的边缘侧可用项目

### 1.从边缘计算场景看，为什么一定要上板端

锂电池寿命预计系统在实际工程中，不可能把数据传回 PC 或云端再分析，而是需要**低功耗、高实时、可嵌入**的推理能力。

如果模型只在 PC 上跑通，那它更多还是一个离线算法；但放到边缘板端以后，它才更接近真实应用场景，因为 =={yellow}BMS 需要的是就地推理、快速响应和可嵌入部署==。

### 2. 为什么是华为昇腾这块板，为什么说它适配这个项目？

第一，这个平台本身就是围绕**推理部署**来设计的。

Ascend310B 的 CANN 架构会在 **ONNX 转 OM 时做=={yellow}算子编译优化==**，=={yellow}提前确定**内存分配、并行策略和算子融合**规则==。这说明这块板子的优势不只是“能运行代码”，而是它对推理执行有专门的编译和优化机制。

第二，它的**工具链和部署链条是完整的**。

- ONNX 作为中间格式，
- ATC (Ascend Tensor Compiler)做模型编译，
- OM 作为昇腾侧执行文件，
- ACL(Ascend Computing Language) 做板端推理程序开发。

总之，选择昇腾这个平台，不仅是因为它**针对推理部署做了优化**，而且还**提供了从模型转换、编译优化到板端推理的一整套工具链**，适合**把算法做成真正可部署的边缘推理应用**。

### ３.从“理论算法”到“可用项目”的角度

因为论文阶段你验证的是：
 **GRA + PCA + LSTM 这个方法在 NASA 数据集上预测有效。**
 但工程上真正有价值的是：
 **这个方法能不能在受限硬件平台上跑起来，而且还能保持可接受的精度和可用性。**

# 算法侧

## 第一层：先讲目标，不要先讲模型

核心是在做锂电池剩余寿命预测。目标是**根据电池充放电过程中的历史数据**，**提前判断它还能稳定工作多久**，从而为后续的健康管理和预警提供依据

- 输出的结果图是两条折线，分别是预测值和实际值
- 横坐标是电池充放电循环次数，纵坐标是电池容量值
- 可以设置一条EOL横线（８０％）代表多少轮循环能到寿命终点

---

## 第二层：算法思路（算法难点）

这个问题的难点在于

- 电池退化是一个**长期、非线性的时序过程**
- 而且原始监测数据里有很多电压、电流、温度等变量（１１维度数据），**不是所有特征都对寿命变化同样敏感**。
- 如果直接把**所有特征都送进模型**，容易带来**冗余和噪声**，尤其在寿命后期会**影响预测精度**。

## 第三层：再讲你的方法，用“先优化输入，再做预测”

### 特征提取

- 先对NASA的数据集进行了特征提取：得到了 11 个退化特征，覆盖充电和放电阶段的关键信息

### 特征筛选和压缩

- 不是所有特征都跟电池寿命变化强相关
- 先用 **GRA （灰色关联度分析）**衡量特征和容量退化的相关性（大于０.７５），保留强相关特征（９个）
- 再用**PCA（主成分分析）**进一步降维：减少冗余，同时尽量保留主要退化信息
  - 是将n维的 数据映射到k维（k小于n）上得到的数据被称为原数据的主成分
- 得到紧凑的健康因子用于模型训练

### 时序建模

- 网络结构是 **输入层 + LSTM 层 + 全连接层 + 输出层**
- **输入**是连续的健康因子序列
- **输出**容量衰减相关的预测值

### 算法测成果：

在算法上形成了完整的 **特征提取—特征优化—时序建模** 流程，并且实验验证表明预测准确率（四组电池数据：９２.８％－９８.５％之间）

## 总体逻辑：

## 第一步：先在 PC 端把算法模型训练好

工程部署的起点不是板子，而是 **PC 端已经训练完成并验证可用的 `.pth` 模型**。

- `.pth` 是 **PyTorch 训练好的模型权重**。

## 第二步：把训练模型转换成板端可接受的格式

### （１）．ｐｔｈ－＞．ｏｎｎｘ

这个阶段本质上还是在**PC 端/PyTorch 环境**完成的。

- ＯＮＮＸ是什么：**通用中间模型格式，用于做中间量转化**，他是一个一个**标准化、跨框架**的“桥梁”

## 主要分为５个步骤：

### １.先在 PC 端重新定义和训练时完全一致的模型类（网络模型）

​	.pth 一般**保存的是权重**，**不是**完整可执行**网络**，所以导出前必须先写出和训练时一致的 nn.Module

### ２.加载 `.pth` 权重

把训练好的 `.pth` 文件通过 `load_state_dict()` 加载到这个模型里。

### ３.切换到推理模式

使用**`model.eval()`**，将网络模型切换为推理模式，因为**导出 ONNX 是推理图，不是训练图**；

也就是说，你要导出的应该是模型以后在板端真正运行时的状态，而不是训练状态。

### ４.构造 dummy input（与．ｐｔｈ格式对应的静态虚拟输入）

​	**这些 `.pth` 的输入维度都是 `1,21,4`**，也就是：

- `batch_size = 1`
- `seq_len = 21`
- `feature_dim = 4`

​	所以导出时要准备一个形状为 **`(1, 21, 4)`** 的虚拟输入

注意：必须是静态格式的输入，因为 **Ascend310B 后续编译**需要**静态 shape 去做内存和算子优化**。

### ５.用 `torch.onnx.export()` 导出

- 核心函数：`torch.onnx.export`
- **使用12 版 ONNX 算子集**opset_version=12
  - 主要是出于部署兼容性考虑，ｏｐｓｅｔ１２工具链兼容、转换更稳定
- **不使用动态维度**
  - Ascend310B 在 **ONNX → OM** 阶段会做静态编译优化
    - 因此 ONNX **不能是动态模型**
    - OM 是固定张量形状、固定执行顺序、固定内存布局的专用执行文件
     所以你在 ONNX 阶段就必须把形状定死。
- 单个模型单独转换，不做批量处理

```python
import torch
import torch.nn as nn

class LSTMNetWithHC(nn.Module):
    def __init__(self, input_size=4, hidden_size=100, num_layers=1, output_size=1):
        super().__init__()
        self.hidden_size = hidden_size
        self.num_layers = num_layers

        self.lstm = nn.LSTM(
            input_size=input_size,
            hidden_size=hidden_size,
            num_layers=num_layers,
            batch_first=True
        )
        self.fc = nn.Linear(hidden_size, output_size)

    def forward(self, x, h0, c0):
        # x:  [1, 21, 4]
        # h0: [1, 1, 100]
        # c0: [1, 1, 100]
        out, (hn, cn) = self.lstm(x, (h0, c0))
        y = self.fc(out[:, -1, :])
        return y, hn, cn

def export_pth_to_onnx_with_hc(pth_path, onnx_path):
    device = torch.device("cpu")

    model = LSTMNetWithHC(
        input_size=4,
        hidden_size=100,
        num_layers=1,
        output_size=1
    ).to(device)

    state = torch.load(pth_path, map_location=device)
    if isinstance(state, dict) and "state_dict" in state:
        model.load_state_dict(state["state_dict"])
    else:
        model.load_state_dict(state)

    model.eval()

    x = torch.randn(1, 21, 4, device=device)
    h0 = torch.zeros(1, 1, 100, device=device)
    c0 = torch.zeros(1, 1, 100, device=device)

    torch.onnx.export(
        model,
        (x, h0, c0),
        onnx_path,
        export_params=True,
        opset_version=12,
        do_constant_folding=True,
        input_names=["x", "h0", "c0"],
        output_names=["y", "hn", "cn"]
        # 不要加 dynamic_axes
    )

    print(f"Export success: {onnx_path}")

if __name__ == "__main__":
    pth_path = "./models/LSTM_net_raw_B0005_with_hc.pth"
    onnx_path = "./models/LSTM_net_raw_B0005_with_hc.onnx"
    export_pth_to_onnx_with_hc(pth_path, onnx_path)
```

### 这个阶段最关键的注意点有四个：

### 1. 为什么一定要“模型类一致”

因为 `.pth` 通常只存参数，不存完整网络语义。
 如果你现在写的 LSTM 层数、hidden size、FC 层和训练时不一致，权重就加载不上，或者能加载但导出的图是错的。

---

### 2. 为什么要 `eval()`

因为导出的是推理图。
 如果模型还处于训练模式，导出的 ONNX 在推理时可能和训练后实际测试行为不一致。文档已明确要求这一点。

---

### 3. 为什么 dummy input 必须是 `(1, 21, 4)`

因为你项目里训练好的模型输入就是这个维度，文档明确写了 **“这几个 `.pth` 的输入维度都是 1,21,4”**。如果你导出时换了输入尺寸，后面 ONNX→OM 编译和板端推理都可能对不上。

---

### 4. 为什么不能设动态维度

这是你项目里最重要的工程约束之一。
 文档明确说明，LSTM 的输入 `[batch_size, seq_len, feature_dim]` 在这里**不能是变量**，因为 Ascend310B 后续编译需要静态 shape 去做内存和算子优化。

## 第三步：用昇腾工具链把 ONNX 编译成 OM

第三步我把**通用格式模型**进一步**编译成昇腾芯片可直接执行的 OM 模型**，这一步相当于**让算法真正适配硬件平台**。

把 ONNX 放到板端环境后，并不能直接执行，还要继续用 **ATC（Ascend Tensor Compiler）** 编译成昇腾专用的 **OM 模型**。

## OM具体有哪些特点

- 第一，**它是面向 Ascend 芯片编译后专用的最终部署模型**
  - 包含**固定的张量形状、固定的算子执行顺序和固定的内存布局**
  - 因此必须由静态形状的 ONNX 转换而成。
- 第二，**它是静态图执行**。
  - **训练时 LSTM 是动态循环**、可以逐步传递 `h/c`；
  - 但转成 OM 后，**循环会被展开成固定步数的计算图**
- 第三，**它对输入 shape 很敏感，必须提前固定**。
  - 因为 Ascend310B 的 CANN 架构会在 ONNX→OM 阶段提前做内存分配、并行策略和算子融合优化，所以如果输入维度是动态的，芯片就无法提前规划。
    - LSTM 输入固定成 `1,21,4`
    - 隐藏状态固定 `h0/c0` 为 `1,1,100`
      - 这里的 `h0/c0` 就是**初始隐藏状态和初始细胞状态**。
      - `h` 是 hidden state，也就是**隐藏状态**，可以理解为当前时刻对外输出的记忆表征
      - `c` 是 cell state，也就是**细胞状态**，可以理解为长期记忆主通道
- 第四，**它更偏部署，不偏训练**。

## 你这个项目里，具体怎么在板端用 ATC 把 ONNX 转成 OM

- **在板端的 Linux 环境里，在 `src` 文件夹下打开终端，用终端命令行执行 `atc`**

```bash
atc --model=./models/LSTM_net_raw_B0005_with_hc.onnx \
    --framework=5 \
    --output=./models/LSTM_net_raw_B0005_with_hc \
    --input_format=ND \
    --input_shape="x:1,21,4;h0:1,1,100;c0:1,1,100" \
    --log=info \
    --soc_version=Ascend310B4 \
    --precision_mode=force_fp32
```

`--model`
 **指定输入的 ONNX 文件路径。**前提是你已经把导出的 ONNX 拖到板子的系统里。文档第一页最后一步就写了“将 onnx 模型拖动到板子的系统内”。

`--framework=5`

**这个模型文件属于哪种框架格式**，这里是 ONNX

`--output`
 **指定输出 OM 文件名和路径**。最终生成的是昇腾可执行的部署模型。

`--soc_version=Ascend310B4`
 **指定目标芯片版本**，要和你实际使用的开发板匹配。你项目平台是 Atlas 200I DK A2，文档中对应配置为 `Ascend310B4`。

`--input_shape`
 **指定静态输入维度**，这是你项目最重要的约束之一。单输入版本是 `input:1,21,4`，带隐藏状态输入版本是 `x:1,21,4;h0:1,1,100;c0:1,1,100`。

`--precision_mode=force_fp32`
 **强制使用 FP32**。文档说明**默认是 FP16**，而你项目选择 FP32，是为了优先保证连续值寿命预测任务的推理精度。简历里也写到你采用了 FP32 精度强制转换来平衡性能与准确率。

`--input_format=ND``--log=info`
 这两个出现在带 `h/c` 输入的命令里，前者用于**输入格式声明**，后者用于**日志级别**。

## 你项目里 ATC 编译这一步有哪些注意事项

### 1=={yellow}ONNX 必须是静态 shape，不能动态==

​	LSTM 的输入 `[batch_size, seq_len, feature_dim]` 不能是变量

### 2）=={yellow}输入名必须和 ONNX 里定义的节点名一致==

如果你的 ONNX 导出时输入名叫 `input`，那 `atc` 里就要写 `input:1,21,4`；
 如果导出时输入名叫 `x, h0, c0`，那就必须写：

```ini
--input_shape="x:1,21,4;h0:1,1,100;c0:1,1,100"
```

### 3）==`soc_version` 必须和板子芯片匹配==

### 4）=={yellow}回归任务优先考虑精度，别默认用 FP16==

你的项目是电池寿命/容量预测，属于连续值回归问题，对数值误差更敏感，所以显式用了 `force_fp32`。

### 5）=={yellow}LSTM 到板端后，不能指望完全保留原始动态隐藏状态传递==

即使你把 `h0/c0` 暴露成输入，OM 模型在昇腾上仍然是静态图执行。文档里说明，它转换后更像一次性处理固定长度序列的黑盒，不能像训练态那样自然把中间 `h/c` 连续传到下一次推理。你最终是通过**滑动窗口**来近似模拟这种记忆效果的。

### 6）窗口长度要和训练时的 `seq_len` 对齐

文档明确说，滑动窗口虽然能适配静态图逻辑，但窗口长度必须和训练时的 `seq_len` 一致，否则预测精度会下降。

### 7）ATC 编译时间和板子性能有关

文档里还提到，这一步所需时间会随着板子性能不同而变化。

- 你的主脚本里 `load_model()` 的逻辑非常清晰：

  - 再创建 `AclLiteModel(model_path)`
  - 由它负责完成底层模型加载。
- 这一步的工程意义是：
**把“一个静态 OM 文件”变成“一个板端可执行的推理对象”。**

### 第四步：把 PC 端同样的数据处理流程搬到板端

### 第五步：把板端推理逻辑设计成“显示输入隐藏状态 + 固定滑动窗口”的时序工程

在 PC 端训练时，LSTM 是按**时间步动态循环**的；但到了昇腾板端，OM 模型是**静态图执行**，不能完全照搬训练态的那套逐步记忆传递方式，所以必须做工程化改写。

#### 这一步具体适配了什么

#### 1. 先把“动态时序推理”改成“固定窗口时序推理”

- 用 `[1-20]`、`[2-21]`、`[3-22]` 这种**滑动窗口**去近似**模拟原始 LSTM 的时序记忆**

#### ２．显式传入 h0/c0 作为输入

- **把上一次的隐藏状态和细胞状态，显式传给下一次推理**
- 如果完全不显式管理 `h0/c0`，那板端每次推理就都是“从零状态重新开始”，时序连续性会更差。显式暴露并更新 `h0/c0`，是在 OM 约束下尽可能保留 LSTM 记忆机制的办法。

所以你做的适配，本质上是在回答这个问题：

**在不能完全按原始 LSTM 动态执行的条件下，怎样尽量保留它的时序依赖能力？**

你的答案就是两件事：

- **显式传 `h0/c0`，尽量保留状态延续**
- **用滑动窗口，近似模拟长期记忆**。

### 第六步：结果不是只打印，而是做成标准化输出

推理完成后，脚本没有停在内存里，而是把结果做成了完整的输出流水线：

- `calculate_metrics()`：计算 RMSE（均方根误差）、MAE（平均绝对误差）、R²、Accuracy。
- `save_results()`：把预测值、真实值、误差写到 `csv/`；同时把评估指标写成 `json`。
- `create_visualizations()`：保存预测对比图、RMSE 曲线图、误差分布图到 `plots/`。
- `print_summary()`：在终端打印摘要。

这一步特别有工程味，因为它说明你搭建的不是“开发调试脚本”，而是一个**可验证、可留痕、可复现实验结果的推理工程**。

### 第七步：资源释放做了闭环

`cleanup()` 里会显式释放模型资源

# 针对昇腾平台做了哪些适配和优化？

## １.模型格式适配：`.pth → ONNX → OM`

## ２.静态图适配：固定输入维度，不能用动态 shape

## ３.芯片与精度适配：绑定 Ascend310B4，强制 FP32

## ４.模型接口适配：从单输入改成 3 输入 `x + h0 + c0`

## ５.LSTM 时序逻辑适配：用滑动窗口近似模拟动态记忆

## ６.板端运行时适配：用 ACLLite 封装 ACL 资源和模型执行

## ７.无 GUI 环境适配：板端不弹窗，图直接落盘

## ８.生命周期适配：补了资源释放闭环
