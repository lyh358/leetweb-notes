# 一、为什么要开发FusedAttention

## 1. 原始Attention做了什么

Attention的核心计算链为：

$$
S=\frac{QK^T}{\sqrt{d}}
$$

$$
P=\operatorname{Softmax}(S)
$$

$$
O=PV
$$

其中：

- `Q`表示查询特征；
- `K`表示被查询特征；
- `V`表示真正需要聚合的信息；
- `QKᵀ`计算不同位置之间的相关性；
- `Softmax`把相关性分数转换成权重；
- `Score×V`根据权重汇总信息。

在普通计算图中，这条链会被拆成多个独立算子：

```text
MatMul(Q,Kᵀ)
→ Scale
→ TransData
→ Softmax
→ TransData
→ MatMul(Score,V)
→ TransData
```

## 2. 原始方案的问题

每个独立算子通常对应一个Kernel。前一个Kernel计算结束后，中间结果往往需要：

```text
片上计算完成
→ 写回GM
→ 启动下一个Kernel
→ 再从GM读取
```

这里涉及三个概念：

- **Kernel**：在AI Core上执行的一段设备程序；
- **GM**：Device侧全局内存，容量较大，但访问延迟高于片上存储；
- **TransData**：在ND、NZ等不同数据格式之间转换。

原始Attention链路的主要问题不是矩阵乘本身太慢，而是：

1. 多个小Kernel反复启动；
2. `QKᵀ`结果和Softmax结果反复写回GM再读取；
3. Cube和Vector之间切换时伴随格式转换；
4. 中间张量无法在片上连续复用；
5. 小矩阵计算很快，调度和搬运反而占据较大比例。

## 3. 为什么ATC自动融合还不够

ATC能够将部分线性计算，例如：

```text
MatMul + Scale
```

融合成一个Kernel。但Softmax包含求最大值、指数、求和和除法等非线性操作，自动融合后仍可能保持独立。

因此，ATC自动融合版本仍需要：

- Softmax前后的格式转换；
- 中间结果写回GM；
- 多个Kernel之间的调度。

这也是为什么进一步选择自定义FusedAttention：

> 不是为了重新实现一个更快的MatMul，而是为了把两次矩阵乘、Scale和Softmax放进同一个Kernel，让中间结果留在片上，减少Kernel启动、GM往返和TransData。

# 二、算子的总体设计

## 1. 算子接口

当前原型配置为：

```text
FusedAttention(Q, K, V) → Output

Q/K/V：[1, 8, 64, 64]，FP16，FRACTAL_NZ
Output：[1, 8, 64, 64]，FP16，ND
```

一个Head内部的完整计算量约为：

```text
QKᵀ：       2×64×64×64 FLOPs
Scale：      64×64 FLOPs
Softmax：    约5×64×64 FLOPs
Score×V：    2×64×64×64 FLOPs
格式整理：   64×64 FLOPs
合计：       约1.08M FLOPs/Head
```

## 2. 三阶段流水线

整个Kernel划分为三个阶段：

```text
Phase 1：Q×Kᵀ，生成注意力分数
      ↓
Phase 2：Scale + Softmax，生成注意力权重
      ↓
Phase 3：Score×V，生成最终输出
```

完整的数据流为：

```text
Q/K/V位于GM
    ↓ MTE2
进入L1
    ↓ MTE1
进入L0A/L0B
    ↓ Cube
完成QKᵀ
    ↓
结果进入UB
    ↓ Vector
完成Scale和Softmax
    ↓
Score进入L1/L0，V从GM进入L1/L0
    ↓ Cube
完成Score×V
    ↓ Vector
完成输出格式整理
    ↓ MTE3
写回GM
```

## 3. 为什么使用Cube+Vector混合实现

Ascend AI Core内部不同单元擅长不同操作：

| 单元 | 适合的工作 | 本算子中的任务 |
| --- | --- | --- |
| Cube | 矩阵乘加 | `QKᵀ`、`Score×V` |
| Vector | 逐元素、规约和非线性 | Scale、Max、Exp、Sum、Div |
| MTE | 数据搬运 | GM、L1、L0、UB之间搬运 |
| Scalar | 控制与地址计算 | 循环、偏移和同步控制 |

纯Vector方案需要用向量指令模拟矩阵乘，文档记录时延约5183 μs，说明计算单元选择错误会导致严重性能退化。

因此最终设计为：

> 矩阵乘交给Cube，Softmax交给Vector，再通过同一个Kernel中的片上存储和流水线同步完成协同。

# 三、面试官最关注的关键技术

## 1. 单Kernel融合

自动融合版本仍有多个Kernel，自定义版本把以下过程合并：

```text
QKᵀ + Scale + Softmax + Score×V + 输出格式整理
```

主要收益是：

- Kernel数量由详细Profiling口径下的9个降为1个；
- 减少固定的Kernel启动和运行时调度；
- 消除算子之间不必要的同步；
- 为片上数据复用创造条件。

## 2. 片上数据驻留与复用

原始方案中：

```text
QKᵀ结果 → GM → Softmax读取
Softmax结果 → GM → 第二次MatMul读取
```

自定义方案中：

```text
QKᵀ结果 → LOC/UB
Softmax直接从UB读取
Softmax结果继续在片上提供给Score×V
```

中间Score不再写回GM，因此：

- 中间GM往返由3次降为0次；
- 不再需要GM侧临时Workspace；
- 减少中间张量读写和格式转换。

这是整个方案最核心的优化，不是单纯减少数学计算量。

## 3. 多核Head并行

8个Attention Head之间不存在数据依赖，因此采用：

```text
BlockDim = headNum = 8
```

每个AI Core根据自己的`blockIdx`处理一个Head：

```text
Core 0 → Head 0
Core 1 → Head 1
...
Core 7 → Head 7
```

这样可以把原本的Head串行处理变为核间并行，同时每个Core写入独立输出区域，不需要跨核规约。

这是一种自然的并行划分方式，因为：

- Head之间独立；
- 每个Head工作量相同；
- 不需要复杂的跨核同步；
- 负载较容易保持均衡。

## 4. Tiling与K维切分

**Tiling**就是把大矩阵切成适合片上存储和计算单元处理的小块。

Ping-Pong版本把K维，也就是`headDim=64`，切成两个32维Chunk：

```text
Chunk 0：0～31
Chunk 1：32～63
```

第一阶段：

```text
Q[:,0:32] × K[:,0:32]ᵀ → partial Score 0
Q[:,32:64] × K[:,32:64]ᵀ → partial Score 1
LOC中累加 → 完整Score
```

第三阶段：

```text
Score[:,0:32] × V[0:32,:] → partial Output 0
Score[:,32:64] × V[32:64,:] → partial Output 1
LOC中累加 → 完整Output
```

### 为什么切K维，而不是随便切一维

Softmax需要看到一整行注意力分数。如果错误地切分Score的列并分别做Softmax，会改变数学含义。

切K维的好处是：

- 两个Chunk只产生矩阵乘的部分和；
- 部分结果在LOC中累加；
- 累加完成后仍得到完整的64×64 Score；
- Softmax只在完整Score上执行一次，数学结果不变。

## 5. Ping-Pong双缓冲

单缓冲的执行方式是：

```text
搬运Chunk 0 → 计算Chunk 0 → 搬运Chunk 1 → 计算Chunk 1
```

双缓冲准备Ping和Pong两组Buffer：

```text
Ping正在计算Chunk 0
Pong同时搬运Chunk 1
```

这样可以使MTE搬运与Cube计算重叠，隐藏一部分访存等待。

当前设计只切成两个Chunk，是因为：

- 两段切分已经能够形成搬运与计算重叠；
- 当前矩阵较小，切得过细会增加同步和控制开销；
- 两组Buffer对片上存储压力较小；
- 在性能收益与Kernel复杂度之间较平衡。

## 6. 事件同步与流水线控制

MTE、Cube和Vector属于不同流水线，不能默认认为数据已经准备好。设计中通过：

```text
set_flag()
wait_flag()
```

建立生产者—消费者关系：

```text
MTE2搬运完成
    ↓ 通知
MTE1可以把数据送入L0
    ↓ 通知
Cube可以开始mad计算
    ↓ 通知
Vector可以处理Cube结果
```

Ping和Pong使用不同`EVENT_ID`，避免两组Buffer错误覆盖或流水线之间互相阻塞。

核心原则是：

> 既要保证消费者不会读取尚未完成的数据，也要避免把本来可以并行的两条流水线强制串行化。

## 7. 片上存储规划

主要存储层级包括：

| 存储 | 用途 |
| --- | --- |
| L1 | 保存从GM搬入的Q、K、V及Score分块 |
| L0A/L0B | 为Cube准备矩阵A和矩阵B |
| L0C/LOC | 保存FP32矩阵乘累加结果 |
| UB | 保存FP16 Score、Softmax临时量和输出 |

当前设计的片上占用约为：

```text
L1：约16 KB
UB：约32 KB
L0：约32 KB
合计：约80 KB
```

通过复用Phase 1和Phase 3不会同时使用的Buffer，Ping-Pong没有线性翻倍整个片上内存占用。

## 8. 数据格式适配

昇腾Cube为了提高矩阵计算效率，通常使用分形数据格式，而业务输入输出常使用普通ND格式。

本方案涉及：

- `ND`：普通连续张量格式；
- `NZ/ZZ/zN`：面向Cube矩阵块的分形排布方式。

设计策略是：

1. Q/K/V在算子入口使用FRACTAL_NZ，由ATC负责入口格式适配；
2. 通过MTE1加载参数和tile顺序表达K转置，避免额外Transpose Kernel；
3. Cube输出进入UB后，在UB内部完成最终zN到ND的数据整理；
4. 只把最终Output写回GM，不把中间Score写回。

这里的关键不是记住每种格式的所有排列细节，而是理解：

> 把格式转换嵌入数据搬运和片上处理过程，避免单独启动TransData或Transpose Kernel。

## 9. 精度策略

当前设计中：

- Q/K/V和UB中间数据以FP16存储，降低带宽和片上空间占用；
- Cube乘加结果在LOC中以FP32累加；
- 再转换成FP16进入UB完成Softmax和后续处理。

这种方案兼顾吞吐和存储，但Softmax使用FP16仍存在数值稳定风险，最终必须通过：

- 单算子Golden数据对比；
- 余弦相似度；
- MSE或最大绝对误差；
- 极端输入测试；
- 整网端到端精度验证；

确认是否能够进入最终模型。

# 四、性能对比与结论

## 1. 统一口径的性能表

以下优先采用《FusedAttention三方案理论性能Profiling报告》的详细统计口径：

| 方案 | Kernel数 | GM搬运量 | GM中间往返 | 理论时延 | 实测时延 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原始零融合 | 10 | 约205 KB | 3次 | 约58 μs | 约1470 μs |
| ATC自动融合 | 9 | 约197 KB | 3次 | 约53 μs | 约99.9 μs |
| 自定义单缓冲 | 1 | 约32 KB | 0次 | 约7.8 μs | 待验证 |
| 自定义Ping-Pong | 1 | 约32 KB | 0次 | 约7.6 μs | 待验证 |

不同文档中Kernel数量和搬运量存在不同统计边界，例如是否计入输入格式转换。面试时使用上表即可，不要同时混用另一套7/6 Kernel或82 KB统计口径。

## 2. 自定义方案取得的理论优势

相对于ATC自动融合版本，自定义方案在理论模型中实现：

- Kernel数量：9 → 1；
- 中间GM往返：3次 → 0次；
- GM搬运量：约197 KB → 32 KB，按该统计口径约减少84%；
- GM临时Workspace：约24 KB → 0；
- 理论时延：约53 μs → 约7.6～7.8 μs；
- 两个矩阵乘使用Cube，Softmax使用Vector，避免纯Vector模拟矩阵乘。

## 3. Ping-Pong带来了多少额外收益

对于当前64×64小矩阵：

```text
单缓冲理论时延：约7.8 μs
Ping-Pong理论时延：约7.6 μs
整体理论改善：约2.6%，可近似说约3%
```

Ping-Pong收益不高的原因是：

- Cube计算64×64小矩阵非常快；
- 整个算子主要受Kernel启动和搬运固定开销影响；
- 可以被双缓冲隐藏的计算区间较短。

因此，本项目中Ping-Pong更重要的意义是：

> 建立正确的搬运—计算流水结构，为更大矩阵或更高负载场景预留扩展能力，而不是在当前小Shape上追求夸张的收益数字。

## 4. 为什么99.9 μs不能直接与7.6 μs计算“实测加速比”

- 99.9 μs是ATC自动融合方案的板端实测；
- 7.6 μs是基于带宽、FLOPs和Kernel启动假设得到的理论预测；
- 两者统计性质不同，不能宣称已经获得约13倍实测加速。

正确说法是：

> 理论Profiling显示自定义方案具有显著降低Kernel数和GM搬运的潜力，但最终收益仍需完成算子编译、单算子板端测试、OM集成和整网验证后确认。

# 五、为什么这个方案有价值

## 1. 它解决的是端侧真实问题

这个方案并没有改变Attention数学公式，而是针对NPU的执行特性重新组织计算：

```text
算法公式不变
→ 改变Kernel边界
→ 改变数据所在的存储层级
→ 改变Cube、Vector和MTE的协同方式
→ 减少非计算开销
```

这体现了部署优化与算法优化的区别：算法关注“算什么”，Kernel优化关注“怎样在硬件上高效地算”。

## 2. 涉及的面试高价值技术点

该设计能够体现以下能力：

- 能从Profiling结果判断模型受计算、搬运还是调度限制；
- 理解Ascend AI Core的Cube、Vector、MTE和存储层级；
- 能进行算子融合和Kernel边界设计；
- 能设计Host侧Tiling和Device侧Kernel；
- 能进行多核任务划分；
- 能使用Ping-Pong双缓冲隐藏访存；
- 能通过Event完成跨流水线同步；
- 能规划L1、L0和UB等片上存储；
- 能处理NZ、ND等数据格式；
- 能区分理论模型、单算子实测和整网端到端结果。

## 3. 方案的适用边界

该方案更适合：

- 同时包含矩阵乘和非线性操作的复合算子；
- 中间结果反复写回GM的计算链；
- 中小Shape、片上存储能够容纳关键Tile的场景；
- 多Head之间相互独立、适合多核并行的Attention。

不一定适合：

- 只有单个MatMul的场景，直接使用成熟内置算子更合适；
- 只有逐元素计算的场景，不需要Cube+Vector混合；
- Shape过大、无法在片上保存关键中间数据的场景；
- 动态Shape变化很大、需要复杂通用Tiling的场景；
- 当前自动融合已经达到较好性能，定制收益不足以覆盖维护成本的场景。

# 六、口语化项目介绍

## 30秒版本

> SPF模型的Attention原本由多个算子组成，虽然ATC可以自动融合一部分，但Softmax前后仍有独立Kernel、格式转换和中间结果写回GM的问题。我的思路是开发一个FusedAttention自定义算子，把QK转置、Scale、Softmax和Score乘V放到同一个Kernel里。矩阵乘由Cube完成，Softmax由Vector完成，中间Score保留在片上UB，不再反复写回GM。同时按照Head分配AI Core，并在K维上做两段Ping-Pong，使数据搬运和Cube计算能够重叠。理论Profiling中，Kernel数从9个降到1个，GM搬运量从约197 KB降到32 KB。自定义版本当时还没有完成最终板端集成，因此这些属于已完成设计和理论收益，不是最终实测结果。

## 90秒版本

> 我在完成SPF计算图优化后继续向Kernel层深入。Attention的计算本身只有QK转置、Scale、Softmax和Score乘V，但在NPU上如果由多个标准算子分别执行，中间结果就需要反复写回GM，同时还会产生Kernel启动和NZ、ND格式转换。ATC虽然能融合MatMul和Scale，但Softmax仍保持独立，所以自动融合版本实测约99.9微秒。
>
> 我设计的FusedAttention把整条链合并到一个Kernel。两个矩阵乘放在Cube上执行，Softmax放在Vector上执行，QK结果从LOC进入UB后直接完成Softmax，再送给第二次矩阵乘，中间结果不写回GM。8个Head相互独立，因此使用8个AI Core、每核处理一个Head。在单核内部，我把K维从64切成两个32维Chunk，使用Ping-Pong双缓冲，让后一块的MTE搬运与前一块Cube计算重叠，并通过不同EVENT_ID保证同步正确。
>
> 按详细理论Profiling口径，自动融合版本有9个Kernel、约197 KB GM搬运，自定义版本降为1个Kernel和约32 KB搬运；单缓冲与Ping-Pong理论时延分别约7.8和7.6微秒。但这部分当时没有完成最终OM集成和板端实测，所以我把它定义为已完成的算子工程与优化设计，而不是已经交付的性能成果。最终整网572到320微秒的收益仍然来自前面的计算图优化。

# 七、高频追问与面试简答

## 1. 为什么不直接依赖ATC自动融合？

> ATC能够融合部分线性算子，但Softmax包含规约和指数等非线性计算，前后仍保留独立Kernel和格式转换。自定义算子的目的，是跨过Softmax这个自动融合边界，把整个Attention放在同一Kernel中，让中间结果留在片上。

## 2. 为什么不是把MatMul写得更快？

> ATC内置MatMul本身已经针对Cube优化。当前小Shape下，主要问题是Kernel启动、GM往返和TransData，而不是Cube算力不足，所以优化重点是减少非计算开销。

## 3. 为什么必须把Cube和Vector放在同一个Kernel？

> 矩阵乘适合Cube，Softmax适合Vector。如果拆成不同Kernel，中间结果通常需要写回GM再读取；放在同一Kernel后，可以通过LOC、UB和L1直接传递数据，保留片上复用优势。

## 4. 多核是怎么划分的？

> Head之间没有数据依赖，因此设置BlockDim等于Head数量，每个AI Core处理一个Head，并根据blockIdx计算输入输出偏移。这样不需要跨核规约，任务量也比较均衡。

## 5. 为什么Ping-Pong切K维？

> K维切分后，两段矩阵乘结果可以在LOC中累加，累加完成后仍得到完整Score，Softmax只执行一次，数学含义不变。同时后一段数据搬运可以与前一段Cube计算重叠。

## 6. 为什么不切Score列并分别做Softmax？

> Softmax需要对完整一行计算最大值和归一化分母。如果把一行拆开分别做Softmax，得到的权重不再等价，除非增加额外的全局规约和校正逻辑。

## 7. 双缓冲怎样保证不会覆盖数据？

> Ping和Pong使用不同的Buffer偏移和EVENT_ID。生产者完成搬运后通过set_flag通知消费者，消费者通过wait_flag确认数据就绪；Buffer重新使用前也要确认上一轮计算已经结束。

## 8. 为什么当前Ping-Pong理论收益只有约3%？

> 当前矩阵只有64×64，Cube计算非常快，算子主要受Kernel启动和搬运固定开销影响。双缓冲能隐藏的计算区间较短，所以整算子收益有限；矩阵规模增大后，计算和搬运重叠的收益才会更明显。

## 9. 为什么使用NZ格式？

> NZ是适合Cube分块矩阵计算的数据排布。让输入以NZ进入Kernel，可以减少运行时额外整理；K转置等操作也可以结合MTE加载方式表达，而不必单独启动Transpose Kernel。

## 10. 片上80 KB是怎样规划的？

> L1主要保存输入和Score分块，L0A/L0B给Cube提供矩阵，L0C保存FP32累加结果，UB保存Score、Softmax临时量和输出。Phase 1与Phase 3复用部分Buffer，因此Ping-Pong不会让全部片上空间翻倍。

## 11. 自定义算子怎样验证正确性？

> 先使用CPU或ONNX实现生成Golden输出，分别比较QK、Softmax和最终输出；再在板端检查余弦相似度、MSE和最大误差；最后替换整网子图，验证端到端精度和稳态时延。

## 12. 理论时延为什么与实测差异很大？

> 理论模型通常只根据FLOPs、带宽和假设的Kernel启动时间计算，没有完整覆盖L2 Cache Miss、流水线停顿、实际指令效率、运行时调度和编译器策略。因此理论值用于比较方案方向，最终结论必须以同条件板端实测为准。

## 13. 这个算子最终取得了多少实际收益？

> 自定义版本尚未完成最终OM集成和板端实测，所以不能给出实际加速数字。可以确认的是，理论设计把Kernel数从9个降到1个，中间GM往返从3次降到0次，详细估算中的GM搬运从约197 KB降到32 KB。最终收益仍需实测验证。

## 14. 这个工作的最大技术难点是什么？

> 难点不是把Attention公式写出来，而是在有限片上存储中同时处理数据格式、Cube和Vector分工、MTE搬运、跨流水线同步以及精度问题，并保证融合后的数学结果与原模型一致。

# 八、最后记住的五句话

1. **问题**：Attention被拆成多个小Kernel，中间结果反复写回GM，并产生TransData和调度开销。
2. **核心方案**：把`QKᵀ、Scale、Softmax、Score×V`融合成一个Cube+Vector混合Kernel。
3. **关键手法**：片上驻留、多核Head并行、K维Tiling、Ping-Pong双缓冲、Event同步和格式融合。
4. **理论优势**：详细口径下Kernel由9降至1，GM搬运约197 KB降至32 KB，中间GM往返由3次降至0次。
5. **真实性边界**：7.8/7.6 μs是理论预测，自定义版本尚未完成最终板端实测；整网572→320 μs来自P0图优化，不来自FusedAttention。
