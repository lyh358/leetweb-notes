# 真实性边界与简历口径

> 华为实习因包含图优化实测、失败实验和自定义算子设计三种不同完成度，单独维护了更详细的[华为实习真实性边界与简历口径](04-华为实习/真实性边界与简历口径.md)。

## 1. 为什么单独维护这份文件

面试官通常不会只问“会不会”，而会检查：是否亲自实现、是否真实运行、是否完成验证、指标如何计算。简历可以概括，但口头回答必须区分事实层级。

## 3. 必须修正或准备解释的冲突

### 3.1 锂电池指标冲突

现有《昇腾项目梳理》写“四组电池、准确率 92.8%~98.5%”；最终简历写“五组平均 RMSE≤0.004Ah、准确率>99.8%、EOL误差<2循环”。二者可能来自不同版本实验，但当前没有明细证明。

面试前必须确定：

- 五组电池编号；
- 训练、验证、测试怎样划分，是否跨电池泛化；
- RMSE 是归一化空间还是反归一化后的 Ah；
- “准确率”定义，回归任务不能只说普通分类准确率；
- EOL 阈值是额定容量的 80% 还是绝对 1.4Ah；
- 是否避免用未来数据拟合标准化、GRA、PCA，防止数据泄漏。

如果无法补齐，建议简历暂时只保留可复核的 RMSE，并去掉“准确率”。

### 3.2 LSTM 状态传递冲突

同一文档一处说 OM 不能自然把 `h/c` 连续传到下一次推理，最终依赖滑动窗口；另一处又说把上一窗口 `hn/cn` 显式传给下一窗口。

这两种方案语义不同：

- 独立滑窗：每个窗口 `h0/c0=0`，窗口本身提供局部历史；不会把重叠窗口重复累积到状态中。
- 状态跨窗：上次 `hn/cn` 作为下次输入；若窗口高度重叠，会重复消费大量相同时间步，状态语义可能偏移。

必须回看真实板端脚本确定采用哪一种。没有脚本时，面试中只能说“接口支持显式状态；实际评估需要对比独立滑窗和状态跨窗，当前备份不足以确认最终策略”。

### 3.3 分布式系统完成度

简历当前写法容易让人理解为三层系统已端到端完成。当前代码能确认的是：

1. ROS-Protobuf 子系统代码存在；
2. Qt 本地 Linux 监控代码存在；
3. gRPC Agent/Center 原型代码存在；
4. 三者的完整运行时集成、Qt gRPC 客户端、配置下发闭环和 compose 编排不存在。

安全说法：

> 我把两个已有子系统抽象为统一 Protobuf 契约，并实现了 gRPC Agent/Center 原型，验证架构设计。当前版本的 Qt 仍是本地监控 UI，和 gRPC 集群服务的代码级接入、配置反向通道与规模化压测是下一阶段工作。

## 4. 面试禁止用语

- 没有日志时不要说“完全解决”“零丢包”“稳定运行数月”。
- 没有对照实验时不要说“显著提升”“大幅降低”。
- 调用库封装时不要说“我实现了底层驱动”；应说“我配置并使用驱动，理解其底层路径”。
- 原型没有编译时不要说“已跑通”；应说“按接口实现了原型，当前材料未包含编译验证”。
- README 中的计划、命令和架构图不能替代实际运行记录。
