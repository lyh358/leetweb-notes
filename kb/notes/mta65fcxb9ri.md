# 实习经历复盘思路——禾赛

实习经历**不建议把整段经历硬套成一个STAR**。因为禾赛实习包含AUTOSAR开发、功能安全诊断、调试工具和版本交付多条工作线，如果只讲一个S、T、A、R，容易把很多独立任务混在一起。

更合适的是：

> **“实习全景＋职责地图＋代表性案例STAR＋技术追问＋复盘”**

我根据最终版简历中的禾赛条目进行了梳理。秋招简历最终版v2.3.pdf

# 一、实习经历的推荐结构

## 第一部分：实习全景

先用一分钟回答“你在禾赛实习是做什么的”。

这里需要交代：

- 公司和部门：禾赛科技软件部，雷达功能与功能安全组；
- 产品场景：车载激光雷达MCU软件；
- 硬件平台：E311X双核Cortex-R5；
- 软件平台：AUTOSAR Classic和RTA-OS；
- 工作类型：嵌入式功能开发、功能安全诊断、调试工具、软件包发布；
- 项目性质：参与小米、理想、吉利等量产项目。

这部分相当于整段实习的“大S”，但不要急着讲某个功能的源码。

推荐口径：

> 我在禾赛软件部的雷达功能与功能安全组担任嵌入式软件实习生，主要参与新一代车载激光雷达MCU软件开发。系统运行在E311X双核Cortex-R5平台上，使用AUTOSAR Classic和RTA-OS，面向ISO 26262功能安全和量产交付要求。我的工作覆盖嵌入式功能开发、UDS/DTC诊断、调试工具以及APP和BOOT软件包发布。

# 二、建立职责地图

接下来不要马上进入STAR，而是先让面试官知道你具体负责哪几类事情。

根据简历，可以整理成四条工作线：

| 工作线             | 主要内容                                                    | 面试定位           |
| ------------------ | ----------------------------------------------------------- | ------------------ |
| AUTOSAR嵌入式开发  | ASW/RTE/BSW/MCAL/CDD、OS任务、多核分区、状态机、参数与Flash | 系统背景与基础知识 |
| 功能安全与诊断     | 入口电压、Rx Start Signal、ADC、CRC、SPAD监控、UDS/DTC/DEM  | 最核心的STAR案例   |
| 调试工具与问题定位 | PC1300 UDP协议、EfuseId/Chip ID、PTC调试指令                | 第二个STAR案例     |
| 工程规范与交付     | MISRA C、MemMap、IAR/Tasking、APP/BOOT Release与Factory包   | 工程能力与责任意识 |

这样面试官能够先形成一张地图：

```
车载激光雷达MCU软件
    ├── 功能开发
    ├── 安全诊断
    ├── 调试工具
    └── 版本交付
```

# 三、选择代表性工作写成“小STAR”

整段实习不套一个STAR，而是在其中选择两到三个有代表性的任务，每个任务单独使用STAR。

## 案例一：功能安全诊断开发

这是最值得重点准备的案例。

可以从以下功能中选择一到两个最熟悉的：

- 入口电压诊断；
- ADC诊断；
- Program/Flash CRC；
- Rx Start Signal；
- SPAD Chip Monitor。

STAR需要回答：

- **S**：为什么激光雷达需要监控这个故障；
- **T**：需求要求你检测什么、满足什么故障判定和恢复逻辑；
- **A**：怎样拆解需求、采集状态、去抖、设置DTC、接入DEM并进行故障注入；
- **R**：功能通过实机和诊断链路验证，并进入对应版本交付。

这个案例重点证明：

> 你能够独立完成“需求分析—代码实现—故障注入—诊断上报—实机验证”的完整闭环。

## 案例二：PC1300遥测协议或PTC调试工具

这类案例更适合体现问题定位和工具开发能力。

### PC1300案例

核心故事可以是：

```
多台雷达同时监控
        ↓
现有UDP数据无法区分具体设备
        ↓
协议中增加EfuseId和Chip ID
        ↓
上位机能够准确区分数据来源
```

### PTC调试指令案例

核心故事可以是：

```
芯片电源域异常难以远程定位
        ↓
需要频繁修改代码或连接现场工具
        ↓
增加上位机调试指令
        ↓
远程切换通道、读取ADC并判断阈值
        ↓
提高台架和产线定位效率
```

这两个案例不一定都长篇准备，选择一个作为主案例，另一个作为备用追问即可。

## 案例三：软件版本发布

Release和Factory软件包发布可以准备成一个较短的责任案例：

- 发布的软件包分别面向什么场景；
- 发布前需要检查哪些内容；
- 如何确认配置、版本号和编译环境；
- 如何避免发布错误；
- 发布后怎样保存记录和支持问题追溯。

这个案例用于证明：

> 你不仅写过功能代码，也接触过量产项目的集成、版本管理和交付流程。

# 四、哪些内容不需要写成STAR

以下内容更适合整理成技术知识和高频问答，不必强行构造故事：

- AUTOSAR的ASW、RTE、BSW、MCAL和CDD分别是什么；
- RTE如何连接软件组件与底层服务；
- RTA-OS任务和多核分区是什么；
- UDS、DTC和DEM是什么关系；
- 去抖、故障确认和故障恢复怎么设计；
- Program CRC和Flash CRC有什么作用；
- MISRA C和MemMap解决什么问题；
- APP、BOOT和Factory软件包有什么区别。

这些问题通常来自面试官看到简历关键词后的直接追问，采用：

> **概念是什么 → 项目中怎么用 → 起什么作用**

三句话回答即可。

# 五、禾赛实习最终文档结构

建议整理成以下七部分：

## 1. 实习口语化介绍

用一分钟讲清楚部门、产品、平台、工作范围。

## 2. 激光雷达MCU系统全景

说明激光雷达中MCU负责什么，以及AUTOSAR软件大致怎样分层。

## 3. 个人职责边界

按照功能开发、诊断、工具和发布四条线划分。

## 4. 核心案例一：功能安全诊断STAR

选择一个你最熟悉的诊断功能重点展开。

## 5. 核心案例二：调试工具STAR

选择PC1300协议改造或PTC调试指令。

## 6. 简历关键词高频问答

覆盖AUTOSAR、RTE、OS、UDS、DTC、DEM、CRC、MISRA C、MemMap等概念。

## 7. 困难、协作与复盘

准备以下问题：

- 遇到的最大问题是什么；
- 怎样和正式员工、测试或其他模块协作；
- 需求不明确时怎么处理；
- 出现问题时如何定位；
- 如果重新做一次会怎样改进。

# STAR在实习中的正确用法

```
整段实习
使用“全景—职责—案例—复盘”组织

具体任务
使用STAR展开
```

也就是说：

> **STAR适合讲一件具体的事，不适合直接承载整段包含多条工作线的实习经历。**

接下来最合理的顺序，是先整理禾赛实习的**系统与岗位全景**，让面试官理解激光雷达MCU、AUTOSAR和功能安全组到底在做什么，然后再选择具体功能进入STAR案例。
