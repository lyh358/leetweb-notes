# 二、低功耗

## 01 低功耗的休眠和唤醒的触发源是什么

| MCU 低功耗模式 | 功耗水平 | 允许的唤醒源 | RTOS 适配场景 |
| --- | --- | --- | --- |
| Sleep（睡眠） | 较高 | **几乎所有中断**（SysTick、GPIO、UART 等） | **轻休眠，快速响应**（如**毫秒**级唤醒） |
| Stop（停止） | 中等 | **外部中断**、**RTC**、LPTIM、**WKUP 引脚** | **主流低功耗场景**（如**秒级 / 分钟级**唤醒） |
| Standby（待机） | 极低 | **仅 WKUP 引脚、RTC 闹钟**、BOD 中断 | **深度休眠**（如**分钟级 / 小时级**唤醒） |

唤醒的本质是「中断触发 MCU 退出低功耗模式 → 恢复 RTOS 任务调度」，因此=={pink}所有唤醒源最终都是硬件中断==；

“=={pink}软件触发源==” 只是 RTOS 对=={pink}硬件中断的上层封装==，并非独立触发源。

## 02 RTOS 系统如何做 Tickless 低功耗？

- **=={pink}Tickless==**

=={yellow}取消1ms周期的sysTick中断，===={yellow}算出下一个任务还要多久才就绪，设个定时器，CPU 睡过去，到点再醒。==****- **=={pink}Tick==**

=={green}每 1ms（configTICK_RATE_HZ=1000）来次 SysTick 中断，CPU 被迫醒来检查调度==- **考察场景**
考察你是否理解 RTOS 为什么周期 Tick 会影响低功耗，以及 Tickless 如何减少无意义唤醒。
- **底层实现原理**

1. 普通 RTOS 依赖 SysTick 周期中断 维护系统节拍，比如每 1ms 进一次中断，用来更新时间、检查延时任务、触发调度。
2. =={pink}**Tickless 的核心是**==：当系统发现 =={green}一段时间内没有任务需要运行== 时，就=={green}临时关闭周期 Tick==，改用=={yellow}低功耗定时器一次性睡到最近的唤醒点==。
3. 进入低功耗前，内核会计算下一个任务超时时间，比如最近有任务 `vTaskDelay(100)`，那就让低功耗定时器设置成 100 tick 后唤醒。
4. 睡眠期间如果有外部中断，比如 GPIO、UART、RTC，也可以提前唤醒；醒来后 RTOS 会根据实际睡眠时间 **补偿系统 tick**。
5. 所以 Tickless 的本质是：空闲时不再周期性打断 CPU，而是睡到下一次真正需要调度的时间点。

## 04 一个低功耗带屏产品，如何设计系统架构？

- **考察场景**
考察你是否能 综合 MCU、显示、RTOS、低功耗策略和外设设计，实现屏幕可用且功耗低的系统。
- **底层实现原理**

1. MCU 核心选择：高性能核心可满足显示刷新需求，但需要支持 多级低功耗模式（Sleep/Stop/Standby）。
2. 显示驱动：屏幕刷新率和显示内容决定 CPU/MCU 活动周期。使用 DMA / 画面缓存，避免 CPU 持续刷新，减少功耗。
3. RTOS / Scheduler：采用 低功耗 Tickless 模式，空闲时让 MCU 进入 Stop 或 Sleep，保证显示更新或用户输入时可以唤醒。
4. 外设管理：UART/I2C/SPI/ADC/ 触摸 / 背光等按需开启，非必要时关闭或用外设独立 DMA 运行，避免唤醒 CPU。
5. 中断唤醒设计：触摸、按键、RTC、传感器等外设产生中断唤醒 MCU，RTOS 通过事件或信号唤醒对应任务。
6. 电源域划分：屏幕背光、电源模块、MCU 内核和外设可独立控制，深睡模式下只保留必要唤醒源。
7. 功耗优化策略：静态画面可用 e‑ink 或帧缓冲保持模式，减少刷新率；动态画面按需刷新 DMA；减少无效 Tick 和中断唤醒。

- **设计原则**

1. =={green}任务分层==：=={pink}UI、后台逻辑、传感器、通信分开，便于**按需唤醒**==。
2. =={green}外设独立性==：尽量让=={pink}外设通过 **DMA / 独立时钟**工作，CPU 可休眠==。
3. =={green}低功耗优先==：深睡模式下只保留必要唤醒源，中断触发再恢复运行。
4. 显示优化：静态画面尽量少刷新，动态画面用 DMA 或硬件加速。
5. 电源域和时钟域划分：可按模块控制开关，降低静态漏电。

- 延申知识点
Tickless RTOS 与 MCU Stop/Sleep 配合
e‑ink 或 LCD 刷新策略对功耗的影响

## 05 低功耗场景下如何处理 UART?

- **考察场景**
考察你是否理解 UART 在低功耗下既可能是耗电源，也可能是唤醒源，关键是睡前处理发送、接收和唤醒配置。
- **底层实现原理**

1. 进入低功耗前，如果 UART 正在发送，要先等待 TX FIFO /shift register 发送完成，否则最后几个字节可能丢失。
2. 如果低功耗期间不需要串口通信，可以关闭 UART 外设时钟、DMA、接收中断，降低动态功耗。
3. 如果 UART 需要作为唤醒源，要配置 RX 引脚唤醒、起始位唤醒、地址匹配唤醒等能力，同时保留对应低功耗时钟。
4. 深睡模式下主时钟可能关闭，UART 波特率时钟可能失效，所以要确认当前低功耗模式下 UART 是否还能接收数据。
5. 唤醒后要重新恢复 系统时钟、UART 时钟、波特率、DMA / 中断状态，否则会出现乱码、收不到数据或只收到部分数据。

## 06 MCU 如何定位系统被谁频繁唤醒？

- **考察场景**
考察你是否理解 MCU 低功耗不等于静止，频繁唤醒会增加功耗，必须找到唤醒源。
- **底层实现原理**

1. MCU 进入低功耗模式（Sleep/Stop/Standby）时，CPU 不执行指令，但外设中断、RTC、GPIO、DMA 等可以触发唤醒。
2. 定位唤醒源的核心方法是利用 MCU 提供的 **低功耗状态唤醒标志寄存器**，大多数 MCU 会在唤醒时记录是哪种中断导致的。
3. 如果低功耗唤醒频繁，可以通过：

- 读取唤醒标志寄存器（Wakeup Flags）
- 统计各唤醒事件次数
- 结合外设状态和任务日志分析唤醒来源

1. 在 RTOS 下，也可以用 idle hook + tickless 模式 统计每个外设中断或事件引起的空闲唤醒次数。
2. 核心原则是：唤醒必留痕迹，分析痕迹找频繁唤醒的具体源。
